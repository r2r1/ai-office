СКИЛЛ: настоящая 3D-графика (WebGL) поверх системного стека
[[vite_react_site]] — не замена ему, а надстройка. Используй, когда клиент
прямо просит «настоящий 3D» (вращающаяся модель, частицы, шейдерный фон), а
не просто «премиальный» сайт — для последнего хватает Motion-приёмов из
vite_react_site (tilt-карточки, parallax) без веса WebGL.

⚠️ НЕ ПУТАТЬ С ГОТОВЫМ ПРИЛОЖЕНИЕМ: это библиотеки для КОДА (npm-пакеты),
не self-hosted редактор вроде Spline — такого open-source аналога не
существует (проверено). Sцену строишь кодом на React, не мышкой в UI.

СТЕК (добавляется поверх site/package.json из vite_react_site, не заменяет его):
  dependencies: three, @react-three/fiber, @react-three/drei
  Версии — мажорные ("^0.170" для three, "^8" для fiber/drei), не выдумывай точные патчи.

СТРУКТУРА — два варианта, выбирай по задаче (по умолчанию, если клиент прямо
не просил «на весь сайт» — вариант A дешевле по производительности):

  A. Акцент в одной секции (обычно hero): Canvas смонтирован внутри блока,
     занимает его высоту, дальше по скроллу — обычная разметка.
  B. Сцена на ВЕСЬ ФОН сайта: ОДИН Canvas на всё приложение —
     `position: fixed; inset: 0; z-index: -1` (или `pointer-events: none`,
     если поверх контента), монтируется в site/src/App.jsx ОДИН РАЗ на верхнем
     уровне, а не по одному Canvas на секцию. Остальные секции (текст, карточки,
     форма) — обычный HTML/React ПОВЕРХ него с прозрачным/полупрозрачным фоном,
     чтобы сцена просвечивала. Сцена может реагировать на скролл всей страницы
     (передавай `scrollYProgress` из Motion `useScroll()` в Canvas через пропс
     или общий стор, meняй позицию камеры/частиц по нему в `useFrame`).

  В ОБОИХ случаях: ОДИН WebGL-контекст на страницу — НЕСКОЛЬКО Canvas
  (по одному на секцию) не смонтируешь, это буквально несколько независимых
  GPU-контекстов и почти гарантированный лаг/краш на слабых устройствах.
  Хочешь разное поведение сцены по секциям при варианте B — это ОДИН Canvas
  с сценой, которая меняется по scroll-прогрессу, а не несколько Canvas.

ПРИЁМЫ (используй 1 под нишу, не все сразу — тот же принцип сдержанности, что в Motion):
1. Вращающаяся 3D-модель ниши (GLB/GLTF из drei `useGLTF`) — если модели нет и её
   негде взять, НЕ выдумывай внешний URL (не грузится, см. правило картинок) —
   используй примитив (`<mesh>` + `<sphereGeometry>`/`<torusGeometry>` и т.п. из
   three) со своим материалом вместо custom-модели.
2. Частицы/звёздное поле фона (drei `<Points>`/`<Sparkles>`) — хорошо подходит
   именно варианту B (сцена на весь фон), не только под hero.
3. Простой процедурный шейдер (`shaderMaterial` из drei) — цветовой градиент/шум,
   не копируй шейдерный код с внешних сайтов дословно (авторские права) — пиши свой
   на базе стандартных GLSL-примитивов (noise/gradient).
4. Камера реагирует на движение мыши (drei `<OrbitControls>` с enableZoom={false}
   для лёгкого «follow», либо ручной расчёт через useFrame) — то же требование
   живой реакции, что и у Motion-приёмов (не статичная сцена).
⚠️ Fallback на слабых устройствах: оборачивай Canvas в проверку
`prefers-reduced-motion`/малого viewport — на мобильном либо упрощай сцену
(меньше частиц/полигонов), либо не рендери 3D вообще, показывай статичный
Motion-акцент вместо него (описано в vite_react_site).

РЕФЕРЕНСЫ (откуда брать примеры ДО того, как писать сцену — не изобретай
приём с нуля, где уже есть проверенный паттерн):
  - `web_search("threejs examples <ниша/эффект>")` — официальная галерея
    threejs.org/examples и её форки почти всегда всплывают в топе.
  - `web_search("awwwards site of the day three.js")` — витрина премиальных
    сайтов с разбором техник (не копируй код 1-в-1 — референс на ПРИЁМ,
    не на готовую реализацию).
  - `web_search("react three fiber <эффект> codepen")` — готовые небольшие
    примеры кода приёма (частицы/шейдер/камера) на React Three Fiber.
  Ищи ПРИЁМ ("как делают parallax-камеру на r3f"), не готовый сайт для
  копирования целиком — референс информирует решение, не заменяет его.

ПРОВЕРКИ ПЕРЕД СДАЧЕЙ (в дополнение к чек-листу vite_react_site):
1. Ровно ОДИН Canvas на страницу (вариант A — в своей секции, вариант B — фон
   на весь сайт) — не несколько Canvas по секциям (см. СТРУКТУРА).
2. Есть хотя бы одна живая реакция сцены на действие пользователя (курсор/скролл),
   иначе это статичная 3D-картинка — тот же критерий, что и у Motion-приёмов.
3. Fallback/упрощение для `prefers-reduced-motion` и узкого viewport — WebGL на
   слабом мобильном без него сажает страницу в лаг или крашит вкладку.
4. verify_code — синтаксис (WebGL-ошибки времени выполнения verify_code не ловит,
   это ограничение известно — визуально сцену не увидеть без реального браузера).
