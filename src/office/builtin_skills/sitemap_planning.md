СКИЛЛ: только для проектов, которым явно нужно БОЛЬШЕ одной страницы —
каталог услуг с карточками, блог, «О нас»/«Контакты» отдельными разделами и
т.п. Для обычного одностраничного лендинга (большинство проектов) этот
скилл НЕ нужен — не создавай sitemap, если владелец/бриф не просили
многостраничную структуру явно.

КОГДА ПРИМЕНЯТЬ: бриф/задача прямо говорят про несколько страниц/разделов
навигации, каталог с карточками услуг, блог — не для «сделай красивый
лендинг».

ШАГ 1 — СПИСОК СТРАНИЦ: исходя из ниши/аудитории брифа и (если есть)
docs/brand_book.md, предложи 3-6 страниц — не больше: разрастание карты
без причины усложняет и разработку, и навигацию для посетителя. Для каждой:
путь (короткий, латиницей, например `/uslugi`), заголовок, 1 предложение —
что на ней должно быть и зачем она нужна посетителю.

ШАГ 2 — ЗАФИКСИРУЙ: write_file('docs/sitemap.md', ...) построчно:
  /path — Заголовок: назначение страницы одним предложением.
Пример:
  / — Главная: результат+доверие+CTA, как обычный лендинг, но с ссылками на остальные страницы.
  /uslugi — Услуги: карточки услуг с ценами "от", ссылка на заявку.
  /o-nas — О нас: история, команда, почему нам можно доверять.
  /kontakty — Контакты: адрес/телефон/форма/карта.

ШАГ 3 — ОБЯЗАТЕЛЬНОЕ ОДОБРЕНИЕ: покажи список владельцу через ask_user
(«Предлагаю карту сайта из N страниц: [список]. Подтверждаете такую
структуру?»). Правки — скорректируй и перепиши файл, спроси снова. Только
после явного «да» — допиши в конец docs/sitemap.md строку ровно так:
«Статус: одобрено владельцем» (без неё developer не будет считать карту
финальной, см. builtin_skills/vite_react_site.md).

НЕ ДЕЛАЙ: не проектируй sitemap «на будущее», если сейчас нужен лендинг —
добавить страницы можно будет отдельным заходом этого же скилла позже, когда
владелец реально попросит расширение.
