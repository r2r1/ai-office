# CLAUDE.md

Руководство для Claude Code и других агентов по работе с этим репозиторием.
Документ описывает **то, что реально есть в коде сейчас**, и **видение, к которому
система движется** — чтобы любые правки сохраняли курс, а не размывали его.

---

## 1. Видение (зачем это всё)

⚠️ **Главная архитектурная спецификация — `docs/bos-architecture.md`** (Business
Operating System). Правило проекта: **никакой новый код не появляется, если его
место не определено в BOS Architecture** — если код туда не ложится, сначала
осознанно правится спецификация, потом пишется код. Там же — строгий глоссарий
(World Model, Intent, Objective, Capability, Project, Decision...) и порядок
разработки ядра. Слово «агент» — только внутренний технический термин; в UI и
документации — роли, исполнители, навыки, провайдеры.

**AI-Office** — мультиарендный SaaS, в котором у каждого клиента появляется
автономный AI-офис: несколько агентов разных ролей самостоятельно ведут его
бизнес, а сам офис визуализирован как изометрическая (псевдо-3D) игра в браузере.

Клиент не ставит задачи поштучно — он формулирует **цель** (через онбординг
или в чате), а офис сам:
- исследует рынок и формирует стратегию,
- проектирует техническое решение (ТЗ),
- разбивает путь к цели на этапы и задачи (план-граф),
- открывает нужные отделы (tech / marketing / sales) и нанимает специалистов,
- выполняет задачи реальными инструментами (пишет код в `workspace/`, публикует
  лендинги, шлёт сообщения через интеграции, собирает живых лидов),
- задаёт клиенту блокирующие вопросы, когда без него нельзя двигаться,
- сам платит за свои LLM-вызовы из квоты тенанта.

Главные принципы, ради которых система устроена так:

- **Автономность.** Агент не просит «сделать руками» — у него есть инструмент,
  он его и вызывает. Нет ключа → запрашивает через `ask_user` с инструкцией.
- **Реальный результат, а не пересказ.** Код пишется в файлы, сайты публикуются,
  сообщения отправляются. Текст в чате — это не результат.
- **Приоритет указаний клиента.** Ответы пользователя главнее стратегии и ТЗ;
  всё, что им противоречит, не делается.
- **Единая ответственность.** На каждую рабочую роль один агент в момент времени —
  никаких клонов «потому что параллельно».
- **Развязка через события.** Отделы сигналят события компании; CEO интерпретирует
  и перенаправляет, а не каждый агент дёргает каждого напрямую.
- **Развязка через способности.** Агент описывает потребность словами
  (`use_capability("опубликовать лендинг")`) — конкретную интеграцию выбирает
  роутер; новая интеграция подхватывается без правки агентов.

Язык продукта, UI и комментариев в коде — **русский**. Сохраняй стиль.

## 2. Запуск

```bash
pip install -r requirements.txt
python scripts/run.py                           # бэкенд + SPA на http://localhost:8000 (reload с исключениями)
DEMO_MODE=1 python scripts/run.py               # демо без расхода токенов
python main.py                                  # CLI: ресёрчер → стратег (без игры)
```

⚠️ НЕ запускай `uvicorn server:app --reload` напрямую: reload следит за всем деревом,
включая `data/tenants/<tid>/workspace/`, куда агенты пишут код и сайты. Любая запись
файла агентом перезапускала сервер и роняла идущий офис-цикл (реальный баг из прода).
`scripts/run.py` включает reload только для исходников и игнорирует данные тенантов.

Frontend (React/Vite) живёт в `webapp/`, билдится в `static/webapp/` и отдаётся
бэкендом на `/webapp/` (корень `/` редиректит туда же). Для активной фронтовой
разработки — `cd webapp && npm run dev`.

Конфигурация — `.env`:
```
LLM_BASE_URL=https://apinet.cloud/v1
LLM_API_KEY=sk-...
LLM_MODEL=gpt-5.4 | glm-4.5-flash | qwen3-vl-plus | ...
DEMO_MODE=0
LOOP_INTERVAL_SECONDS=10
AGENT_COOLDOWN_SECS=25
AGENT_MAX_THINK_SECS=240
APP_SECRET=...                  # Fernet-ключ шифрования тенант-секретов
APP_BASE_URL=...                # для GitHub OAuth / Telegram webhook в проде
APINET_ACCESS_TOKEN=...         # opt-in: автогенерация per-tenant LLM-ключа
APINET_USER_ID=...
APINET_TENANT_QUOTA=...
ALLOW_CODE_EXECUTION=0          # 1 = разрешить execute_code/run_command (терминал);
                                # без песочницы это исполнение БЕЗ изоляции от ФС
                                # хоста — security-долг, docs/audit-dd-2026-07.md §17
TELEGRAM_API_ID=...              # ключи ПРИЛОЖЕНИЯ (my.telegram.org), не пользователя —
TELEGRAM_API_HASH=...            # без них форма входа в личный Telegram (office/
                                # telegram_login.py) просит их у каждого пользователя
```

### Минимальная проверка перед коммитом
Тестов и линтера нет. Что прогонять руками:
```bash
python -m py_compile $(git ls-files '*.py')   # синтаксис Python
cd webapp && npx tsc --noEmit                  # типы React-приложения
```

Запускаешь сервер — **обязательно убей процесс за собой**. На этой Windows-машине
процесс называется `python3.13`, а не `python` (см. `MEMORY.md`).

## 3. Архитектура

### 3.1 Жизненный цикл клиента

```
лендинг → авторизация (GitHub / dev-вход) → онбординг (3 сценария + интервью)
       → бриф готов → офис-цикл запускается → BOOTSTRAP → циклы CEO
       → результат: лендинг/бот/код в workspace + лиды + платежи
```

### 3.2 Иерархия агентов

Реальная организационная модель (см. `src/office/org.py`, `src/agents/orchestrator.py`):

```
CEO (orchestrator)        — структура компании: открывает/закрывает отделы, ставит цели
  ├── tech (CTO)          — продукт, код, боты, сайты
  │     ├── developer     — код (Python/JS)
  │     ├── integrator    — внешние API, запуск ботов
  │     └── designer      — UI/UX, верстка
  ├── marketing (CMO)     — контент, реклама, бренд
  │     ├── marketer
  │     └── analyst
  └── sales (Head of Sales) — клиенты, переговоры, CRM
        └── salesman

Сервисные роли (вне отделов):
  researcher, strategist, architect, hr
```

CEO **не ставит задачи людям** — он ставит цели **отделам**. Лидер отдела (CTO/CMO/…)
распределяет задачи внутри. На каждую рабочую роль — один агент (`MAX_PER_ROLE=1`).

### 3.3 Поток работы (`src/office/loop.py`)

**Менеджер:** `loop.run()` опрашивает всех тенантов и для каждого с готовым брифом
запускает `_run_office(tid)` в отдельной задаче с установленным `tenant`-контекстом
(через `saas/context.py` ContextVar — наследуется дочерними asyncio-задачами).

**Внутри одного офиса:**

1. **BOOTSTRAP** (один раз на тенанта):
   researcher (deep) → strategist → `strategy.md`
   → architect → `tech_design.md`
   → orchestrator разбивает путь на бизнес-этапы (milestones)
   → orchestrator генерирует план-граф задач (`plan.py`) или берёт детерминированный
     фолбэк (`_fallback_plan` в `loop.py`), чтобы офис **всегда** был plan-driven.
2. **Циклы** (раз в `LOOP_INTERVAL_SECONDS`):
   - проверка паузы (`control.is_paused()`);
   - проверка завершения плана (`_engagement_complete`) — если всё сделано,
     офис публикует сайт, делает финальную верификацию (`critic.check_site`),
     при критических проблемах добавляет fix-задачу, иначе уходит в режим ожидания;
   - самолечение зависших агентов (`_heal_stuck_agents`, watchdog по
     `AGENT_MAX_THINK_SECS`);
   - CEO принимает ОДНО решение (open/close department / delegate / wait);
   - лидеры отделов распределяют задачи плана между подчинёнными;
   - агент выполняет задачу через ядро `llm.run_agent` с подмешанным контекстом.

### 3.4 Контекст, который видит работник

В задачу каждого работника подмешиваются (через `_task_with_context`):
- **бриф клиента** (цель, ниша, ограничения);
- **указания пользователя** (`memory.all_entries()`) — приоритет над всем;
- **ТЗ архитектора** (`architect.load()`);
- **3-слойная память** (`knowledge.retrieve(task, department)`) — топ-N фактов,
  релевантных именно этой задаче (TF-like + словарь намерений);
- **уроки прошлых прогонов** (`lessons.py`) по его роли;
- **дайджест отдела** (что коллеги уже сделали).

Это и есть «moat»: агент не тонет в простыне всего подряд и не забывает контекст
между циклами. Слои памяти: **GLOBAL** (бриф + ответы клиента, высокий приоритет),
**DEPARTMENT** (что отдел узнал), **RETRIEVAL** (подбор по задаче).

### 3.5 Event Layer (`src/office/events.py`)

Отделы не дёргают друг друга напрямую. Видишь проблему/возможность/блокер вне
своей задачи — публикуй событие через `raise_event(kind, summary)`. CEO на
следующем цикле читает накопленные события (`events.pending()`), интерпретирует
и решает, что с ними делать; обработанные помечает `mark_processed`.

### 3.6 Tool Router (`src/office/tool_router.py`)

Агенты не привязаны к именам интеграций. Вместо `use_integration("website", "publish_landing", {...})`
они говорят `use_capability("опубликовать лендинг", params)`. Роутер:
- собирает каталог способностей из метаданных интеграций;
- скорит кандидатов по словам запроса + словарю синонимов (`_INTENT_HINTS`:
  «лендинг»→website, «письмо»→gmail, «таблиц»→google_sheets, …);
- если кандидат явно лидирует — выполняет; иначе возвращает топ-N для выбора.

Поменяли инструмент под капотом — агент не заметил. Новая интеграция подхватится
автоматически.

### 3.6.1 Skills Layer (`src/office/skills.py`)

Второй способ Execution Engine из `docs/3.md`: **роль не держит «как делать» в своём
промпте — «как» живёт в скилле**. Роль (см. `roles.py`) описывает *кто я / что нельзя*;
способ выполнения (структура файлов, приёмы, проверки) — это `Skill.playbook`.
Захотели менять способ строить 3D-сайты — правим скилл, а не каждую роль; новый способ —
новый скилл, роли не трогаем (тот же принцип развязки, что у интеграций).

**Хранение — каждый скилл отдельным файлом**, не Python-литералом в коде:
- `office/skills.py` — только инфраструктура (`Skill`, `register`, `match`, `score`,
  `prompt_block`); при импорте сканирует `office/builtin_skills/*.md` и регистрирует
  их через `skill_store.parse_skill_md` — тот же формат (`---frontmatter---` +
  markdown-тело), которым уже пользуются скиллы, устанавливаемые клиентом.
- `office/builtin_skills/<id>.md` — сами встроенные скиллы (лендинг, 3D-сайт,
  копирайтинг, SEO, боты и т.д.), по одному файлу. Редактируешь один скилл —
  открываешь один файл на 15–100 строк, а не общий `.py` на полтысячи строк.
- `office/skill_store.py` — установленные клиентом скиллы (per-tenant/глобальные
  `.md`-файлы, `npx skills`-совместимый формат) + тот же парсер для встроенных.

Добавить новый встроенный скилл — положить `.md`-файл в `builtin_skills/`, без
правки Python. `Skill.handler` (Python-код) остаётся опцией для скиллов, которым
реально нужна детерминированная логика (а не просто текст плейбука).

**Как воркер выбирает скилл** (тот же приём, что в Tool Router):

```
        задача воркеру («сделай красивый лендинг»)
                        │
            воркер сомневается «как именно»
                        │
                        ▼
        use_skill("3D-лендинг с анимациями")        ← потребность словами
                        │
        skills.match(need, role)  ── скорит по keywords, фильтрует по роли
                        │
          ┌─────────────┴─────────────┐
          ▼                           ▼
   уверенный лидер              неоднозначно / нет
          │                           │
   плейбук скилла →            suggestions() топ-N
   воркер исполняет его        (воркер уточняет или
   СВОИМИ инструментами         делает напрямую)
   (write_file/verify_code)
```

**Каталог скиллов не зашит в промпты ролей** — `prompt_builder` подмешивает
`skills.prompt_block(role)` ДИНАМИЧЕСКИ из реестра, отфильтровав под роль. Поэтому
каталог из 200 скиллов не раздувает промпт (воркер видит только релевантные его роли),
а `roles:` в frontmatter скилла сам определяет, в промпте каких ролей он появится —
ни одной правки текстов ролей. Это масштабируемая замена прежнему хардкоду «вызови
use_skill(...)».

`kind`: `builtin` — работа делается встроенной моделью по плейбуку; `external` —
плейбук говорит делегировать внешнему исполнителю/репозиторию (задел на External
Workers из `docs/3.md`). Флагманский скилл — `framer_motion_3d_site`
(`builtin_skills/framer_motion_3d_site.md`): премиальный 3D-лендинг на React +
framer-motion через esm.sh, без шага сборки; доступен ролям `designer`/`developer`.
Добавить новый скилл — положить `.md`-файл в `builtin_skills/` (см. формат в
`skill_store.py`).

⚠️ **Дизайн-скиллы (`static_landing_site`, `framer_motion_3d_site`) не выбирают
палитру сами** — это решение маркетинга. Стиль хранится строкой «Стиль: …» в
`docs/site_content.md`, которую пишет `marketer` (скилл `landing_conversion`,
общий для `marketer`/`designer`/`developer`); designer/developer читают её или
спрашивают через `ask_colleague("marketer", ...)`. Без этого агент скатывается в
один из «AI-дефолтов» палитры (тёмно-синий+cyan/violet «SaaS-гласморфизм» и т.п.) —
одинаковый для любой ниши сайт был реальным багом прод-прогонов.

| `office/chat.py` | LLM-диалог с агентом (history, краткие ответы) |
| `office/connections.py` | Хранилище учётных данных интеграций (Fernet at-rest) |
| `office/workspace.py` | Рабочая папка тенанта; `write_file/read_file/list_files/run_command/execute_code`; `verify()` компилирует `.py` И проверяет синтаксис `.js`/`.mjs`/инлайн `<script type="module">` (ESM-aware `node --check`) — раньше проверялся только `.py`, для чисто-JS сайтов (3D-скилл) это был ложный «✅ всё ок» без единой реальной проверки (UTF-8 env для Windows) |
| `office/sites.py`, `leads.py` | Опубликованные лендинги и собранные с них лиды |
| `office/costs.py` | Учёт токенов и стоимости (инкрементальный); прайс apinet |
| `office/models.py` | Выбор LLM-модели (глобально / на агента) |
| `office/llm_settings.py` | Per-tenant LLM-креды (свой ключ клиента); `provision_tenant_key` через apinet |
| `office/bot_engine.py`, `bot_runtime.py`, `bot_config.py` | Шаблонный Telegram-бот записи: один движок на платформу, поведение задаётся конфигом тенанта; long-polling запускается из lifespan |
| `office/state.py`, `memory.py`, `brief.py` | Лента событий, ответы клиента, бриф |
| `office/bus.py` | Event bus для SSE-стрима в UI |

### 3.8 Мультиарендность (`src/saas/`)

Всё, что относится к данным офиса, **per-tenant и stateless**: модули `office/*`
читают/пишут `data/tenants/<tid>/<name>.json` через `context.read_json/write_json`.
Никаких глобальных словарей с состоянием тенанта — иначе утечка между клиентами.

- `saas/context.py` — `tenant_id` в ContextVar. Middleware ставит из сессии на
  HTTP-запрос; `loop._run_office` ставит на свою asyncio-задачу.
- `saas/db.py` — sqlite, таблицы `users` / `workspaces`.
- `saas/auth.py` — сессии (PyJWT) + GitHub OAuth + dev-вход.
- `saas/store.py` — пользователи/тенанты; при создании workspace вызывает
  `llm_settings.provision_tenant_key`.
- `saas/crypto.py` — Fernet от `APP_SECRET` для шифрования секретов at-rest
  (LLM-ключ тенанта, креды интеграций).
- `saas/apinet.py` — клиент apinet.cloud account API: баланс, создание per-tenant
  токена (opt-in через `APINET_ACCESS_TOKEN/USER_ID`).

`core/llm.py` берёт креды текущего тенанта (через `llm_settings.credentials()`),
fallback — общий `LLM_*` из `.env`. Лендинги тенанта публичны по
`/site/{tenant}/{slug}`, лиды — `POST /api/lead/{tenant}/{slug}`.

### 3.9 Слой интеграций (`src/integrations/`)

В отличие от `office/connections.py` (хранилище кредов), это **реальные вызовы**.

- `base.py` — `Integration` / `Action` / `CredField`: декларативное описание сервиса
  (нужные креды + `how_to` + действия с JSON-схемой и async-`handler(creds, params)`).
- `registry.py` — каталог (`_ALL`), статус подключения, `catalog_payload` для UI.
- `telegram.py` — Bot API (`get_me` / `send_message` / `send_photo`).
- `github.py` — `create_repo` / `push` workspace тенанта через Contents API;
  токен берётся из GitHub OAuth (scope `repo`) или вводится вручную (PAT).
- `website.py` — **без кредов**: публикует лендинг (`publish_landing`), бэкенд сам
  его хостит (`GET /site/{slug}`), форма шлёт лиды (`POST /api/lead/{slug}`).
  Интеграции с пустым `cred_fields` считаются всегда подключёнными.
- `gmail.py`, `google_calendar.py`, `google_sheets.py`, `google_oauth.py` —
  Google-стек через OAuth.

Агенты ходят сюда через `use_capability` (роутер) или `use_integration(name, action, params)`.
Креды подтягиваются автоматически; нет кредов → агенту возвращается инструкция, он
запрашивает через `ask_user` (учётка автосохраняется в `connections`). Реальные
действия во внешних сервисах CEO поручает отделу tech (роль integrator).

**Чтобы добавить интеграцию:** создай модуль по образцу `telegram.py` (объект
`INTEGRATION`) и зарегистрируй в `registry._ALL`. Фронт, `list_integrations` и
`use_capability` подхватят её автоматически. Проверка из UI — `POST /api/integrations/{name}/test`.

### 3.10 Frontend (`webapp/`)

React + Vite + TypeScript + motion/react. Старый ванильный canvas-фронт удалён;
изометрический офис теперь живёт в `app/components/OfficeView.tsx`.

Структура:

- `data/roles.ts` — имена/иконки/цвета ролей. **При добавлении новой роли обнови

- `app/landing/LandingView.tsx` — публичный лендинг продукта.

- `app/onboarding/OnboardingFlow.tsx` — 3 сценария (business/launch/idea), CEO-интервью

- `app/components/OfficeView.tsx` — изометрические комнаты и агенты.

## 4. Инварианты (НЕ ломать)

- **Автономность.** Агент не просит ручной работы. Нужен сервис → `get_connection`
  → если нет, `ask_user` с инструкцией. Правила в `office/policies/autonomy.md`.
- **Артефакты — только через инструменты.** Код / HTML / содержимое файлов
  создаются **только** вызовом `write_file`. Текст ответа агента — короткий
  (2–4 предложения): что сделал и где смотреть. Никаких ```-блоков с кодом
  в ответе: такой текст не становится файлом. Правило живёт в
  `office/policies/team.md` — не выпиливай.
- **Весь промпт собирает Prompt Builder.** И системный промпт (`build`), и контекст
  задачи (`task_context`) — только `office/prompt_builder.py`; собранный промпт
  целиком логируется в `prompts.jsonl` тенанта. Новый слой контекста → новый слот
  билдера, а не строчка в случайном месте. Сериализатор каждой сущности мира в
  промпт — ровно один (бриф → `brief_block`).
- **Роль — это «кто/что нельзя», не «как».** «Как делать» (стек, приёмы, структура)
  держим в скиллах (`office/builtin_skills/*.md`), а не в текстах ролей
  (`office/builtin_roles/*.md`).
  Меняешь способ работы — правь/добавляй `.md`-файл скилла; роль трогаешь только если
  меняются её миссия, границы или метрики. Воркер достаёт способ через `use_skill`.
- **Цель прогона офиса ≠ то, что продаёт бизнес клиента.** `goal` из брифа — ответ
  клиента на «какой результат вы хотите ОТ ОФИСА» (`onboarding.py`), а `niche`/
  `audience` — что бизнес реально продаёт конечным покупателям. Любой промпт/проверка,
  которая видит сырой `goal` без `niche`, рискует спутать их (реальный кейс: клиент с
  нишей «натяжные потолки» и целью «упаковка бизнеса» получил сайт, продающий
  «упаковку бизнеса» владельцам квартир вместо потолков — баг тянулся через
  `_task_with_context`, `critic.review_site_llm`, `knowledge.py`, `agent_factory.
  _brief_context`, `chat.py` И `orchestrator.interpret_directive` одновременно).
  Добавляешь новое место, где `goal` идёт в промпт — подмешивай `niche`/`audience`
  рядом с явной подписью «это НЕ то, что продаёт компания».
- **Задача закрывается только приёмкой.** Сдача ≠ приёмка: `_job` гоняет результат
  через `acceptance.check` (build/functional/базовый), провал возвращает задачу в
  очередь с фидбеком (`last_feedback` виден исполнителю при переназначении), третий
  провал блокирует её с blocker-событием. Никогда не возвращай «done = непустая строка».
- **Plan-driven всегда.** Если LLM-генерация плана падает — `_fallback_plan` в
  `loop.py` даёт детерминированный план. Офис без плана уходит в LLM-хаос.
- **Общие доступы.** Любой ключ доступен любому агенту через `get_connection`.
  CEO не выбирает агента «потому что у него ключ».
- **Единая ответственность.** `MAX_PER_ROLE=1`. Исполнитель занят → ждём, не клонируем.
- **Приоритет указаний клиента.** `memory.all_entries()` подмешивается в контекст
  CEO и работников и главнее стратегии/ТЗ. Прямая просьба клиента («не BotsBox»)
  — запрет, а не рекомендация.
- **Реальный код, не описание.** Разработчик пишет в `workspace/` через `write_file`,
  верифицирует (`verify_code` — компиляция), и пушит в GitHub **только после
  одобрения** клиента (через `ask_user`). Платные конструкторы (Tilda/BotsBox) без
  одобрения не подключаются.
- **Дедупликация.** Одинаковые вопросы делят один future (`questions.py`);
  одинаковые подключения не дублируются (`connections.py`).
- **Кулдаун, не дедлок.** `AGENT_COOLDOWN_SECS` — антидребезг живости.
- **Multi-tenancy.** Никаких глобалей с состоянием тенанта в `office/*`. Всё —
  через `context.read_json/write_json`.
- **Учёт расхода — инкрементальный.** `costs.record` зовётся **внутри** цикла
  `llm.run_agent` после каждого ответа API. Иначе зависшие/убитые прогоны
  тратят деньги, а индикатор показывает $0.
- **Прайс apinet — единственный источник правды.** Цены моделей сверять с
  `GET https://apinet.cloud/api/pricing`. Хардкод-угадывания приводили к 21x
  занижению (см. `MEMORY.md`). Модель без цены в `costs.PRICES` НЕ должна писать
  $0 — `price_for()` отдаёт консервативную оценку (медиану известных цен) и
  предупреждает в лог; добавляя модель, сразу впиши реальную цену в `PRICES`.
- **Убивать процессы за собой.** Каждый запущенный сервер — реальные деньги, пока
  жив. На Windows процесс — `python3.13`. См. `MEMORY.md`.

## 5. Стиль

- **Python.** Docstring на русском в шапке файла, типы в сигнатурах, маленькие
  функции. Без сторонних зависимостей сверх `requirements.txt`.
- **TypeScript / React.** Функциональные компоненты, motion/react для анимаций,
  без классов, без сторонних state-менеджеров (только провайдер с reducer).
- **Комментарии — только о НЕочевидном.** Объяснять *почему*, а не *что*.
  Что делает функция — видно из её имени и сигнатуры; почему оно сделано именно
  так — нет.
- **Не добавляй модель/идентификатор Claude** в коммиты, комментарии, артефакты.
