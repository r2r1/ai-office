# Product Vision — зачем AI-Office и как инструменты создают ценность

*Продуктовый документ (не архитектурный — архитектура в `docs/bos-architecture.md`,
дорожная карта реализации в `docs/дорожная_карта.md`). Отвечает на вопрос «что мы
продаём и почему это работает», а не «как это устроено внутри». Обновлено 2026-07-04.*

---

## 0. Что продаёт AI-Office (и что НЕ продаёт)

**Продаёт:** не «агентов», не «конструктор сайтов», не «автономный офис» как
метафору. Продаёт **операционную систему бизнеса**, которая:

1. складывает у себя модель бизнеса клиента (не картинку — измеримое состояние:
   лиды, конверсии, конкуренты, разрывы);
2. сама создаёт недостающую инфраструктуру бизнеса, если её нет (нет сайта →
   строит сайт; нет воронки → строит воронку; нет CRM → сама ей становится);
3. непрерывно сравнивает, где бизнес сейчас и где хочет быть, и **действует**:
   предлагает и (с подтверждением владельца) выполняет конкретные шаги.

**Не продаёт:** визуальную метафору изометрического офиса (это UI, не ценность —
см. «тест архитектуры» в `bos-architecture.md` §0), генерацию кода как таковую
(это делают Bolt/v0/Cursor лучше), общий чат с LLM (это делает сам ChatGPT).

**Формула ценности:**
> Каждый отдельный сервис (CRM, таргетолог, копирайтер, аналитик) не видит
> бизнес целиком. AI-Office видит — потому что через него проходят данные.
> Из этого целостного взгляда рождаются решения, которые ни один
> изолированный инструмент предложить не может: «у вас лидов вдвое меньше, чем
> у трёх конкурентов в нише — вот их оффер, вот что предлагаю поменять»,
> «10 лидов не получили ответ 3+ дня — вот черновики сообщений, отправить?»,
> «в отчётности расхождение между кассой и 1С за март — вот где».

## 1. Инструменты — не витрина, а рабочие руки

Кибернетический цикл BOS (`bos-architecture.md` §3: Gap → Plan → Decision →
Execution → Acceptance → Measurement) настолько же хорош, насколько хороши
**инструменты**, которыми Execution реально трогает мир. Красивый цикл с
посредственным инструментом на выходе — это генератор разочарования: клиент
видит не архитектуру, он видит результат конкретного действия (сайт, текст
письма, рекомендацию). Если результат хуже, чем клиент получил бы вручную в
специализированном сервисе — весь цикл обесценивается за один плохой артефакт.

**Принцип качества инструмента:**
> Инструмент внутри AI-Office обязан быть не «сопоставим», а **лучше**, чем тот
> же класс задачи, решённый вручную в отдельном сервисе. Разница в его пользу
> обеспечивается ровно одним активом — **полнотой контекста бизнеса**
> (World Model), которого нет у изолированного SaaS. Если инструмент не
> использует этот контекст (генерирует сайт без знания ниши и конкурентов,
> пишет лиду без знания истории переписки) — он не оправдывает своё место
> внутри системы, и с тем же успехом клиент мог открыть внешний сервис сам.

Отсюда правило приоритизации: **инструмент, который не читает World Model
по-настоящему (не декоративно), не готов к продакшену**, вне зависимости от
того, сколько строк кода в нём уже написано.

## 2. Критерий выбора: build / open-source / внешний API

Три способа реализовать любой инструмент. Выбор — не идеологический
(«свой код всегда лучше»), а по конкретным осям для данной задачи.

### Дерево решения

```
Инструмент нужен → задай по порядку:

1. Это МОЙ дифференциатор (то, ради чего клиент выбрал именно нас)?
   ДА → строить самому (builtin), даже если дольше.
   НЕТ → следующий вопрос.

2. Требует ли инструмент глубокого чтения/записи World Model
   (не может работать «сбоку», должен быть встроен в контекст задачи)?
   ДА → builtin-обвязка вокруг чужого движка (гибрид), не чистый API-вызов.
   НЕТ → следующий вопрос.

3. Существует ли зрелое open-source решение с приемлемой лицензией
   и без вендор-лока, которое можно самостоятельно хостить и модифицировать?
   ДА → open-source, обёрнутое в Integration (по образцу integrations/*.py).
   НЕТ → следующий вопрос.

4. Есть ли внешний API, качество которого объективно выше того, что
   можно построить самим за разумное время (реклама, email-доставляемость,
   OCR, финансовые данные банков)?
   ДА → внешний сервис через Integration + Tool Router (use_capability),
        креды пользователя, `how_to` для ask_user.
   НЕТ → строить самому по остаточному принципу (временный костыль,
        помечен TODO на замену).
```

### Как это расставляет реальные инструменты

| Инструмент | Дифференциатор? | Читает World Model? | Решение | Почему |
|---|---|---|---|---|
| Сайтогенерация + скиллы дизайна | Да (флагман) | Да (ниша/стиль/аудитория) | **Builtin** | Уже реализовано (`builtin_skills/*`), это лицо продукта — доверять внешнему рендереру нельзя |
| Критик сайта (проверка перед сдачей) | Да | Да (спецификация, критерии приёмки) | **Builtin** | Acceptance — ядро доверия к системе, не аутсорсится |
| Лид-менеджмент / мини-CRM | Да (создаёт воронку с нуля) | Да (весь смысл — история лида в контексте бизнеса) | **Builtin** (см. §3) | Готовые CRM (AmoCRM) хороши, когда УЖЕ есть — но клиент без CRM должен получить её от нас, иначе цикл Bootstrapping не замыкается |
| Follow-up / дожим лидов (тексты, отправка) | Да | Да (история переписки, тон бренда) | **Builtin** генерация + **внешний API** доставки (email/Telegram/WhatsApp) | Текст — наш контекст, канал доставки — чужая инфраструктура доставляемости |
| Веб-исследование конкурентов | Частично | Да (сравнение с брифом клиента) | **Гибрид**: OSS-парсер (Playwright/BeautifulSoup) + builtin-анализ | Парсинг HTML — решённая задача, ценность в сопоставлении с брифом — наша |
| Контент-завод (посты, публикация) | Частично | Да (голос бренда, ниша) | **Builtin генерация** + **внешний API публикации** (VK/Telegram Bot API) | Генерация текста под бренд — наш контекст; публикация в конкретную соцсеть — готовый API, изобретать не нужно |
| Таргетированная реклама | Нет | Косвенно (данные для брифа кампании) | **Внешний API** (Яндекс.Директ/VK Ads) | Рекламные платформы — зрелые продукты с десятилетиями оптимизации аукциона; строить свою рекламную сеть бессмысленно |
| Email-рассылки (доставляемость) | Нет | Косвенно | **Внешний API/OSS** (Unisender API либо self-host Listmonk) | Доставляемость email — решённая инженерная проблема с репутацией доменов, конкурировать не нужно |
| Аналитика/дашборды | Частично | Да (метрики — часть World Model) | **Builtin** поверх `metrics.py`, витрина может использовать **OSS** (Metabase) для сложных отчётов | Базовые метрики — наши (Measurement Layer), сложная BI-аналитика может выехать на готовом движке |
| Финансовый аудит (1С/банк) | Да (уникальная связка с World Model) | Да | **Гибрид**: OSS-коннектор к 1С/банк-API (там где есть) + builtin-анализ несостыковок | Парсинг форматов 1С решён в OSS-библиотеках, поиск смысловых нестыковок — наша аналитика |
| CRM-интеграция (когда уже есть у клиента) | Нет (интеграция, не создание) | Да (обогащает World Model) | **Внешний API** (AmoCRM/Битрикс24 API) | Не переизобретать то, что у клиента уже работает — просто подключиться и читать |

## 3. Как это ложится на BOS-архитектуру (без новых сущностей)

Ничего из описанного не требует новых понятий сверх `bos-architecture.md` §1.
Соответствие:

- **Capability Layer (§5)** — правильное место для решения build/OSS/API.
  Каждый инструмент — это `Capability` с конкретной `Provider`-реализацией;
  замена OSS-парсера на builtin (или наоборот) не трогает роли и скиллы,
  ровно так же, как смена LLM-провайдера.
- **Skill vs Provider.** «Как делать» (плейбук: как оценивать лида, как
  писать follow-up, какие критерии у хорошего сайта) — это `Skill`.
  Конкретный механизм выполнения (какая библиотека парсит HTML, через какой
  API уходит email) — это `Provider`. Путать их означает зашивать
  инфраструктурный выбор в промпт роли — инвариант §14 запрещает это.
- **Мини-CRM как воплощение Bootstrapping (§3, два режима зрелости).**
  Если у клиента нет воронки — задача `developer`/`integrator` по плану
  строит минимальную (лиды + статусы + история контакта) внутри workspace
  тенанта. Это не отдельная фича, а конкретный случай принципа BOS №1
  («любая работа увеличивает способность компании понимать себя») —
  воронка создаётся, чтобы дать системе данные для Gap Analysis, которых
  раньше не было.
- **Follow-up и «недожатые лиды» — Event Layer, не отдельный модуль.**
  Обнаружение «лид не получил ответ 3 дня» — доменное событие
  (`events.raise_event`), которое CEO интерпретирует на следующем цикле,
  ровно как любой другой blocker/opportunity. Не нужен параллельный
  механизм — нужно **начать реально писать эти события**, которых сегодня
  для лидов нет.
- **Финансовый аудит — Gap Analysis (§3/Phase 4 дорожной карты) над новым
  источником Metrics**, не отдельная подсистема. Несостыковка — это gap
  между `desired` (баланс должен сходиться) и `current` (не сходится),
  вычисленный так же, как gap по лидам.

**Вывод:** видению из этого диалога не нужна новая архитектурная спецификация.
Нужно то, что дорожная карта уже называет Phase 2 (Capability + Artifacts) и
Phase 3 (Measurement) — но с явным включением в scope **инструментов**, а не
только внутренних реестров. Дорожную карту стоит дополнить, не переписывать.

## 4. Приоритет и зависимости инструментов

Без оценок трудозатрат — только порядок и то, что от чего зависит.

```
УЖЕ ЕСТЬ (довести до состояния "лучше, чем руками"):
  Сайтогенерация + дизайн-скиллы
  Критик/Acceptance сайта
  Веб-исследование (сейчас неглубокое)
        │
        ▼
БЛОКИРУЕТ ВСЁ ОСТАЛЬНОЕ:
  Мини-CRM / лид-менеджмент (лид перестаёт быть строкой в JSON)
        │
        ├──▶ Follow-up / дожим лидов (нужны статусы и история из мини-CRM)
        │        │
        │        └──▶ Каналы доставки (Telegram/email API) — независимая
        │             интеграция, можно тянуть параллельно
        │
        ├──▶ Аналитика "вы vs конкуренты" (нужны собственные метрики
        │        │     + углублённое исследование конкурентов)
        │        │
        │        └──▶ Углублённое исследование конкурентов (парсинг,
        │             не только поисковая выдача) — можно тянуть параллельно
        │             с мини-CRM, зависимости нет
        │
        └──▶ Gap Analysis по лидам/конверсии (нужны метрики из мини-CRM)
                 │
                 └──▶ Авто-инициативы ("предлагаю запустить таргет") —
                      зависит от Gap Analysis + доступной Capability рекламы

ПАРАЛЛЕЛЬНО, БЕЗ ЖЁСТКИХ ЗАВИСИМОСТЕЙ ОТ ЦЕПОЧКИ ВЫШЕ:
  Контент-завод (генерация + публикация в соцсети)
  Таргетированная реклама (интеграция Яндекс.Директ/VK Ads)
  CRM-интеграция для тех, у кого CRM уже есть (AmoCRM/Битрикс24)
  Финансовый аудит (1С/банк-коннекторы) — отдельная вертикаль,
      имеет смысл только после того, как Gap Analysis доказал себя на лидах
```

**Логика порядка:** мини-CRM — корневая зависимость, потому что без неё
«лид» не является сущностью с состоянием, и весь дальнейший смысл
(«недожатые», «конверсия», «follow-up») не на чем стоять. Всё, что не
требует состояния лида (контент, реклама, финансы, готовые CRM) — можно
разрабатывать в любом порядке параллельно, ограничение только по
пропускной способности команды.

**Что сознательно НЕ в этом списке сейчас:** Decision Engine как diff и
Sandbox-механизм (`bos-architecture.md` §9, Phase 5 дорожной карты) — это
инфраструктура принятия решений, она нужна, когда инструментов и авто-
инициатив станет много и конфликты между ними станут реальным риском. Пока
инструментов два с половиной — риска конфликтов нет, ускорять эту фазу
преждевременно.

## 5. Как не потерять доверие, наращивая автономность инструментов

Чем больше инструментов реально действуют (пишут лидам, тратят рекламный
бюджет, трогают финансовые данные), тем выше цена ошибки одного из них.
Правило, которое обязано масштабироваться вместе с числом инструментов:

- **Necessary но не sufficient: план проходит Acceptance.** Достаточным
  условием для автономного действия является явная категория из
  `office/policies/autonomy.md` — новый инструмент, который тратит деньги,
  публикует необратимо или касается чужих персональных данных (переписки,
  финансы), по умолчанию требует подтверждения владельца перед первым
  использованием и может перейти в полностью автономный режим только после
  явного разрешения по этой конкретной способности (не «в целом доверяю
  системе», а «доверяю этому классу действий»).
- Это уже частично описано Constitution (§2 `bos-architecture.md`) — новые
  инструменты должны явно классифицироваться в её терминах при добавлении,
  а не полагаться на общую формулировку «система осторожна».
