# Первое расследование компании (Company Investigation) — план

**Дата:** 2026-07-16. **Статус:** зафиксирован в обсуждении с владельцем, к реализации.

Это НЕ документ про регистрацию/онбординг. Это отдельная функция продукта —
механика, которой офис ЛЮБОЙ раз узнаёт компанию: при первом запуске, при открытии
нового филиала, при старте нового направления, при возврате клиента через полгода.
«Онбординг» — лишь первый (но не единственный) момент, когда она запускается.

---

## 0. Главная мысль — переворот рамки

**Старая рамка (неверная):** цель этого шага — собрать `Brief`, чтобы запустить офис.

**Новая рамка:** цель расследования — построить и с этого момента непрерывно
достраивать **World Model** компании, потратив как можно меньше усилий пользователя.
Всё, что можно узнать самостоятельно, офис добывает сам. Пользователь отвечает
только на то, что физически невозможно выяснить автоматически.

`Brief` — это НЕ результат расследования и не главный вход системы. Это один из
источников World Model, наравне с:

- сканом сайта / соцсетей / карт-сервисов,
- подключённой CRM/почтой/календарём,
- завершёнными проектами и их «следом» (`left_behind`),
- перепиской в чатах (владелец ↔ агенты, агент ↔ агент),
- метриками и результатами работы самого офиса (лиды, продажи, публикации).

Через год AI-Office не будет «жить брифом» — он будет жить World Model. Эту мысль
нужно закрепить в архитектуре сейчас, пока продукт формируется, а не переписывать
её задним числом, когда `brief.py` уже вплетён в промпты десятков модулей.

---

## 1. Принципы

1. **Источник знаний — не только самоотчёт пользователя.** Офис активно ищет факты
   (веб-поиск), а не ждёт, что человек напишет абзац.
2. **ИИ на пути, а не после него.** Расследование — один живой агентский диалог
   (tool-loop, тот же паттерн, что уже используют ресёрчер/CEO), не «сначала форма,
   потом бот начнёт работать».
3. **Каскад по убыванию усилия пользователя:**
   - ноль ввода (тап по чипу ниши, гео по IP) — самый частый случай, полноценно поддержан;
   - есть ниша, нет названия компании — рыночное исследование ниши+региона;
   - компания есть, но не гуглится (только открылась) — законный, первоклассный исход;
   - есть название/URL — полноценный кросс-источниковый поиск.
4. **Усилие тратит офис, а не пользователь.** Каждый недостающий факт — сначала
   попытка добыть самим, и только если нечем — самый дешёвый вопрос (тап/да-нет/
   одно слово), никогда не абзац.
5. **Поиск — инструмент агента, не обязательный шаг после каждого ответа.** LLM сам
   решает, когда `web_search` добавит ценности; один точный запрос за раз.
6. **World Model никогда не перестаёт строиться.** Первое расследование не
   заканчивается стартом офиса. Каждый найденный факт, подключённая интеграция,
   завершённый проект, новый лид или сообщение владельца увеличивают понимание
   компании — это и есть главная идея AI-Office, не разовая процедура регистрации.
7. **Задержка не должна ощущаться как тишина.** Пока агент решил искать — статус
   «ищу…» (приём ScanBox), не молчание на 5-10 секунд.

## 2. Видимый результат — Company Understanding, не «бриф готов»

Индикатор `office/understanding.py` уже существует и реально считается (score 0-100
+ разбивка по доменам `business/marketing/sales/finance/team`, живой UI в `App.tsx`).
Первое расследование делает его ВИДИМЫМ И ГЛАВНЫМ результатом с первой секунды —
вместо «Бриф готов! Запускаю офис под задачу: …» пользователь видит:

```
Company Understanding
██░░░░░░░░ 24%

✓ рынок
✓ конкуренты
✓ регион
✓ продукты
✓ сайт
○ продажи
○ финансы
○ процессы
○ команда
○ CRM
○ аналитика
```

Психологический эффект прямой: «офис уже знает обо мне 24%» рождает желание
увеличить процент — не «форма отправлена, жди» (тупик), а прогресс-бар, который
растёт и после регистрации. Технически: расширить существующий набор доменов
(`business/marketing/sales/finance/team`) до более гранулярного чек-листа пунктов
(как в макете выше) — не заменять механизм, а сделать его детальнее и показать
раньше, чем сейчас (сейчас он скрыт в попапе статуса, а не на входном экране).

## 3. Цикл (расследование не заканчивается стартом офиса)

```
Первое расследование
        ↓
   World Model v1
        ↓
   Работа офиса
        ↓
   Новые данные (лиды, публикации, интеграции, переписка, завершённые проекты)
        ↓
   World Model v2
        ↓
   Более точные решения
        ↓
   Новые данные
        ↓
   World Model v3   ← и так далее, бесконечно
```

Это полноценный цикл обучения компании, а не «регистрация → разовый снимок».
Технически цикл уже частично существует (`office/world.py` — снапшоты, `diff()`,
журнал; `office/knowledge.py` — 3-слойная память) — расследование делает вход в
этот цикл явным и видимым пользователю, а не только внутренним механизмом.

## 4. Поток самого расследования (сценарий)

**Граница уже проведена (решение зафиксировано):** полноценный живой агентский
диалог с `web_search` как инструментом начинается ТОЛЬКО ПОСЛЕ регистрации —
у анонимного посетителя лендинга нет бюджета/сессии для агентского tool-loop.
До регистрации ScanBox остаётся лёгкой витриной (детали — при реализации Фазы 5,
см. §7); главное расследование начинается сразу после того, как тенант создан,
даже если он пуст (0 фактов о компании).

```
РЕГИСТРАЦИЯ (тенант создан, World Model пока пуста)
              │
              ▼
     ЖИВОЙ АГЕНТСКИЙ ДИАЛОГ (своя UI-сущность на старте — см. §7 "где живёт диалог";
     позже становится видимым как переписка с CEO в общих чатах — та же личность,
     тот же History, не два разных агента)
              │
    агент сам решает: есть смысл искать? ── нет (мало сигналов) → короткий
              │                              вопрос (тап/да-нет), НЕ абзац
              │ да
              ▼
     web_search(ниша + регион [+ имя, если есть]) — суббюджет ~20 сек на попытку,
     несколько формулировок запроса до сдачи (с именем/без, с регионом/без)
              │
   ┌──────────┼──────────────────────┬───────────────────────────┐
   ▼          ▼                      ▼                           ▼
 нашёл ОДНУ  нашёл несколько      нашёл РЫНОК,               не нашёл вообще, хотя
 компанию —   похожих — "это      но не эту компанию         пробовал разные
 озвучивает   вы?" (тап)          конкретно — "идея на       формулировки — честно:
 находки                          старте?" (тап)              "не нашёл, буду
   │               │                      │                    спрашивать сам"
   │               │                      │                           │
   └───────────────┴──────────────────────┴───────────────────────────┘
                              │
                              ▼
              World Model v1 (Company Understanding растёт на глазах,
              business_stage с явной пометкой confirmed/inferred/unconfirmed)
                              │
                              ▼
                      Офис стартует (BOOTSTRAP) — не конец цикла, а его продолжение
```

**Повторный вход (не первый раз, новая область/филиал компании через месяцы):**
не отдельный `Project`, а та же самая World Model — новая ОБЛАСТЬ внутри неё
(например, новый регион присутствия/направление), а не параллельный слепок и не
дублирующая сущность. Где именно в UI живёт кнопка запуска — решается в Фазе 5
(см. §7), логика повторного входа архитектурно фиксируется здесь.

## 5. Что меняется в существующих модулях

| Модуль | Что меняется |
|---|---|
| `src/office/company_scan.py` | Расширить: сегодня работает только от готового URL. Добавить путь «ищи компанию по нише+региону+(опционально)имени» через `core/search.py`. `_stage_heuristic` возвращает пометку уверенности (confirmed/inferred/unconfirmed) всегда, никогда не молчаливое отсутствие. |
| `src/office/understanding.py` | Гранулярный чек-лист (рынок/конкуренты/регион/продукты/сайт/продажи/финансы/процессы/команда/CRM/аналитика) — ПОД-УРОВЕНЬ внутри уже существующих 5 доменов (`business/marketing/sales/finance/team`), не замена структуры. | `src/agents/onboarding.py` | `make_questions`/`build_brief` — единая агентская сессия с `web_search` как инструментом, не два изолированных вызова. Мёртвые `MODES`/`_INTERVIEW` — решить: удалить или превратить в список «измерений», которые агент закрывает по ходу диалога. |
| `webapp/src/app/landing/LandingView.tsx` (ScanBox) | Судьба до-регистрационной формы (чипы ниш вместо текста, или оставить как лёгкую витрину) — решается в Фазе 5, не блокирует более ранние фазы. |
| `webapp/src/app/onboarding/OnboardingFlow.tsx` | Заменяется живым диалогом сразу после регистрации — своя UI-сущность на старте (см. §7), позже видна как переписка с CEO в общих чатах. |
| `webapp/src/app/App.tsx` | Company Understanding — не попап статуса, а видимый прогресс-бар с первой секунды расследования, растущий и после старта офиса. |
| `server.py` | Живой SSE/WS-эндпоинт диалога расследования — новый транспорт (не серия изолированных `POST`, см. §7). `/api/onboarding/scan` (до регистрации) не трогаем до Фазы 5. |

## 6. Фазы реализации (предложение, не решено окончательно)

1. **Фаза 1 — источник данных.** Расширить `company_scan.py` под поиск без URL
   (ниша+регион+имя через `core/search.py`).
2. **Фаза 2 — явная уверенность.** `business_stage` всегда с полем `confidence`,
   прокидывается везде, где сейчас читается голый `key`.
3. **Фаза 3 — видимый Company Understanding.** Гранулярный чек-лист доменов,
   прогресс-бар на входном экране, а не только в попапе статуса.
4. **Фаза 4 — агентский диалог.** Единая LLM-сессия вместо связки изолированных
   вызовов; агент сам решает, когда искать и когда спрашивать.
5. **Фаза 5 — UI входной точки.** Чипы ниш вместо обязательного текстового поля;
   ScanBox и OnboardingFlow — визуально один поток.
6. **Фаза 6 — уборка мёртвого кода.** Решить судьбу `MODES`/`_INTERVIEW`/
   `make_questions` в текущем виде.

## 7. Принятые решения (закрыты в обсуждении 2026-07-16)

| Вопрос | Решение |
|---|---|
| Повторное расследование (новый филиал/направление) vs существующая World Model | Отдельная ОБЛАСТЬ внутри той же компании, не отдельный `Project` и не параллельный снапшот |
| Протокол диалога расследования | Полноценный живой чат (SSE/WS), не серия изолированных `POST` |
| Где хранится состояние ДО регистрации (анонимный посетитель) | Живой агентский диалог — только ПОСЛЕ регистрации. До неё — прежний лёгкий ScanBox (детали витрины — Фаза 5) |
| Судьба `onboarding.MODES`/`_INTERVIEW`/`make_questions` | Решаем при Фазе 6, не блокирует более ранние фазы |
| Бюджет на `web_search` в сессии расследования | Лимит по ВРЕМЕНИ на попытку (~20 сек), не по жёсткому числу вызовов — агент сам решает, тратить один точный запрос или несколько мелких в рамках этого времени |
| Поиск систематически не даёт результата (узкая/локальная ниша) | Несколько формулировок запроса (с именем/без, с регионом/без) до сдачи, затем честное "не нашёл" — не одна попытка и не бесконечный перебор |
| Гранулярный чек-лист Company Understanding vs текущие 5 доменов | Чек-лист — ПОД-УРОВЕНЬ внутри существующих `business/marketing/sales/finance/team`, не замена структуры |
| Где живёт сам диалог расследования (после регистрации) | Своя UI-сущность на старте; со временем сливается с обычной перепиской с CEO в чатах — тот же History, не второй параллельный агент |

### Осознанно отложено до конкретной фазы (не блокирует более ранние)

- **Фаза 5** — судьба пре-регистрационного ScanBox (остаётся как есть / чипы ниш без
  живого поиска) и точка входа в UI для повторного расследования (Настройки vs
  «Работа/Проекты»).
- **Фаза 6** — судьба мёртвого кода `MODES`/`_INTERVIEW`/`make_questions`.
