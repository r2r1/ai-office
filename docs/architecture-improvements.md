### #12 — Digest/Understanding-попапы блокируют клики по ВСЕЙ странице после закрытия
**Баг:** попап «Пока тебя не было» (Morning Digest) — после `location.reload()` появляется поверх контента; клик по «×» скрывает видимый контент попапа, но НАВИГАЦИЯ (NavRail, любые кнопки) остаётся полностью нерабочей — клики физически не доходят до React-обработчиков нигде на странице. Живой репро в этой сессии: подтверждён `elementFromPoint`/ручным `dispatchEvent` — клик доходит до DOM-узла, но не до `onClick`; воспроизводится стабильно после `reload()`, лечится только повторной SPA-навигацией из другого источника (deep-link), не самим закрытием попапа. Похоже на тот же класс проблемы, что уже упоминался в `docs/handoff.md` («обе всплывашки — абсолютно спозиционированные поверх ВСЕГО контента... оставались»), но с более тяжёлым следствием — не просто визуальное наложение, а полная потеря интерактивности приложения до ручного `location.reload()` без reload-триггера или смены вкладки.
**Эффект от фикса:** сейчас это блокирующий баг всей навигации, не только эстетика — пользователь, дождавшийся дайджеста, может потерять способность кликать куда-либо в приложении.
**Файлы:** вероятно `App.tsx` (компонент попапа Digest, оверлей-контейнер — див с `position: fixed`/`absolute` inset:0, который остаётся в DOM или сохраняет `pointer-events` после закрытия).
**Статус:** done (2026-07-14) — `App.tsx`: `pointerEvents` на digest/understanding-попапах теперь явно завязан на `digestOpen`/`understandingOpen`, а не на факт присутствия узла в DOM. Корневая причина (почему AnimatePresence иногда не завершает exit) не изолирована на 100% (вероятный кандидат — `setDigestOpen(false)` в эффекте `[view]` прилетает в том же тике, что смена вкладки, см. комментарий в коде), но фикс не зависит от причины: даже если «призрачный» узел останется в DOM невидимым, он больше не сможет перехватывать клики. Живая проверка — точный репро (открыть дайджест → закрыть × → кликнуть NavRail) на реальном тенанте: навигация в «Ресурсы» сработала, `/api/ui-prefs/resources` вызван корректно.

### #14 — Figma-write и Sitemap (следующий шаг после #13)
**Запрос:** реализовать Figma-write (designer создаёт мокапы в Figma) и формальную сущность Sitemap для многостраничных сайтов.
**Важное открытие — Figma-write физически невозможен через нашу интеграцию:** публичный REST API Figma (`api.figma.com/v1/*`) не имеет и никогда не имел эндпоинтов создания дизайн-контента (фрейм/шейп/текст) — только чтение + комментарии/webhooks/variables (Enterprise). Инструменты `mcp__figma-bridge__create_frame` и т.п., доступные в этой сессии — это ДРУГОЙ механизм (плагин внутри открытой Figma конкретного пользователя), не облачный API, который можно вызвать за произвольного тенанта через его OAuth-токен. Строить фейковый "Figma-write" через `use_integration` было бы нечестно — не делали.
**Решение (по указанию владельца "думай широко" — Figma нужна не только бренд-буку):** усилена READ-сторона как переиспользуемая способность:
  - `builtin_skills/brand_book.md` — новый шаг 0.5: если у клиента уже есть готовый Figma-файл (ссылка в референсе/брифе), designer читает его структуру (`figma.get_file` — только текст: названия страниц/фреймов, БЕЗ картинки, т.к. `core/llm.py` не поддерживает vision) как ПРИОРИТЕТНЫЙ сигнал направления, вместо гадания по каталогу.
  - `builtin_skills/vite_react_site.md` — developer тоже может прочитать Figma-файл клиента (если он упомянут в бренд-буке) за структурными подсказками (сколько экранов, порядок) — не заменяет «Стиль: …», а уточняет структуру.
**Sitemap — реализовано полностью:**
  - `src/office/sitemap.py` — read-side helper (по образцу `creative_brief.py` после исправления, см. ниже): читает `docs/sitemap.md`, который designer сам пишет/читает через `write_file`/`read_file`; `is_approved()` смотрит на маркер-строку «Статус: одобрено владельцем», которую designer дописывает ТОЛЬКО после явного «да».
  - `builtin_skills/sitemap_planning.md` — designer'ский скилл: 3-6 страниц (не больше — разрастание карты без причины усложняет и разработку, и навигацию), явное одобрение владельцем.
  - `builtin_skills/vite_react_site.md` — developer читает `docs/sitemap.md`; если есть и одобрена — строит `react-router-dom` по карте; если нет или черновик — обычный лендинг (не начинает многостраничную структуру раньше времени).
  - `prompt_builder.py` — новый слот `sitemap_section` для designer/developer.
**Побочная находка — исправлен реальный баг в `creative_brief.py` (issue #13):** модуль был написан с `capture()`/`load()`/`is_set()` как отдельным JSON-хранилищем (`ctx.read_json`), которое ДОЛЖЕН был вызывать агент напрямую — но агенты вызывают ТОЛЬКО зарегистрированные инструменты (`write_file`/`read_file`/`ask_user`), не произвольные Python-функции `office/*.py`. Это значило, что `capture()` НИКОГДА не вызывался — интейк вкуса молча не работал с момента коммита issue #13, несмотря на чистые тесты (тестов на реальный вызов из агента не было). Исправлено на файловый паттерн: `creative_brief.py` теперь read-only helper над `docs/creative_brief.md`, который designer пишет через `write_file` — тот же принцип, что уже проверен в `design_style.ensure_style_line`. `sitemap.py` сразу спроектирован правильно, по этому же паттерну.

### #15 — Enforcement границ ролей на уровне кода (закрывает «известное ограничение» из #13)
**Запрос:** #13 честно документировал, что граница `designer` никогда не пишет в `site/*` держится ТОЛЬКО текстом роли/скилла — технически ничто не мешало LLM вызвать `write_file("site/index.html", ...)`. Нужен настоящий code-level enforcement, а не только промпт.
**Почему это не гипотетический риск:** `ROLE_META[role]["tools"]` — чисто описательные метаданные, `agent_factory.py` выдаёт КАЖДОМУ агенту полный набор файловых тулов независимо от роли (никакой фильтрации по роли не было и нет). Единственная реальная преграда — надежда, что модель прочитает и не нарушит текст `builtin_roles/designer.md`.
**Реализовано:**
- `src/office/roles.py` — новый словарь `ROLE_DENY_PREFIXES` (сейчас: `designer` → `("site/",)`) и функция `path_denied(role, path) -> str` (пусто — разрешено; иначе — текст отказа для tool-результата). Единственный источник правды для enforcement, отдельно от свободного текста в `constraints`.
- `src/agents/file_tool_handlers.py` — `_handle_write_file`/`_handle_delete_file` вызывают `roles.path_denied(role, path)` СРАЗУ после нормализации пути (это единственный фрейм, где одновременно доступны и `role` из замыкания `build(agent_id, role, ...)`, и целевой `path`) и возвращают отказ ДО вызова `workspace_module.write_file`/`delete_file` — designer физически не может записать/удалить файл в `site/*`, а не «не должен по инструкции».

### #23 — Ветвление CEO по стадии бизнеса в детерминированном плане (закрывает «осознанно не сделано» из #22)
**Запрос:** явный выбор владельца из предложенных в #22 направлений — научить план реагировать на `business_stage`, а не только показывать его в промпте.

Единственное место, где ветвления не было вообще — **детерминированный фолбэк** (`planning_engine.fallback_plan`), который используется, когда LLM-генерация недоступна (слабая модель/429/битый JSON) и ДОЛЖЕН быть предсказуем сам по себе (CLAUDE.md §4 «Plan-driven всегда»).
**Реализовано:**
