# Продуктовые сценарии и возможности офиса — где обрывается путь клиента

*Составлено 2026-07-08 прямой проверкой кода (интеграции, скиллы, боты, лиды,
инициативы) — не по старым аудитам. Фокус строго на продукте и пользовательских
сценариях; инфраструктурные/security/биллинг-для-AI-Office доработки —
в `docs/pre-launch-checklist.md`.*

---

## Базовая картина: что офис реально умеет сегодня

Интеграции ([src/integrations/registry.py](../src/integrations/registry.py)):
website (публикация лендинга), telegram/telegram_personal, github, gmail,
google_sheets, google_calendar — 7 штук. 18 скиллов
([src/office/builtin_skills/](../src/office/builtin_skills)) покрывают сайты,
telegram-ботов, копирайтинг, SEO, конкурентный анализ, контент-план.

Это реально работает: лендинг → форма → лид в `leads.json` → виден в UI. Но
это **конвейер анализа и первого контакта**, а не полноценная операционная
система бизнеса — ни один сценарий не доходит до денег в кассе клиента.

---

## Где сценарий обрывается

### 1. Приём платежей — отсутствует полностью
Ни Stripe, ни ЮKassa, ни CloudPayments — ноль совпадений во всём
`src/integrations/`. Офис может написать сайт с ценами, но не может
подключить оплату на нём: клиенту продукта клиента буквально некуда заплатить.
**Приоритет: высокий** — без этого сайт только показывает, не продаёт.

### 2. Бот бронирования — это форма, а не бронирование
[bot_engine.py](../src/office/bot_engine.py) собирает имя/телефон/услугу и
пишет лид — ни разу не обращается к `google_calendar.py`. Нет проверки
занятости слота, нет защиты от двойной записи. Называется «booking bot», по
факту — разговорная анкета.
**Приоритет: высокий** — это буквально функция, заявленная в названии скилла
(`booking_bot_routing`, `launch_booking_bot`), и она не соответствует ожиданию.

### 3. Код после GitHub — тупик для нетехнического клиента
`github.py` умеет создать репозиторий и запушить код. Дальше — ничего: ни
Vercel/Netlify/Render, ни кнопки «скачать zip» в `FileExplorer.tsx`/`server.py`.
Разработчик написал сайт — а поднять его должен сам клиент, ровно та работа,
от которой продукт обещал избавить.
**Приоритет: средний** — для сайтов есть свой хостинг (`/site/{tenant}/{slug}`),
проблема касается кастомного кода/ботов, которые публикуются только через GitHub.

### 4. Лид после захвата дожимается вручную и без напоминаний
`leads.py::stale_new()` находит протухшие лиды (>72ч без ответа) и поднимает
**одно** событие за цикл для продажника — но нет автоматической серии
сообщений, нет email/SMS-дожима, нет правил маршрутизации. Маркетинг и продажи
делят одну таблицу лидов, но ноль автоматизации между ними: это ручной труд
агента заново каждый цикл, не пайплайн.
**Приоритет: высокий** — прямо влияет на конверсию лида в продажу, а «мы
приводим лидов» — часть ценностного предложения.

### 5. Сайт всегда на чужом домене
Ноль упоминаний domain/DNS/CNAME в коде — сайт живёт только на
`/site/{tenant}/{slug}` под доменом платформы. Малый бизнес не может показать
`моякомпания.рф` — блокирует профессиональное позиционирование ровно для
целевой аудитории продукта.
**Приоритет: средний** — не блокирует первую демонстрацию ценности, но
блокирует «настоящий» запуск бизнеса на этом сайте.

### 6. Сценарий «идея» не даёт настоящего вердикта
`initiatives.py::set_research()` пишет результат ресёрча и переводит
инициативу в «pending», но это **рекомендация, не гейт** — владелец может
принять инициативу вопреки любому результату исследования. Заявленная
ценность «AI Office проверит жизнеспособность идеи» на практике не блокирует
запуск, даже если исследование говорит «не стоит».
**Приоритет: низкий-средний** — продуктовое решение, не баг: возможно, это
осознанно (последнее слово у владельца, BOS §2), но тогда стоит явно показать
пользователю «мы рекомендуем не запускать» вместо тихого прохождения дальше.

### 7. Нет CRM/рекламы/инвойсинга как класса
Ни одной интеграции с рекламными платформами (Google/Meta Ads), ни внешней
CRM, ни выставления счетов — то, чем реально живёт малый бизнес день в день,
вне зоны действия офиса совсем.
**Приоритет: низкий для MVP** — большой объём работы, стоит проверить, входит
ли это в целевой сценарий первой волны клиентов, или сознательно оставлено
внешним инструментам (Zapier-подход).

## Что это значит на практике

Продукт сегодня хорош ровно в одном: **исследование + первый контакт**
(маркет-анализ, сайт, форма, первый лид). Всё, что происходит **после**
первого лида — оплата, реальное бронирование, дожим, деплой, реклама — либо
ручное, либо отсутствует. Для позиционирования «полноценная операционная
система, которая ведёт бизнес» это существенный разрыв между обещанием и тем,
что клиент может унести с собой без помощи разработчика.

## Рекомендуемый порядок закрытия

По критерию «что первым увидит и попробует использовать живой малый бизнес»:

1. **Реальное бронирование** (бот ↔ `google_calendar.py`, проверка слота,
   защита от двойной записи) — это буквально то, что уже названо «booking bot».
2. **Приём платежей** (хотя бы один провайдер, без сложной логики тарифов) —
   без него сайт не продаёт, только показывает.
3. **Автоматический дожим лида** (хотя бы одна email-серия после `stale_new()`).
4. **Кастомный домен** для опубликованного сайта.
5. Явный UI-сигнал, когда офис рекомендует НЕ запускать инициативу (сценарий 6).
6. CRM/реклама/инвойсинг — по решению, входит ли это в объём продукта вообще.
