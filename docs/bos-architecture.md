# BOS Architecture — главная архитектурная спецификация AI-Office

*Статус: **утверждаемая спецификация** (v3, 2026-07-08 — §13/§14 сверены с кодом:
шестёрка ядра реализована полностью, таблица mapping переписана с «судьбы» на
факт; см. §14 «Что осталось нерешённым» для реального открытого долга).
Правило проекта: **никакой новый код не появляется, если его место не определено в этом документе.**
Если код не ложится в BOS — сначала правится спецификация (осознанно), потом пишется код.*

## 0. Что такое AI-Office

**AI-Office — это Business Operating System (BOS): операционная система бизнеса,
которая непрерывно сравнивает, куда бизнес хочет прийти, где он находится сейчас,
что мешает — и выполняет действия с максимальным эффектом.**

Цифровая компания — офис, отделы, CEO, персонажи — это **пользовательский интерфейс**
этой системы, её главная проекция. Не сама система.

**Тест архитектуры (применять к каждому решению):**
> Если через 5 лет полностью убрать из интерфейса офис, столы, комнаты и персонажей —
> останется ли ядро таким же сильным? Если нет — ядро заражено визуальной метафорой.

Второй тест:
> Если завтра LLM исчезнут и появится другой тип ИИ — что придётся переписать?
> Правильный ответ: только Providers. Мир, планы, решения, приёмка, история — остаются.

## 1. Язык системы (глоссарий — строгие определения)

Это «слова», на которых разговаривает вся система. Каждое понятие имеет ровно одно
значение. Код, документация и промпты обязаны использовать их в этих значениях.

| Термин | Определение | Чем НЕ является |
|---|---|---|
| **World Model** | Единственный источник правды о компании клиента и её мире. Всё остальное — производные и проекции. Копируемый (snapshot), сравнимый (diff). | Не «база данных всего»: только то, что нужно для решений |
| **Identity (DNA)** | Личность компании: Constitution, Values, Voice, Risk Profile. Живёт отдельно, мутирует от опыта (кроме Constitution), имеет историю версий. | Не конфиг и не часть Prompt Builder |
| **Constitution** | Несмываемая часть DNA: ограничения безопасности (деньги, данные, секреты, публикации). Единственное, что выше воли владельца. | Не бизнес-правила — в бизнесе последнее слово у владельца |
| **Business State** | Текущее измеримое состояние бизнеса: стадия, метрики, бюджет, открытые блокеры, живые артефакты. Часть World Model. | Не весь World Model (историческое имя, теперь — подмножество) |
| **Objective** | Желаемое состояние: измеримая цель с полем `measured_by`. Пока `measured_by` пуст — objective не участвует в gap-анализе, а порождает работу по созданию измеримости. | Не лозунг и не milestone |
| **Gap** | Вычислимая разница между Objective (desired) и Business State (current). Главный источник работы в зрелом режиме. | Не «ощущение CEO» |
| **Intent** | Намерение, поступившее извне (владелец) или изнутри (инициатива): неструктурированная воля до интерпретации. Входящий сигнал, не управляющий. | Не задача и не приказ к немедленному исполнению |
| **Strategy** | Выбранный способ закрытия Objectives: позиционирование, приоритеты, ограничения курса. Производная от Objectives + Research. | Не документ ради документа — читается Planning Engine |
| **Capability** | Способность компании делать класс работы (сайты, боты, реклама, CRM, видео). Есть/нет/можно приобрести. Отсутствие Capability — самостоятельный вид Gap. | Не синоним Skill: Skill — один из способов реализации Capability |
| **Work** | Единый конверт любой деятельности компании крупнее задачи: id, title, `type` (project \| process \| initiative), goal, status, owner. Одна сущность, три разных внутренних движка — см. §5. | Не синоним Project: Project — один из трёх `type` |
| **Project** | `Work` с `type=project`: есть начало и конец, ведёт к результату. Цель + спецификация + Stage-путь (веха за вехой) + Task-дерево + артефакты + метрики, оставленные после себя. Закрывается один раз. | Не «весь план тенанта», не годится для незавершающейся работы |
| **Process** | `Work` с `type=process`: никогда не завершается сам по себе (продажи, контент-конвейер, поддержка). Не имеет одной «текущей Stage» — вместо этого набор Stage-**определений** (шаблон конвейера) + поток `Instance`, у каждого своя текущая стадия. | Не Project без даты окончания — это структурно другая сущность (см. §5) |
| **Initiative** | `Work` с `type=initiative`: идея владельца или компании ДО решения — одна стадия «исследование» → бинарный `decision` (спородить Project / закрыть). Самая лёгкая из трёх: без Stage-пути и без Task-дерева. | Не Project «в зачаточном состоянии» — до decision структуры плана не существует |
| **Stage** | Веха на пути `Work`. Для Project/Initiative — одноразовый этап (todo→active→done), Work проходит их по порядку. Для Process — это НЕ прогресс самого процесса, а определение шага конвейера, через который проходит каждый `Instance`. | Не milestone-навсегда: смысл слова зависит от `Work.type` |
| **Instance** | Один элемент, проходящий через Stage-конвейер `Process` (лид, тикет поддержки, единица контента). Имеет свою текущую Stage, историю переходов, свой критерий завершения (сделка выиграна/проиграна). Обобщение того, что раньше было `Lead` только для продаж. | Не Task — не исполняется ролью напрямую, отслеживает состояние бизнес-объекта |
| **Specification** | Формализованное понимание Project ДО исполнения: функции, стек, критерии успеха. Подтверждается владельцем. Источник чек-листа Acceptance. | Не ТЗ-архитектора-в-стол: это контракт приёмки |
| **Workflow** | Повторяемая последовательность шагов ВНУТРИ одной задачи/проекта (разработка→тест→ревью→деплой) — деталь исполнения, не бизнес-уровня. | Не Process: Process — это Work верхнего уровня, Workflow — техника внутри Task/Project |
| **Task** | Атомарная единица исполнения: роль, зависимости, done_criterion, декларация артефактов, попытки. Может иметь `parent_id` на другую Task — так получается вложенность произвольной глубины (что раньше называли Subtask) без отдельной сущности. Закрывается ТОЛЬКО Acceptance. | Не «поручение в чате», не закрывается фактом сдачи; нет отдельного типа Subtask |
| **Decision** | Транзакция над Plan, прошедшая Sandbox-проверки. Всегда выражается как diff плана/мира, никогда — как прямое действие. | Не мысль CEO в ленте |
| **Plan** | Действующая структура достижения целей: граф задач проектов. Первичен над решениями («Decision = ремонт плана»). | Не список пожеланий |
| **Event** | Доменный факт, произошедший в компании (сигнал, проблема, блокер, возможность, измерение). Имеет kind-контракт: blocker гарантированно обрабатывается детерминированно. | Не SSE-сообщение UI (это проекция) |
| **Fact** | Единица знания в памяти: источник, сущность, уверенность, время. Ужимается при подаче, не при записи. | Не результат-отчёт («X сделал Y» — это History) |
| **Artifact** | Продукт для клиента или компании: код, сайт, документ, кампания. Живёт в workspace, имеет владельца-проект. | Не знание и не состояние |
| **History** | Append-only журнал: что происходило и почему (решения, сдачи, публикации, ответы владельца). Источник дайджестов, уроков и «почему сайт такой». | Не отладочный лог |
| **Role** | Функция в компании: миссия, границы, что нельзя. «Кто». | Не способ («как» живёт в Skills) и не персонаж UI |
| **Worker** | Исполнитель работы (сегодня — LLM-воркер с инструментами; завтра — любой). | Внутренний термин «агент» допустим только в коде |
| **Skill** | Упакованный способ делать работу (playbook, .md-файл). Реализация Capability. | Не роль |
| **Provider** | Механизм вычисления/действия: LLM, внешний сервис, API. Заменяемый слой. | Не часть домена |
| **Sandbox** | Универсальный механизм проверки любого изменения: копия среза мира → изменение → проверки → оценка → merge/discard. Работает на двух масштабах: Decision Sandbox (снапшот World Model) и Sandbox Company (клон тенанта). | Не только тестовая среда для кода |

**Терминология для пользователя:** слова «агент» в UI и документации нет.
Есть руководители, специалисты, отделы, процессы, решения, результаты.

## 2. Иерархия воль и целей

```
Constitution        ← выше всех, но ТОЛЬКО в ограничениях безопасности
      ↑ (safety veto)
Owner Intent        ← последнее слово во всех бизнес-решениях
      ↓
Objectives          ← измеримые цели (desired state)
      ↓
Gap                 ← вычислимый разрыв (Objective vs Business State)
      ↓
Strategy            ← способ достижения
      ↓
Plan                ← действующая структура работы: порождает Work
      ↓
Work                ← Project | Process | Initiative (см. §5)
      ↓
Stage / Instance     ← вехи (Project/Initiative) или поток элементов (Process)
      ↓
Tasks (+ вложенность через parent_id)  ← исполнение
```

**Gap не создаёт голую задачу напрямую — он создаёт Work.** Разрыв «не хватает
заявок» порождает Project «усилить привлечение» (или несколько), а не одну строку
в общем списке задач без владельца-структуры. Это правило заменяет более раннюю,
упрощённую реализацию `gap.replan()` (см. §13).

Правила разрешения конфликтов:
1. **Система никогда не отказывает владельцу — она торгуется, показывая цену.**
   Intent, конфликтующий с Objectives, не отклоняется и не исполняется молча:
   владельцу показывается конфликт и варианты («бот сдвинет CRM на квартал: бот
   сейчас / CRM сейчас / урезанный бот»). Выбор владельца обновляет Priorities,
   после чего система не «саботирует» его ради старой цели.
2. Constitution даёт вето только на классы действий: перевод денег, удаление данных,
   раскрытие секретов, необратимые публикации — без явного подтверждения владельца.
3. Собственным инициативам компании (не-владельцу) система отказывать может и должна —
   через gap-анализ и бюджет.

## 3. Ядро BOS: кибернетический цикл

```
        Desired State (Objectives)
                 │
                 ▼
   ┌──── Gap Analysis ◄──── Current State (Business State)
   │             │                       ▲
   │             ▼                       │
   │        Priorities                   │
   │             │                       │
   │             ▼                       │
   │     PLANNING ENGINE  ── план/diff ──┤
   │             │                       │
   │             ▼                       │
   │   Decision (= транзакция над Plan,  │
   │     прошедшая Sandbox-проверки)     │
   │             │                       │
   │             ▼                       │
   │        EXECUTION                    │
   │   (Execution Policy → Worker)       │
   │             │                       │
   │             ▼                       │
   │        ACCEPTANCE                   │
   │             │                       │
   │             ▼                       │
   └──────── Measurement ────────────────┘
```

**Planning Engine выдаёт Work, а не голые задачи.** Каждый Gap/Intent, дошедший
до планирования, порождает `Work` (Project/Process/Initiative — см. §5) с
Stage-путём или Instance-потоком внутри; отдельная задача без владельца-Work —
запрещённое состояние (переходное, только пока миграция plan.json не завершена,
см. §13).

**Planning Engine главнее Decision Engine.** Решение — локально, план — глобален.
Каждый Intent и каждый Gap оцениваются не сами по себе, а через план достижения
Objectives. Decision Engine нужен там, где план рвётся: блокер, новый intent,
изменившийся gap. Его выход — всегда diff плана.

### Два режима зрелости компании

| | **Bootstrapping (intent-driven)** | **Steady State (gap-driven)** |
|---|---|---|
| Когда | Мир ещё не измерим (онбординг, первые проекты) | Метрики накоплены |
| Источник работы | Intents владельца | Gap Analysis (+ Intents как один из сигналов) |
| Обязанность | **Каждый проект оставляет после себя измеримость** (бот → счётчики заявок, сайт → лиды) | Continuous Improvement: измерение → инициатива |
| Переход | Автоматический: Objective получает `measured_by` → участвует в gap-цикле | — |

**Принцип BOS №1:** *любая выполненная работа должна увеличивать способность
компании понимать собственный бизнес.* Первые проекты — это создание органов чувств.

**Принцип BOS №2 (непрерывная ответственность):** работа не заканчивается деплоем.
Deploy → Monitoring → Measurement → авто-инициативы («47% уходят на шаге телефона —
предлагаю альтернативный сценарий»). AI-Office отвечает не за создание артефакта,
а за то, чтобы артефакт достигал бизнес-цели и продолжал её достигать.

## 4. World Model

```
World Model  (SSOT; snapshot + diff; никто ничего не «знает» — все читают мир)
├── Identity (DNA)      — Constitution, Values, Voice, Risk Profile (+ версии)
├── Business State      — стадия, бюджет, метрики, блокеры, живые артефакты
├── Objectives          — desired state, measured_by, приоритеты
├── Strategy            — курс, позиционирование, ограничения
├── Capabilities        — что компания умеет / чего не умеет / что приобретает
├── Work                — Project/Process/Initiative: активные и завершённые;
│                          spec, Stage-путь или Instance-поток, артефакты, метрики
├── Knowledge           — факты (source, entity, confidence, ts)
├── Artifacts           — реестр продуктов (владелец-проект, ревизии)
├── Metrics             — временные ряды измерений (источник: факт | оценка)
├── History             — append-only журнал происходившего и почему
└── Relationships       — люди и системы вокруг: владелец, клиенты, интеграции
```

Правила:
- **SSOT.** Запрещены два паттерна: состояние в памяти процесса (futures, watchdog-словари)
  и знание, существующее только в тексте промпта. Всё — в мире.
- **Snapshot + diff обязательны с первого дня** — на них стоят оба Sandbox-механизма.
- Метрика всегда помечена источником: `факт` (система измерила) или `оценка`
  (сказал владелец / прикинула LLM). Решения на оценках — с пониженной уверенностью.
- Экономика бизнеса (выручка, burn, ROI) — поля Metrics/Business State; пока нет
  доступа к реальным данным — прокси (лиды × заявленный чек) с пометкой `оценка`.

## 5. Work — Project / Process / Initiative

Не вся деятельность компании — проект. Настоящая компания живёт одновременно в
трёх режимах, и попытка засунуть их в одну модель («всё — проект») либо врёт о
прогрессе процессов, либо утяжеляет разовые инициативы лишней структурой.

```
Work (envelope: id, title, type, goal, status, owner)
 │
 ├── type=project     → Stage (веха, once) → Task(parent_id?) → Acceptance
 │                       Разовое: есть начало и конец, после — закрыт навсегда.
 │
 ├── type=initiative  → одна Stage «исследование» → decision: spawn_project | closed
 │                       Самое лёгкое: до decision Stage-пути и Task-дерева не существует.
 │
 └── type=process     → Stage-определения (шаблон конвейера, НЕ прогресс)
                         + поток Instance, у каждого своя текущая Stage
                         Никогда не завершается сам; «прогресс» не определён для
                         Process в целом — только у отдельного Instance.
```

### Почему три, а не одна сущность

- **Project** и **Initiative** имеют единую жизненную линию, которая один раз
  доходит до конца — здесь естественна модель «путь по вехам».
- **Process** (продажи, контент-конвейер, поддержка) не имеет единой текущей
  стадии: одновременно десятки Instance на разных шагах конвейера. Раньше это
  решалось разовым кодом под конкретный случай (`leads.py` — лид со статусом и
  историей переходов). Правильная генерализация: `leads.py` становится частным
  случаем `process_instances.py` (Instance с `process_id`, `stage`, `history`),
  применимым не только к продажам, но и к любому конвейеру, который заведёт компания.
- **Task** не получает отдельного типа Subtask: `parent_id` даёт вложенность
  произвольной глубины дешевле, чем фиксация ровно четырёх уровней иерархии.

### Как рождается Work

Пользователь формулирует цель или задачу («хочу увеличить прибыль на 30%»,
«нужен Telegram-бот») — не структуру. Planning Engine сам решает, во что это
превращается:

```
Intent/Gap → Planning Engine → решает тип Work:
   разовый результат с понятным концом   → Project
   идея, требующая оценки перед стартом  → Initiative
   постоянный поток однотипных элементов → Process
```

Пользователь может скорректировать получившийся план (Stage/Task/Instance-шаблон),
но не обязан проектировать его сам — это и есть переход от таск-менеджера к
системе, превращающей бизнес-цели в исполнимую работу.

### Acceptance для разных типов Work

Acceptance (§9) в исходном виде (5 уровней) применяется к Task внутри Project и
Initiative. У Process своя семантика завершения — не «пять уровней приёмки
конвейера целиком», а критерий на уровне Instance («сделка выиграна/проиграна»,
«тикет закрыт»), определяемый шаблоном процесса.

## 6. Capability Layer

Перед принятием работы Planning Engine спрашивает не только «кто свободен»,
а «умеем ли мы это». Отсутствие Capability — самостоятельный Gap с собственным решением:

```
Intent «выйти в TikTok»
        ↓
Capability check → отсутствует
        ↓
Decision: приобрести способность
   ├─ установить Skill
   ├─ подключить Provider / внешний сервис
   ├─ попросить владельца дать API-ключ (ask_user)
   ├─ делегировать внешнему исполнителю
   └─ (будущее) нанять человека
        ↓
Capability появилась → исходная работа планируется
```

Так компания растёт: не только выполняет работу, но расширяет собственные возможности.
Skills-каталог и Tool Router — существующие реализации нижней половины этого слоя;
Capability — их доменная надстройка (и общий скорер потребностей — один, не два).

### 6.1. Platform Self-Knowledge

Способность агента понимать **свою собственную конфигурацию** (роль, активный
скилл, список доступных ему инструментов) — не исходный код платформы. Умышленно
узкая: агент не читает `src/office/*.py` целиком (это раскрыло бы устройство
security-чувствительных модулей — `auth.py`, `crypto.py` — без необходимости
для его задач), а видит ровно ту же информацию, что уже пришла ему в системном
промпте (`office/self_awareness.py::describe`).

- Доступно всем ролям — риска нет: это отражение собственной, уже выданной
  агенту конфигурации, а не чтение чужого кода или чужих данных.
- Нет read-доступа к исходникам платформы вообще ни для одной роли — если в
  будущем понадобится architect/cto-доступ к части кода платформы, это отдельное
  решение с собственным денилистом security-модулей, не переиспользование этой
  способности.

### 6.2. Иерархия доступа к данным бизнеса

Область видимости данных — по зоне ответственности роли, а не одинаковая для всех:

| Уровень | Роли | Что видит |
|---|---|---|
| **Портфель** | CEO (orchestrator), лидеры отделов (CTO/CMO/Head of Sales), надпроектные сервисные роли (architect/strategist/researcher/hr) | все проекты тенанта (read), файлы любого проекта (read) + свой рабочий контекст |
| **Проект** | рядовые воркеры (developer/designer/integrator/marketer/analyst/salesman) | только свой `project_dir` (read+write) |
| **Общий (всем)** | все роли | бриф/бизнес-инфо, доступы (connections), скиллы, командные политики |

Принципы:
- **Кросс-проектное — только чтение.** Менять чужой проект нельзя: артефакт
  меняет тот, кому он делегирован (инвариант единой ответственности). Портфельные
  инструменты (`list_projects`/`list_project_files`/`read_project_file`) физически
  read-only, поверх `workspace.project_scope()` (область гарантированно возвращается).
- **Гейт по роли, не по флагу** — в `agent_factory` (как `ask_user` vs `ask_leader`);
  воркер портфельных инструментов не видит вовсе.
- **project_dir от модели валидируется** через `projects.valid_workspace_dir`
  (только имена из реестра проектов) — path-инъекция и выход за тенанта отсечены.
- Ложится в §4 World Model (проекты — уже SSOT, это чтение среза, не новое
  состояние) и §8 Prompt Builder (портфельный дайджест лидеру — слот, зависящий
  от роли, сериализатор один).

## 7. Execution Policy

Формальный выбор исполнителя для задачи — по четырём осям:
**стоимость × качество × скорость × доступность.**

```
Task ──► Execution Policy ──► детерминированный код   (проверки, публикация, роутинг)
                          ──► LLM-Worker + Skill       (производство артефактов)
                          ──► LLM-вызов без персоны    (интерпретация, оценка)
                          ──► Интеграция / внешний API (действия в мире)
                          ──► Внешний исполнитель       (kind: external)
                          ──► Человек (владелец)        (ask_user — последний резерв)
```

- Стоимость определяет **задача, а не отдел**: reasoning-задача → дорогая модель,
  рутина → дешёвая. Cost-tier — атрибут типа задачи в политике.
- Каждое платное действие имеет `estimated_cost`, сверяемый с бюджетом до исполнения.
- Приоритет: если детерминированный код может — LLM не вызывается
  (уже доказано продом: маршрутизация задач без LLM-лидеров).

## 8. Prompt Builder — компилятор мышления

`build(WorldModel, Role, Decision/Task) → Prompt` — **чистая функция без собственного
состояния**. Преобразует состояние компании в мышление конкретной роли.

Слоты (порядок фиксирован):
```
Identity (DNA) → Policies → Brief/State → Memory (указания владельца)
→ Knowledge (retrieval) → Events → Task → Tools → Output Format
```

Правила:
- Builder не знает ничего, чего нет в World Model. Понадобилось что-то ещё —
  это дырка в модели мира, а не повод дописать шаблон.
- Каждая сущность мира сериализуется в промпт ровно одним сериализатором
  (пример: подпись «цель прогона ≠ то, что продаёт бизнес» пишется один раз —
  класс багов goal/niche исчезает по построению).
- Собранный промпт целиком логируется в History/trace — отладка мышления зрячая.
- Роли и политики — файлы (.md), как скиллы, а не Python-литералы.

## 9. Acceptance — пять уровней валидации

Задача/проект закрываются только приёмкой. «Done = непустая строка» запрещено.

| Уровень | Что проверяет | Механизм |
|---|---|---|
| 1. **Specification** | Понята ли задача — ДО кода | Спека (функции, стек, критерии успеха) → подтверждение владельца |
| 2. **Build** | Собирается/компилируется | verify_code, линтеры, установка зависимостей, тесты |
| 3. **Functional** | Проходит ли пользовательский путь | Прогон сценария: для бота — вызов хендлеров с фейковыми Update без сети; для сайта — критик + формы |
| 4. **Business** | Соответствует ли бизнес-цели | Оценка против Objective/measured_by; рекомендации («сократить сценарий до 3 шагов») |
| 5. **Acceptance** | Чек-лист из Specification | Детерминированный чек-лист + LLM-ревью; провал → работа возвращается |

После деплоя уровни 3–5 продолжают жить как Monitoring (Принцип №2).

## 10. Sandbox — универсальный механизм изменений

Одна механика, два масштаба, любой предмет (код, стратегия, цены, бюджет, найм):

```
Срез мира ──clone──► изменение ──► детерминированные проверки ──► оценка ──► merge / discard
```

- **Decision Sandbox:** snapshot World Model → применить diff решения → проверки
  (бюджет, конфликты артефактов, ограничения владельца, Constitution, risk profile).
  LLM может участвовать только как один из чекеров с пометкой «оценка»; вето дают
  детерминированные проверки. Это dry-run транзакции, не «симуляция мира».
- **Sandbox Company:** клон тенанта (копия `data/tenants/<tid>/` — файловая
  персистентность делает это дёшево) как ветка: разработка → тесты → ревью →
  merge артефактов и фактов в основную компанию.

## 11. События

- Доменные события ≠ события UI (SSE — проекция).
- Контракт по kind: `blocker` — гарантированная детерминированная реакция
  (пауза ветки плана / вопрос владельцу), `problem`/`opportunity` — вход Planning
  Engine, `signal`/`info` — контекст. «Может быть, LLM заметит» — не обработка.
- Каждое значимое событие пишется в History.

## 12. Офис как проекция

UI-слой (изометрический офис, персонажи, чаты с CTO) — проекция ядра, эмоциональный
интерфейс. Он важен для продукта (пользователь разговаривает с CTO, а не с
Developer #14) и **не подлежит удалению** — но не может владеть логикой:

- Лидер отдела — персона (имя, чат, доска отдела), НЕ решатель: маршрутизацию
  делает Planning Engine детерминированно.
- Board / trust / «понимание компании» — UX-механики поверх данных ядра, без
  собственной бизнес-логики.
- Чат с персоной = view над Role + History.
- Два режима UI: «клиент» (что сделали / что нашли / что спросить / что согласовать /
  сколько потратили) и «под капотом» (план, события, память, решения).

## 15. Инварианты BOS (сводка — НЕ ломать)

1. World Model — SSOT: ни состояния в памяти процесса, ни знаний только-в-промптах.
2. Владелец имеет последнее слово во всех бизнес-решениях; Constitution — вето
   только по безопасности; система торгуется, но не отказывает и не саботирует.
3. Decision = транзакция над Plan, прошедшая Sandbox. Прямых действий мимо плана нет.
4. Задача закрыта только Acceptance. Сдача ≠ приёмка.
5. Каждый проект оставляет после себя измеримость.
6. Ответственность непрерывна: deploy → monitoring → инициативы.
7. Стоимость исполнения определяет задача; платное действие знает свой estimated_cost.
8. Детерминированный код первичнее LLM везде, где возможен.
9. Офис — проекция. Логика в UI-сущностях не живёт.
10. «Агент» — только внутренний технический термин.
11. Gap/Intent порождают Work (Project/Process/Initiative), не голую задачу без
    владельца-структуры.
12. Process не имеет единой «текущей стадии» — прогресс есть только у Instance;
    попытка посчитать «процент выполнения процесса целиком» — архитектурная ошибка.
13. Subtask — не отдельная сущность: вложенность Task через `parent_id`.
