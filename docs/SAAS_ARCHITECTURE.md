# AI-Office → многопользовательский SaaS: архитектура

Документ описывает, как превратить текущий одно-пользовательский прототип в
мультиарендный (multi-tenant) сервис, где у каждого клиента свой изолированный
офис, свои доступы (включая GitHub), свой деплой и свой бюджет.

> Статус: проект архитектуры (код пока не меняется). Реализуется поэтапно (см. §12).

---

## 1. Принцип мультиарендности

- **Row-level multi-tenancy**: один экземпляр приложения и одна БД; у каждой записи
  есть `tenant_id` (= рабочее пространство клиента). Проще и дешевле, чем
  схема-на-клиента; достаточно для старта и роста.
- Единица изоляции — **workspace (рабочее пространство клиента)**. У пользователя
  может быть несколько workspace (свои проекты), но на старте: 1 пользователь = 1 workspace.
- **Жёсткое правило**: ни один запрос/агент/файл/событие не пересекает границу `tenant_id`.

```
User ──many──> Workspace(tenant) ──> { Brief, Office(agents), Connections,
                                       Workspace files, Leads, Sites, Costs,
                                       Threads, Milestones, Events }
```

---

## 2. Аутентификация — «Войти через GitHub» (ключевое решение)

Логин через **GitHub OAuth** закрывает сразу две задачи: вход в сервис И подключение
GitHub клиента. Это и есть удобный интерфейс «как подключить GitHub».

- **Hosted-версия (есть домен + HTTPS)**: GitHub OAuth **Authorization Code + PKCE**.
  Кнопка «Войти через GitHub» → редирект на github.com → callback `/auth/github/callback`
  → обмен `code` на access token → создаём/находим `User` + `Workspace` → ставим
  сессионную cookie (подписанную / JWT).
- **Self-host / без домена**: GitHub **Device Flow** (кнопка → код → ввод на
  github.com/login/device → поллинг токена). Работает локально, без callback URL.
- **Альтернативный вход** (для тех, кто без GitHub): email magic-link. GitHub тогда
  подключается отдельной кнопкой «Подключить GitHub».

**Scopes**: `read:user` для логина; `repo` (или точечнее) — когда клиент хочет
пуш кода/деплой. Лучше двухшаговая выдача: сначала логин (минимум), потом
«Подключить GitHub для деплоя» с `repo` — меньше пугает пользователя.

Рекомендация: использовать готовый провайдер, чтобы не писать безопасность паролей
самим — **Supabase Auth / Clerk / Auth0** (все умеют GitHub OAuth из коробки) либо
тонкий собственный OAuth-хендлер на FastAPI (`authlib`). Для контроля и без вендор-лока
— `authlib` + наша таблица `users`.

---

## 3. Подключение внешних сервисов клиентом (GitHub и др.)

Каждый клиент в своём кабинете («Доступы») видит кнопки-коннекторы:

| Сервис | Способ подключения | Что хранится |
|--------|--------------------|--------------|
| GitHub | OAuth (login/Device Flow) → токен | access token (шифр.), username, repo-scope |
| Telegram | ввод токена бота (как сейчас) | bot token (шифр.) |
| Прочие (Notion, Sheets…) | OAuth где есть, иначе ввод ключа | креды (шифр.) |

- Текущая вкладка «Доступы» (`connections`) становится **per-tenant** и получает
  для GitHub поток OAuth/Device вместо ручной вставки токена.
- Токен GitHub используется для `create_repo` и `push` (через GitHub REST API или
  `git` с `x-access-token`).

---

## 4. Хранение секретов (закрывает проблему утёкших ключей)

- Сейчас ключи лежат открытым текстом в `reports/connections.json` — недопустимо для SaaS.
- Все креды шифруются **at rest**: симметрично (Fernet/AES-GCM) ключом из
  `APP_SECRET`/KMS; в БД — только шифротекст. В API наружу — маскированные значения.
- Доступ к расшифровке — только серверный код агентов в рамках своего `tenant_id`.

---

## 5. Модель данных (БД вместо плоских JSON)

Переход с `reports/*.json` на БД (Postgres в проде, SQLite в dev; ORM — SQLModel/SQLAlchemy).

Базовые таблицы (все, кроме `users`, имеют `tenant_id`):

```
users(id, email, github_login, created_at)
workspaces(id, owner_user_id, name, plan, created_at)            -- tenant
briefs(tenant_id, niche, goal, audience, assets, summary, ...)
agents(tenant_id, agent_id, role, skill, desk, status, task)
deliverables(tenant_id, agent_id, role, task, content, ts)
milestones(tenant_id, stages_json)
connections(tenant_id, name, type, fields_encrypted, note)
memory(tenant_id, question, answer, ts)
threads(tenant_id, agent_id, messages_json)
office_channel(tenant_id, messages_json)
sites(tenant_id, slug, title, html, ...)         -- slug уникален глобально
leads(tenant_id, slug, name, contact, message, ts)
costs(tenant_id, agent_id, model, in_tokens, out_tokens, cost, calls)
files(tenant_id, path, content|blobref, size)    -- или объектное хранилище
events(tenant_id, type, payload, ts)             -- лента/история
```

Каждый текущий модуль `office/*.py` (синглтон) превращается в репозиторий с явным
`tenant_id` (см. §11). Файлы кода (`workspace`) — на диск в `data/<tenant_id>/workspace`
или в объектное хранилище (S3/R2) при масштабировании.

## 6. Исполнение «офиса» на каждого клиента

Сейчас один глобальный `office_loop.run()` (asyncio-таск). В мультиаренде:

- **Этап 1 (просто, с лимитом)**: менеджер тенант-циклов внутри процесса —
  словарь `tenant_id → asyncio.Task`, запускается при активном брифе, останавливается
  при простое/выходе. Лимит одновременно активных офисов (например 20–50) на инстанс.
- **Этап 2 (масштаб)**: вынести цикл в **очередь задач/воркеры** — `Arq`/`Celery`/`RQ`
  + Redis. Каждый «ход директора» — это job, планируемый по расписанию на тенанта.
  Горизонтальное масштабирование воркеров; FastAPI остаётся тонким API/SSE-слоем.
- Блокирующие `ask_user`-futures (`questions.py`) переносятся в БД (вопрос со статусом
  pending/answered), чтобы переживать рестарты и работать в воркерах.

---

## 7. Реалтайм (SSE) по клиенту

- `bus.py` сейчас вещает всем. Делаем **шину на тенанта**: подписка `/events` берёт
  `tenant_id` из сессии и получает только свои события. При воркерах — события идут
  через Redis pub/sub (канал на тенанта), а FastAPI ретранслирует в SSE.

---

## 8. Деплой артефактов клиента (сайты и боты)

- **Сайты/лендинги**: уже хостятся бэкендом (`/site/{slug}`). Делаем slug-namespacing
  по тенанту; артефакт работает сразу, без внешних сервисов.
- **Telegram-боты** (нужен долгоживущий процесс):
  - Агент-разработчик пишет код в `workspace` тенанта → пуш в **GitHub-репозиторий клиента**
    (его токен) + генерим `Dockerfile`/`railway.json`/`Procfile` и README.
  - Запуск:
    - **MVP**: репозиторий с кнопкой «Deploy to Railway» (template) — клиент в один клик
      разворачивает у себя; токен бота берётся из его connections.
    - **Авто**: интеграция с **Railway API** (деплой по токену — клиента или нашему
      «зонтичному» аккаунту) → бот поднимается автоматически, статус возвращается в UI.
  - Запуск произвольного LLM-кода = **изоляция обязательна** (отдельный контейнер на
    бота, лимиты CPU/RAM/сети, без доступа к нашей инфре). Не запускать в основном процессе.
- Для сайтов с кодом (не лендинг-конструктор) — тот же путь: репозиторий + статический/контейнерный деплой.

---

## 9. Биллинг и лимиты (поверх уже готового учёта)

- `costs.py` уже считает токены/стоимость — делаем его **per-tenant** и добавляем:
  - тарифные планы (free/pro), месячный лимит трат, **жёсткий стоп** при превышении;
  - подтверждение «дорогих»/внешних действий (Фаза 1 из прошлого плана).
- Платежи — **Stripe** (подписки + usage-based при желании).

---

## 10. Безопасность и приватность (для multi-tenant обязательно)

- Изоляция `tenant_id` на уровне каждого запроса к БД (helper, который всегда
  подставляет tenant из сессии; запрет «сырых» запросов без него).
- Шифрование кредов (§4), HTTPS, защита от CSRF на OAuth-callback (`state`-параметр),
  rate-limiting, аудит-лог действий агентов наружу.
- Песочница для исполнения кода ботов (§8).

---

## 11. Карта рефактора текущих модулей

| Сейчас (глобальный синглтон) | Станет |
|------------------------------|--------|
| `brief.py`, `state.py`, `registry.py`, `milestones.py`, `progress.py` | репозитории с `tenant_id` |
| `connections.py` | per-tenant + **шифрование** + OAuth-коннекторы |
| `memory.py`, `threads.py`, `office_channel.py`, `agent_inbox.py` | per-tenant |
| `sites.py`, `leads.py`, `costs.py`, `workspace.py` | per-tenant (slug/файлы неймспейсятся) |
| `questions.py` (futures в памяти) | вопросы в БД (pending/answered), совместимо с воркерами |
| `bus.py` | шина на тенанта (in-proc → Redis pub/sub) |
| `loop.py` (`run()` один общий) | менеджер тенант-циклов → очередь задач |
| `core/llm.py` | без изменений по сути; `costs.record(tenant_id, …)` |
| `server.py` | + auth/OAuth, сессии, извлечение `tenant_id`, per-tenant эндпоинты |

Приём: ввести объект **`Tenant`/контекст запроса** и протащить `tenant_id` во все
функции офиса (или хранить в `contextvars` на время обработки запроса/хода офиса).

## 12. Поэтапный план

- **Phase 0 — Каркас мультиарендности**
  Auth (GitHub OAuth login) + таблицы `users/workspaces` + сессии + извлечение
  `tenant_id`. БД (SQLite→Postgres) + ORM. Один тестовый тенант проходит онбординг.
- **Phase 1 — Изоляция данных**
  Перевести модули из §11 на `tenant_id` (поэтапно, начиная с brief/state/connections).
  Шифрование кредов.
- **Phase 2 — Per-tenant офис + реалтайм**
  Менеджер тенант-циклов + SSE по тенанту. Лимит активных офисов.
- **Phase 3 — GitHub-коннект и пуш кода**
  Коннектор GitHub (OAuth/Device) → `create_repo`/`push` из `workspace` тенанта.
- **Phase 4 — Деплой**
  Сайты (namespacing) + боты (репозиторий + Railway template, затем Railway API,
  изоляция исполнения).
- **Phase 5 — Биллинг и лимиты**
  Планы, лимиты трат поверх `costs`, Stripe, подтверждение внешних действий.
- **Phase 6 — Масштаб**
  Очередь задач (Arq/Redis) для офис-циклов, объектное хранилище файлов, многоинстансность.

---

## 13. Рекомендуемый стек

- **Backend**: текущий FastAPI; ORM — SQLModel/SQLAlchemy; миграции — Alembic.
- **БД**: Postgres (Neon/Supabase/Railway) в проде, SQLite в dev.
- **Auth**: GitHub OAuth (`authlib`) или Supabase Auth/Clerk.
- **Очередь/реалтайм при масштабе**: Redis + Arq (jobs) и Redis pub/sub (события).
- **Хранилище файлов**: диск per-tenant → S3/R2 при росте.
- **Деплой ботов клиентов**: GitHub-репозиторий + Railway (template → API).
- **Платежи**: Stripe.
- **Секреты**: шифрование Fernet/AES-GCM ключом из env/KMS.

---

## 14. Что первым (рекомендация)

Phase 0 (Auth «Войти через GitHub» + каркас тенанта + БД) — это и фундамент
мультиарендности, и сразу даёт удобное подключение GitHub, которое просил клиент.
Без него «свой GitHub у каждого» и изоляция невозможны.
