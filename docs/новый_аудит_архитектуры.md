Принято. Прежде чем писать отчёт, дочитаю модули, которые ещё не смотрел в этой сессии — иначе аудит будет нечестным (доменная модель: онбординг, вехи, DNA, capability-режимы, intake, уроки).

Контекст собран — за эту сессию я прочитал практически весь домен (30+ модулей ядра, спека BOS, роли/политики/скиллы, фронт). Ниже — полный архитектурный аудит.

# Ревизия AI-Office относительно BOS Architecture

*Chief Architect review, 2026-07-03. Аудитория — команда, принимающая проект.*

## 1. Общая архитектура

**Как сейчас.** Система — это **мультиарендный автономный цикл над файловой персистентностью**. Ядро — не «офис» и не «агенты», а связка из четырёх вещей: (1) **план-граф задач** (`plan.py`) как единственный источник работы; (2) **автономный цикл** (`loop.py`), который каждые N секунд детерминированно маршрутизирует готовые задачи плана свободным исполнителям; (3) **LLM-воркер** (`llm.run_agent` + `agent_factory`) — универсальный исполнитель с инструментами; (4) **per-tenant файловое состояние** (`saas/context.py`: ContextVar + `data/tenants/<tid>/*.json`). Всё остальное — брифы, вехи, события, знания, доверие, автономия — сателлиты вокруг этой оси. Главный поток данных: `бриф → bootstrap (ресёрч→стратегия→ТЗ→план) → цикл {CEO-гейт → маршрутизация → воркер → приёмка → доска} → артефакты в workspace/ → публикация → лиды`.

**Почему так.** Проект вырос из демо «агенты в изометрическом офисе» и был последовательно пересобран вокруг plan-driven цикла, когда LLM-хаос (лидеры выдумывали работу, 128 пустых вызовов CTO) доказал, что решения должен принимать детерминированный код.

**Хорошо.** Ось «план → детерминированная маршрутизация → приёмка» — это уже скелет кибернетического цикла BOS §3, и он реально работает (проверено живым прогоном). Мультиарендность честная: ни одной глобали с данными тенанта.

**Плохо.** `loop.py` — это 1300 строк, в которых сплавлены Planning Engine, Decision Engine, watchdog, публикация, приёмочный оркестратор и антициклы. Это «главный файл», который знает всё, — новый разработчик обязан прочитать его целиком, чтобы понять систему.

**Не соответствует BOS.** BOS требует Planning Engine как отдельную подсистему («вынести из loop.py», §12) — не сделано. Живость (watchdog-словари, futures вопросов) в памяти процесса — прямое нарушение SSOT §4.

**Что менять.** Расслоить `loop.py`: планирование/маршрутизация → planning-модуль, жизненный цикл воркера → execution-модуль, циклический шедулер — остаётся.

**Приоритет: высокий** (это предусловие масштабирования командой).

## 2. Domain Model

**Реальное дерево сегодня:**

```
Tenant (workspace, saas/db)
└── Company (неявная — НЕТ сущности, «компания» = сумма файлов тенанта)
    ├── Identity: Philosophy + Constitution (два модуля, не слиты в DNA)
    ├── Brief (нетипизированный dict)
    ├── Intent (журнал, v1)
    ├── Objectives (desired state, measured_by)
    ├── Strategy (strategy.md — ТЕКСТ, не сущность)
    ├── TechDesign (tech_design.md — ТЕКСТ)
    ├── Milestones (вехи — производный индикатор)
    ├── Project (активный + история, left_behind)
    │   └── Task {id, role, deps, done_criterion, status, attempts,
    │             acceptance, tier, project, assignee}
    ├── Departments (org) → Workers (registry: role, desk, status)
    ├── Events (домен) / Decisions (журнал) / Lessons / Knowledge (факты)
    ├── Artifacts: workspace/ (файлы) + Sites + Leads  ← реестра НЕТ
    └── Costs / Limits / Autonomy / Trust
```

**Отсутствуют** (по глоссарию BOS §1): **Company** как сущность; **Strategy** как читаемая машиной структура (сейчас markdown, который режется `[:1500]` в промпты); **Capability**; **Workflow**; **Artifact-реестр** (файлы есть, владельца-проекта и ревизий у них нет); **Metrics** (временные ряды); **Gap**; **Relationships**; **History** как единая сущность (размазана: trace + state + decisions + intents). **Лишние/сомнительные:** `hr.py` (мёртвый модуль), `agent_inbox` (полуживой — только чат), `board.py`/`trust.py` — UX-механики, живущие как отдельные домены, хотя BOS §11 велит им быть view поверх данных ядра.

**Приоритет:** средний — дерево достраивать по мере ядра, но **Strategy как структура** и **Artifact-реестр** нужны раньше остальных (на них завязаны Prompt Builder и мьютексы).

## 3. World Model

**Как сейчас.** `world.py` — честный **SSOT-агрегатор**: собственных данных не хранит, читает 15 модулей-источников, отдаёт `snapshot()`, `diff()`, журнал срезов и `context_block()` для CEO. Это ровно та архитектура, что в BOS §4, — но только читающая проекция.

**Что уже SSOT (в JSON тенанта):** бриф, план, проекты, objectives, intents, события, знания, уроки, расход, автономия, конституция/философия, доска агентов, треды, лиды, сайты.

**Что живёт в промптах и только в них:** стратегия и ТЗ (тексты, интерпретируемые заново каждым потребителем); бизнес-правила CEO/лидеров/архитектора (см. раздел «знание в тексте» ниже); критерии качества критика.

**Что живёт в памяти процесса (нарушение SSOT §4):** futures вопросов (`questions._pending`), watchdog (`loop._thinking_since/_agent_task/_model_fail_count`), анти-циклы лидеров (`_last_leader_sig`), текущая веха для атрибуции (`_current_ms`), кеш JSON (легально), `_office_tasks`. Рестарт сервера теряет: ожидающие вопросы (futures) и таймеры — частично компенсировано `reset_stuck_statuses`.

**Вердикт: World Model существует как витрина, но не как хранилище.** Metrics с пометкой источника (`факт`/`оценка`) — нет вовсе; экономика (лиды × чек) не считается.

**Приоритет:** высокий для Metrics (без них нет Gap Analysis — вся зрелая половина BOS §3 заблокирована), средний для выноса живости.

## 4. Prompt Architecture

**Полная карта мест, где строятся промпты** (это исчерпывающий список):

| Кто | Где | Через Builder? |
|---|---|---|
| Воркеры (developer/designer/…) | `prompt_builder.build()` + `task_context()` | ✅ да, с логом в prompts.jsonl |
| Консультация `ask_colleague` | `agent_factory._handle_ask_colleague` — руками: `roles.render + brief_block + хвост` | ⚠️ частично (использует куски билдера) |
| CEO `decide_company` | `orchestrator._COMPANY_SYSTEM` — хардкод-литерал | ❌ |
| CEO `plan_tasks` / `plan_milestones` | `_PLAN_SYSTEM` / `_MILESTONES_SYSTEM` — литералы | ❌ |
| CEO-триаж чата | `_DIRECTIVE_SYSTEM` — литерал | ❌ |
| Лидеры отделов | `leaders._LEADER_SYSTEM + _ROLE_DESC + _DEPT_HINTS` | ❌ |
| Ресёрчер / Стратег / Архитектор | свои `SYSTEM_PROMPT` в модулях | ❌ |
| Онбординг | `onboarding._QUESTIONS_SYSTEM/_BRIEF_SYSTEM` | ❌ |
| Личный чат с агентом | `chat.ROLE_SYSTEM` — **параллельная копия ролей** | ❌ |
| Критик (LLM-ревью) | `critic.review_site_llm` — литерал | ❌ |
| Совет директоров / инициативы | `_BOARD_SYSTEM` / `_INITIATIVE_SYSTEM` | ❌ |

**Путь промпта воркера** (эталонный): `build()` = роль (.md) → 3 политики (.md) → бриф (единый сериализатор с подписью goal≠niche) → память клиента → каталог скиллов роли; `task_context()` = niche/audience → цель → веха → отдел → задача → ТЗ `[:3000]` → knowledge retrieval → уроки → формат. Логируется целиком. **Это лучший фрагмент системы.**

**Не соответствует BOS §7:** «весь промпт собирает Builder» выполнено для ~40% вызовов по количеству мест (но для большинства токенов — воркеры самые дорогие). Роли продублированы в `chat.ROLE_SYSTEM`. `leaders._ROLE_DESC` дублирует `roles.ROLE_META`.

**Что менять.** Перевести CEO/лидеров/чат на слоты билдера; убить обе дубли-копии ролей. **Приоритет: высокий** — это дешёвый и большой прирост зрелости, класс багов «подписал goal тут, забыл там» закрывается по построению.

## 5. Decision System

**Детерминированно решается** (и это правильно по BOS §6/§8): маршрутизация задач по отделам/ролям; мьютекс сайта; найм под задачу; эскалация приёмки (3 провала → блок); watchdog; авто-публикация; бюджетные гейты (цикл + предварительная оценка); capability-гейт плана; автостарт tech-отдела; закрытие blocker-событий при разблокировке.

**Через LLM:** структура компании (decide_company — open/close/delegate по гейту раз в 3 цикла); генерация плана и вех; триаж сообщений владельца; LLM-ревью сайта; инициативы; совет директоров. Плюс LLM-путь лидеров — но он живёт **только до генерации плана** (реликт).

**Нигде не описано** (дыры): решение «перепланировать» — план генерируется один раз, дальше только add_task; решение «приобрести способность» (BOS §5) — гейт лишь сообщает о нехватке; торговля Intent↔Objectives (§2) — конфликт не вычисляется.

**Не соответствует BOS §1/§9:** Decision — НЕ транзакция над планом. `decide_company` меняет оргструктуру напрямую, `interpret_directive` пишет задачи напрямую; Sandbox-проверок нет вообще, diff плана не вычисляется. `decisions.py` — журнал для UI «Почему?», а не механизм.

**Приоритет:** средний. Сначала Metrics/Measurement — Decision Engine без данных всё равно останется «интуицией CEO».

## 6. Planning

**Как сейчас.** План рождается один раз на bootstrap: LLM (`plan_tasks`, ≤7 задач, роли из белого списка) с детерминированным фолбэком (`_fallback_plan` — эвристики по словам цели). Далее задачи добавляются: делегированием агентов (`delegate_task`), триажем директив владельца, инициативами, финальной верификацией (fix-задачи). Нормализация ролей (`_ROLE_REMAP`), чистка битых deps, дедуп по названию+роли — детерминированные и хорошие.

**Это Planning Engine или эвристики?** Честно: **исполнение плана — движок** (готовность по deps, параллелизм отделов, мьютекс артефакта, попытки, блокировки — настоящая машина состояний). **Порождение плана — одноразовый LLM-вызов плюс эвристики.** Перепланирования нет: если план перестал вести к цели, офис этого не узнает — нет петли Measurement→Gap→replan.

**Не соответствует BOS §12:** artifacts-декларации у задач отсутствуют (вместо них — слова в заголовках, см. `touches_site`); Planning Engine не вынесен из loop.py.

**Приоритет:** artifacts-декларации — высокий (закрывают целый класс словесных эвристик), replan — после Measurement.

## 7. Execution — жизненный цикл задачи

Полный путь (все переходы, как есть в коде):

```
Появление: plan_tasks | _fallback_plan | add_task(делегат/директива/инициатива/fix)
   → pending
Готовность: deps ⊆ done∪skipped  → ready_for_department
Маршрутизация (_run_leaders, без LLM): свободный worker роли? → assign
   | роли нет в отделе → hire + assign | все заняты → wait
   → in_progress (assignee, синхронно ДО корутины — от двойного ассайна)
Исполнение (_job): Execution Policy (модель по задаче, оценка $)
   → бюджетный гейт (would_exceed → пауза офиса + revert)
   → prompt_builder → llm.run_agent (tool-loop, маскирование старых observations,
     инкрементальный учёт $) → [для сайта: критик + ≤2 доработки + автопубликация]
Приёмка (acceptance.check): L5 непустая сдача → L2 build (файлы ЭТОЙ задачи)
   → L3 functional (сайт/бот)
   ├── passed → done (+вердикт в задачу)
   └── fail → revert → pending (attempts+1, last_feedback в задачу)
        └── attempts ≥ 3 → blocked (+blocker-событие с task_id,
                                    +сообщение в личный чат CEO)
Разблокировка: POST /api/task/{id}/unblock → pending (attempts=0,
   blocker-событие закрывается) 
Аварийные: watchdog >240с (кроме ожидания ответа клиента) → revert,
   либо сайт готов и без критических → done через мини-приёмку
Снятие: роль без отдела → skipped (deps удовлетворяет, в done не врёт)
Ошибка LLM → revert; quota → пауза офиса; битая модель ×2 → сброс на дефолт
```

**Хорошо:** цикл замкнут, каждое ребро появилось как ответ на реальный прод-баг и задокументировано. **Плохо:** всё это живёт в одной функции `_job` на ~140 строк внутри `_assign`; статусная машина нигде не описана декларативно. **Приоритет:** средний (рефакторинг при расслоении loop.py).

## 8. Acceptance

**Честный ответ: это уже Acceptance, а не «код написан», — но на 3 уровня из 5.** L5 (непустая сдача) + L2 (build: py_compile + node --check, включая инлайн-ESM, по файлам задачи) + L3 для сайтов (критические маркеры критика, для titled-задач — всегда) — детерминированные, вердикт пишется в задачу, провал возвращает работу с фидбеком, эскалация ограничивает циклы. Финальная сдача проекта дополнительно гоняет полный критик + Playwright-рендер + LLM-ревью позиционирования.

**Что отсутствует:** L1 — спецификация собирается, но подтверждение владельца опционально и **чек-лист success_criteria не сверяется при приёмке** (checklist() существует, никто не вызывает); L3 для ботов — статический grep по коду, не «фейковые Update»; **L4 Business — нет совсем** (соответствие Objective никто не оценивает); пост-деплой мониторинг (§8: «уровни 3–5 продолжают жить») — нет.

**Приоритет:** подключить `specification.checklist()` к финальной верификации — низкая цена, высокая честность. L4 — после Metrics.

## 9. Memory

**Существующие уровни:** GLOBAL (бриф + ответы владельца + философия/конституция — читается из источников, не дублируется — правильно); DEPARTMENT (факты, потолок 60, дедуп); отдельный журнал результатов (намеренно не «знания» — хороший фикс A5); LESSONS (по ролям, 12 на роль); история чатов (12 реплик); observation masking внутри tool-loop (компрессия контекста — работает).

**Retrieval — есть**: TF-подобное перекрытие токенов + 2 зарезервированных слота под верхнюю иерархию воль. **Summary — нет** (факты режутся `[:280]`, а не сжимаются). **Decay — нет** (только FIFO-потолки; факт с ts не стареет по весу). **Confidence/source у фактов — нет** (BOS §1 Fact: «источник, сущность, уверенность» — не реализовано; есть только src-слой).

**Приоритет:** низкий-средний. Текущая память — реальный moat и работает; довести Fact до BOS-схемы стоит при переходе на sqlite/embeddings (спека: «по мере роста»).

## 10. Event System

**Есть — и после последней волны фиксов у него впервые замкнулся контракт (§10):** `raise_event(kind, task_id)` → pending → CEO видит блок событий в `decide_company` → problem/signal/info детерминированно помечаются после показа; opportunity → детерминированно конвертируются в инициативы (карточка владельцу); blocker → блокировка задачи + событие + личный чат CEO, закрывается разблокировкой задачи.

**Чего нет:** записи в History как сущность (§10: «каждое значимое событие пишется в History» — сейчас события живут в своём journal + trace, унификации нет); подписчиков, кроме CEO (отделы не реагируют на чужие события); событий измерений (нет Metrics — нечего мерить).

Это не полноценная EDA — это **event-inbox для одного потребителя**. Для текущего масштаба этого достаточно и это честно.

**Приоритет:** низкий, до появления Measurement.

## 11. Capability Layer

**Понятия Capability как сущности нет.** Есть три его осколка: `tool_router` (потребность→интеграция, с каталогом из метаданных), `skills` (потребность→плейбук, roles-фильтр), `capabilities.py` — **ложный тёзка** (это режимы качества моделей, не BOS-Capability!). Плюс статический гейт `execution_policy.missing_for_plan` (слова задачи → нужная интеграция → «подключите заранее»).

После унификации скорера (`needs.py`) нижняя половина слоя соответствует §5. **Отсутствует верхняя:** реестр «умеем/не умеем/можно приобрести», Capability-gap как решение с вариантами приобретения (установить скилл / подключить провайдера / спросить ключ / делегировать). Сейчас нехватка способности — это уведомление, а не работа.

**Отдельный долг:** имя модуля `capabilities.py` обязано быть переименовано (например, `quality_modes.py`) до создания настоящего Capability — иначе новая команда будет путаться каждый день. **Приоритет: средний.**

## 12. Providers

**Как выбирается исполнитель сегодня:** Execution Policy выбирает **модель** (оверрайды владельца > рутина→дешёвая > capability роли > дефолт); а **способ** (LLM сам / скилл / интеграция / человек) выбирает воркер в процессе работы через use_skill/use_capability/ask_user. Лестница BOS §6 реализована де-факто, но её проходит LLM, а не политика: формального выбора «эту задачу вообще не давать LLM, тут детерминированный код» на уровне задач нет (есть только на уровне подсистем — маршрутизация, критик).

**Можно ли заменить LLM?** Да, с локальным ущербом: весь трафик идёт через один `core/llm.py` (OpenAI-формат, tool-loop, таймауты, учёт) — замена провайдера = один модуль. Что придётся переписать сверх него: `costs.PRICES` (прайс привязан к apinet — Billing-provider интерфейса из §12 нет) и tool-схемы (OpenAI function-формат зашит в определения инструментов agent_factory). Промпты, план, приёмка, мир — переживут замену. **Это соответствует второму тесту BOS §0 примерно на 80%.**

**Приоритет:** низкий (осознанно отложено спекой: «не разрабатывать собственный мультипровайдерный слой»).

## 13. Business Logic

**Граница бизнес/техника сегодня проходит… по типу файла, а не по слою.** Технические решения (как собрать сайт, чем проверить) — в скиллах и критике: хорошо. Но бизнес-решения размазаны на три носителя: (1) структурированные — Constitution/Autonomy/Objectives/Philosophy — образцово; (2) **текстовые в промптах** — что нельзя (Tilda), что не выдумывать (лиды/масштабирование), кому маршрутизировать ботов — LLM может их проигнорировать, код — не может прочитать; (3) **эвристики в if-ах** — «хочет ли клиент бота» по подстрокам. Понимание бизнеса клиента = бриф (5 нетипизированных полей) + факты knowledge. Экономику бизнеса (выручка, ROI, лиды×чек) система **не понимает вовсе** — §4 требует хотя бы прокси с пометкой «оценка».

**Приоритет:** высокий — это и есть тема финального раздела про «знание в тексте».

## 14. UI

**Соответствие §11 — высокое, лучшая дисциплина в проекте.** Офис — проекция: маршрутизацию делает движок, лидер — персона; board/trust/understanding — UX поверх ядра; вкладки «Проект/Спецификация/Цели/Решения» показывают сущности BOS напрямую. Два режима («клиент»/«под капотом») фактически есть — вкладки Дашборд vs События/Знания/Трейс.

**Утечки реализации:** слово `agent` — во всех API (`/api/agents`, `agent_id`, тип `Agent` во фронте) — спека требует этого не показывать пользователю; в интерфейсных текстах уже «роли/команда» (чисто), но JSON-контракт и DOM выдают термин. Плюс `/api/knowledge`, `/api/trace` доступны без пометки «диагностика». Переименование `agent_id → worker_id` уже запланировано спекой (§12, вместе с миграцией Project). **Приоритет:** низкий — синхронизировать с той миграцией, отдельно не трогать.

## 18. Readiness (проценты и почему)

- **World Model — 45%.** Агрегатор+snapshot+diff есть (это уже больше половины идеи), но без Metrics/Artifacts/Relationships и с живостью вне мира.
- **Prompt Builder — 70%.** Эталонный для воркеров (самых дорогих потребителей), с полным логом; минус 30% за прompты мимо билдера и дубли ролей.
- **Planning Engine — 55%.** Исполнение плана — движок; порождение — одноразовое, без replan и artifacts-деклараций.
- **Decision Engine — 35%.** Решения принимаются и журналируются, но Decision ≠ транзакция-diff с проверками.
- **Acceptance — 60%.** Три детерминированных уровня в бою, эскалация, вердикты; нет L1-гейта, L4, ботов-Update.
- **Execution Policy — 55%.** Модель по задаче, cost-tier, est-cost с бюджетным гейтом, capability-гейт; лестница неформализована.
- **Project Model — 50%.** Сущность, принадлежность задач, закрытие с left_behind; один активный, без spec/метрик проекта.
- **Capability Layer — 25%.** Единый скорер + роутер + скиллы + статический гейт; сущности и «приобретения» нет.
- **Event System — 65%.** Контракт по kind замкнут детерминированно; нет History/подписок.
- **Memory — 55%.** Три слоя, retrieval, уроки, masking; нет confidence/decay/summary.
- **Intent — 40%**, **Objectives/Gap — 30%** (Gap = 0), **Sandbox — 0%**, **Measurement — 10%**, **History — 30%**, **Identity/DNA — 40%**, **Providers — 50%**, **UI-проекция — 70%**.

## 19. Roadmap

Спека определяет пятёрку ядра — она **выполнена** (PB, WM v1, Acceptance, Project, EP). Следующая стадия, в порядке зависимости, а не желания:

1. **Домиграция Prompt Builder** (CEO/лидеры/чат/критик/онбординг + удаление дублей ролей). Дёшево, закрывает целый класс багов, предусловие для «знания из текста в мир».
2. **Metrics v1 + прокси-экономика** (лиды×заявленный чек с пометкой `оценка`, счётчики визитов сайта). Без этого не существуют: Gap Analysis, L4-приёмка, честный Measurement, Steady State — половина BOS заблокирована этим одним компонентом.
3. **Artifacts-декларации задач** (план объявляет, какие артефакты трогает задача) — убивает словесные эвристики мьютекса и приёмки.
4. **Gap Analysis + перепланирование** (петля §3 замыкается).
5. **Decision=diff плана + Decision Sandbox** (snapshot/diff уже готовы — фундамент лежит).
6. Инфраструктура по росту: sqlite, вынос живости, embeddings.

**Нельзя писать, пока не готово ядро:** Sandbox Company (клон тенанта) — до Decision-diff; мультипроектность — до Metrics проекта; внешние воркеры (kind: external) — до формальной лестницы EP; любые новые UX-механики с собственной бизнес-логикой — запрещены §11 всегда.

## Знание о бизнесе, живущее только в тексте

Главная просьба аудита. Полный реестр (файл → код → почему долг → куда → сложность):

**1. [loop.py](src/office/loop.py) `_fallback_plan`** — `wants_bot = any(p in g for p in ("нужен бот", "сделай бот", ...))`. Интерпретация воли клиента подстроками. Это работа Intent-интерпретатора: результат должен жить как `Intent.interpretation.artifact_type` в журнале intents, фолбэк-план — читать его, а не парсить цель заново. **Сложность: средняя.**

**2. [execution_policy.py](src/office/execution_policy.py) `_ROUTINE_WORDS`** — `("исправ", "провер", "почин", ...)`. Классификация сложности задачи по заголовку. Должно быть: `task.tier`, выставляемый генератором плана всегда (поле уже существует — LLM его просто не заполняет; добавить в `_PLAN_SYSTEM`-схему и оставить слова фолбэком). **Сложность: низкая.**

**3. [execution_policy.py](src/office/execution_policy.py) `_TASK_CAPABILITY`** — `(("телеграм","bot"), "telegram", ...)`. Потребность задачи во внешней способности — по словам. Должно быть: `task.required_capabilities[]`, декларируемые при планировании (artifacts/capabilities-декларации BOS §12). **Сложность: средняя.**

**4. [plan.py](src/office/plan.py) `_NON_SITE_WORDS` + `touches_site`** — «какие артефакты трогает задача» выводится из роли и отсутствия слова «бот» в заголовке. Дважды ловили прод-баг именно тут. Должно быть: `task.artifacts: ["site/"]` — декларация плана, мьютекс сравнивает пути. **Сложность: средняя** (правка генератора плана + add_task + два потребителя).

Хрупко: переформулировал сообщение — потерял критичность. Должно быть: критик возвращает структуру `{code, severity, text}`; маркеры-строки исчезают. **Сложность: средняя** (меняется контракт критика, 5 потребителей).

**8. ## Финал — три ответа

**1. Насколько AI-Office уже ЯВЛЯЕТСЯ BOS?**
**~45%.** Взвешенно по компонентам: кибернетический цикл реализован в «интуитивном» полукруге (Intent → Plan → Execution → Acceptance — работает и детерминирован в ключевых местах), но **измерительный полукруг** (Metrics → Gap → Priorities → replan) отсутствует как класс, Sandbox — 0%, Decision — журнал вместо транзакции. Система сегодня — это честный **Bootstrapping-режим BOS** (§3, intent-driven) с выполненной пятёркой ядра — и НЕ является Steady-State BOS даже частично.

**2. Можно ли начинать масштабную разработку?**
**Нет — с одним уточнением.** Фичи поверх ядра (новые интеграции, скиллы, UI-режимы) — можно и параллельно: слои развязаны, точки расширения (skills/.md, integrations/registry) чистые. Масштабную разработку **доменной логики** — нельзя, пока: (а) все промпты не пройдут через Builder, (б) не появятся Metrics, (в) не расслоён loop.py. Иначе каждая новая фича будет добавлять словесные эвристики — долг растёт быстрее ядра.

**3. Какой следующий шаг даст наибольший прирост зрелости?**
**Metrics v1 + типизированный Brief (пункт 16 выше) — одним ходом.** Это единственный компонент, который разблокирует сразу четыре: Gap Analysis, L4-приёмку, Measurement-петлю и осмысленный Decision Engine. Всё остальное ядро уже стоит и ждёт данных: snapshot/diff готовы, Objectives с measured_by готовы, projects.left_behind готов — им всем не хватает именно чисел о бизнесе. Прирост зрелости: с ~45% до ~60% одним компонентом, потому что он превращает «офис, выполняющий поручения» в «систему, сравнивающую желаемое с действительным» — а это и есть определение BOS из §0.
