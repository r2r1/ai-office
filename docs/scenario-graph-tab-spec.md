# Спека: вкладка «Сценарии» — живая диаграмма оргструктуры и потока работы

*Продуктовая+техническая спецификация для отдельной сессии реализации. Не билдим
сейчас — по решению из обсуждения (2026-07-04): сначала спека, разработка отдельным
заходом. Отвечает на вопрос «что строить», не «как выглядит финальный UI».*

---

## 0. Что показываем (решено в обсуждении)

**Не** план-граф задач (`plan.json`) как таковой — он уже показан во вкладке
«Проект» линейным списком с зависимостями. Дублировать его как граф без нового
смысла бессмысленно.

**Показываем оргструктуру + живой поток работы:**

```
CEO (orchestrator)
 ├── Технический отдел (CTO) ──┬── developer_1 [🔴 думает: t4]
 │                              ├── integrator_1 [🟢 свободен]
 ├── Отдел маркетинга (CMO) ───┴── marketer_1 [🔴 думает: t7]
 └── Отдел продаж (не открыт)
```

Узлы — **компания → отделы → сотрудники** (не задачи). Рёбра — иерархия
подчинения + (опционально, второй слой) стрелки `delegate_task`/`ask_colleague`
между узлами за последние N минут, чтобы был виден не только статичный штат, но
и кто кому реально передал работу только что.

Каждый узел «сотрудник» несёт текущий статус (`🔴 думает` / `🟢 свободен` /
`⏸ заблокирован`) и id текущей задачи, если есть — клик открывает её детали, не
превращая диаграмму в дублирующий план-граф.

## 1. Источники данных (уже существуют, ничего нового собирать не нужно)

| Что на диаграмме | Откуда |
|---|---|
| CEO, отделы, статус (открыт/закрыт) | `office/org.py` (`catalog()`, `open_departments()`, `state_of()`) |
| Сотрудники отдела | `office/registry.py` (`all_agents()`, `members_of()`) |
| Текущая задача сотрудника | `office/plan.py` (`assignee == agent_id`, `status in (pending,in_progress)`) |
| Последний результат/статус | `office/state.py` (`result_for`), `registry` (`.status`) |
| Недавние delegate/ask рёбра | `office/trace.jsonl` (`assign`/`tool=ask_colleague` записи за последние ~15 мин) |
| Блокеры/вопросы к агенту | `office/questions.py` |

Ничего не требует новой модели данных — это агрегирующая проекция существующего
состояния, ровно как `world.snapshot()` уже агрегирует world model для других
целей.

## 2. Новый backend

### 2.1 `GET /api/org-graph`
Единая точка, отдающая nodes+edges одним запросом (не 5 отдельных вызовов с
фронта — иначе диаграмма мигает при каждом poll).

```json
{
  "nodes": [
    {"id": "ceo", "type": "ceo", "label": "orchestrator_1", "status": "idle"},
    {"id": "dept:tech", "type": "department", "label": "Технический отдел",
     "status": "open", "objective": "..."},
    {"id": "agent:developer_1", "type": "agent", "role": "developer",
     "label": "developer_1", "status": "thinking", "task_id": "t4",
     "task_title": "Реализовать сайт..."}
  ],
  "edges": [
    {"from": "ceo", "to": "dept:tech", "kind": "manages"},
    {"from": "dept:tech", "to": "agent:developer_1", "kind": "member"},
    {"from": "agent:marketer_1", "to": "agent:developer_1", "kind": "delegated",
     "ts": 1783188120.9, "task_id": "t4"}
  ]
}
```

Обновление — тот же SSE-канал `/events`, что уже питает остальной UI (не новый
poll-луп): достаточно, чтобы существующие `agent_start`/`task_done`/`hired`/
`assign` события триггерили refetch графа на фронте (дешёво — граф маленький,
обычно <20 узлов на тенанта).

### 2.2 Write-действия по клику (решено: не read-only, а управление узлом)

Три действия, все — тонкие обёртки над уже существующей логикой, не новая:

| Действие | Узел | Backend |
|---|---|---|
| Переназначить задачу другому свободному сотруднику той же роли | agent (с активной задачей) | **Новый** `POST /api/task/{id}/reassign {assignee}` — валидация: новый assignee свободен и той же роли, иначе 409 |
| Поставить конкретного агента на паузу | agent | **Новый** `POST /api/agent/{id}/pause` / `/resume` — сейчас пауза только глобальная (`control.pause()` на весь офис); нужен per-agent флаг в `registry.py` (агент не берёт новых задач, лидер видит его как занятого, не переназначает) |
| Написать агенту напрямую | agent | Уже есть — `POST /api/ask` (тот же путь, что личные чаты вкладки «Чаты»), диаграмма просто открывает существующий thread UI поверх узла, не новый канал |

`pause` на уровне агента — единственный кусок с реальной новой доменной логикой
(остальное — переиспользование). Он логичен как отдельная примитива: сейчас
единственный способ «притормозить одного сотрудника, не всю компанию» —
отсутствует.

## 3. Frontend

- Новая вкладка `app/views/ScenarioView.tsx`, рядом с существующими `app/views/*`.
- Библиотека графа — не писать force-layout руками: `reactflow` (react-flow) —
  уже стандарт для node-link диаграмм в React-экосистеме, лицензия MIT, простая
  интеграция с кастомными нодами (нужны для статус-индикаторов/иконок ролей).
- Кастомные ноды переиспользуют `data/roles.ts` (иконки/цвета ролей — уже
  используются в `TopBar`/`OfficeView`), не изобретают вторую палитру.
- Клик на узел → боковая панель (`Sheet`/`Drawer`, как в `FileExplorer.tsx`) с
  деталями + кнопки действий из §2.2.
- Layout — иерархический (dagre-подобный: CEO сверху, отделы посередине,
  сотрудники снизу), не физический force-graph — предсказуемость важнее
  «живости» для бизнес-пользователя, который должен читать оргструктуру, а не
  распутывать её.

## 4. Что сознательно НЕ входит в первую версию

- Полный план-граф задач как часть диаграммы — остаётся в «Проект» (иначе два
  представления одних данных разъедутся, ровно как раньше разъехались milestones
  и plan.json).
- History/Decision timeline на диаграмме — это `observability.timeline()`
  (Phase 0.5 дорожной карты), отдельная вкладка «Трейс», не сюда.
- Retry/rewind (изменить прошлое решение) — не write-примитив уровня MVP, это
  требует Decision Engine как diff (Phase 5), которого пока нет.

## 5. Порядок реализации (для следующей сессии)

1. `GET /api/org-graph` (backend, без UI) — можно проверить curl'ом.
2. `POST /api/agent/{id}/pause|resume` + флаг в `registry.py`
   (`planning_engine`/`leaders.decide` должны видеть paused-агента как занятого,
   не предлагать ему задачи).
3. `POST /api/task/{id}/reassign`.
4. Frontend вкладка с react-flow, статичный рендер графа.
5. Клик → панель деталей → кнопки действий, подключённые к 2-3.
6. SSE-триггер refetch (последним — чтобы не отлаживать реалтайм поверх ещё
   нестабильного графа).
