# Дорожная карта до идеального BOS

*Обновлено 2026-07-03 по итогам ревизии с техническим директором. Версия v2:
добавлена ось User Value, реордер фаз (Capability+Artifacts перед Measurement,
Acceptance L1 вплотную к Prompt Builder), новая Phase 0.5 (Observability),
Metrics переименован в Measurement Layer, Sandbox переосмыслен как
универсальный механизм, добавлен документируемый горизонт Phase X.*

Это не список пожеланий, а два наложенных друг на друга графа: зависимости
(что можно строить только после чего) и ценность (что почувствует владелец
бизнеса между релизами). Всё привязано к уже утверждённой `bos-architecture.md`
— новых сущностей нет, только порядок реализации того, что в ней описано.
Свод неизменяемых правил, которым подчиняется вся работа ниже — см.
`docs/engineering-principles.md`.

---

## Принцип секвенирования

Три правила, определяющие порядок:

1. **Measurement раньше Gap, Gap раньше Decision-as-diff.** Без чисел о
   бизнесе Gap Analysis нечего анализировать; без Gap Decision Engine нечего
   решать — он продолжит быть «интуицией CEO» с журналом вместо транзакции.
2. **Capability и Artifacts — планирование, а не steady-state.** Цепочка
   `Task → Capability → Provider → Execution` первична: проверка «умеем ли
   мы это» должна происходить ДО того, как Execution Policy начнёт выбирать
   модель. Ставить их после Gap Analysis (как в первой версии карты) было
   ошибкой порядка.
3. **Trust раньше Scale.** Acceptance L1 (чек-лист спецификации) не имеет
   зависимостей и стоит дёшево — поднимается вплотную к Prompt Builder, а не
   ждёт своей очереди за Measurement. L4 (Business Acceptance) технически не
   может подняться так же высоко: оценить попадание в цель без числа этой
   цели нельзя — это математика, не приоритет.

Гигиена (Phase 0) не блокирует ничего и не блокируется ничем — делается
первой неделей параллельно с планированием остального.

## Ось User Value

Каждая фаза дальше маркирована по двум осям:

- **Архитектура** (⭐ 1–5) — насколько компонент критичен для соответствия
  BOS и разблокировки следующих фаз.
- **Пользователь ощущает** (✅ прямо / ⚠️ косвенно / ❌ невидимо) — почувствует
  ли владелец бизнеса эту фазу между релизами, не читая код.

Сводная таблица — в конце документа. Без этой оси проектная работа рискует
стать бесконечной полировкой ядра, которую никто снаружи не увидит.

## Phase 0.5 — Observability (1–1.5 недели, сразу за Phase 0)

Существующие журналы (`trace.jsonl`, `prompts.jsonl`, `world.diff()`,
`decisions.py`) уже покрывают почти всё, что нужно — фаза не создаёт
логирование с нуля, а **сшивает** разрозненные записи в одну временную шкалу
с перекрёстными ссылками. Обоснование приоритета: диагностика зависания на
ресёрчере (реальный инцидент этого проекта) была сделана ровно через
`trace.jsonl` — это доказывает, что наблюдаемость и есть первичный
инструмент отладки, и без неё дальнейшая миграция (Phase 1) идёт вслепую.

- Каждая запись `trace.log(...)` получает опциональную ссылку на
  `prompt_id`/`decision_id`, которые её породили.
- Единая точка чтения (`observability.timeline(tenant, from, to)`),
  объединяющая trace + prompts + decisions + world-снапшоты по времени.
- UI: существующие вкладки «События»/«Трейс» переиспользуют этот API вместо
  прямого чтения `trace.jsonl`.

**Definition of Done:** по `decision_id` из `/api/decisions` можно получить
полную цепочку — промпт, который его вызвал, trace-записи исполнения,
world.diff до/после — одним запросом.

**Архитектура:** ⭐⭐⭐⭐ · **Пользователь ощущает:** ❌ (видно только команде
при разборе инцидента)

## Phase 1 — Prompt Builder (полное покрытие) + Acceptance L1 (2–3 недели)

Две задачи объединены в одну фазу: обе дёшевы, обе про доверие к системе, ни
одна не имеет внешних зависимостей.

### 1a. Prompt Builder — полное покрытие

Мигрировать в `prompt_builder.py` всё, что сейчас строит промпт руками:
`orchestrator._COMPANY_SYSTEM/_PLAN_SYSTEM/_MILESTONES_SYSTEM/_DIRECTIVE_SYSTEM`,
`leaders._LEADER_SYSTEM`, `researcher/strategist/architect.SYSTEM_PROMPT`,
`onboarding._QUESTIONS_SYSTEM/_BRIEF_SYSTEM`, `critic.review_site_llm`
system, `_BOARD_SYSTEM/_INITIATIVE_SYSTEM`.

**Как мигрировать без переписывания логики:** каждый System-литерал
становится файлом `office/policies/<name>.md` или получает свой слот в
`build()`/новую функцию `builder.company_context(role="ceo"|"leader"|...)`.
Цель — не переписать тексты, а чтобы:
- у CEO/лидеров/архитектора появился тот же слот **Brief** (единственный
  сериализатор goal≠niche), который сегодня есть только у воркеров;
- **каждый** промпт логировался в `prompts.jsonl` — сейчас это работает
  только для воркеров, решения CEO отлаживаются вслепую.

**Definition of Done:** `grep -rn "SYSTEM = \"\"\"" src/agents src/office` не
находит промпт-литералов вне `prompt_builder.py`/policies; в `prompts.jsonl`
появляются записи с `role="orchestrator"`/`role="cto"` наравне с воркерами.

### 1b. Acceptance L1 — чек-лист спецификации

`specification.checklist()` уже существует и возвращает `success_criteria`
из плана — просто ничего не читает его при приёмке. Подключить
`acceptance.check()` к проверке деклараций спецификации; статус
`specification.status` («draft»/«confirmed») учитывается как модификатор
уверенности приёмки, не как жёсткий гейт (v1 подтверждения владельца
остаётся опциональным по дизайну спеки).

**Definition of Done:** задача, чьё `done_criterion` явно расходится с
`specification.success_criteria`, получает предупреждение в вердикте
приёмки, даже если build/functional прошли.

**Архитектура:** ⭐⭐⭐⭐⭐ · **Пользователь ощущает:** ⚠️ (косвенно — меньше
«сайт продаёт не то, что нужно» багов, но не отдельная видимая фича)

**Приоритет: высокий.** Дешёвая работа с большим приростом честности — первая
содержательная фаза после гигиены.

## Phase 2 — Capability + Artifacts как единая сущность (3–4 недели, частично параллельно с Phase 1)

Объединены намеренно: Capability отвечает «умеем ли мы производить артефакт
такого типа», Artifact — «что конкретно произведено» — два конца одной связи,
разносить их по разным фазам означало бы проектировать половину контракта
вслепую.

### 2a. Artifact как полноценная сущность

Сегодня артефактов-как-сущности нет вообще (только файлы в `workspace/` +
отдельно `sites.json` + отдельно `leads.json`, без реестра и без владельца).
Схема (глоссарий BOS уже определяет Artifact как «продукт с владельцем-
проектом»):

```
Artifact {
  id, type,            # "site" | "bot" | "doc" | ...
  owner_project,        # projects.id
  status,                # draft | published | deprecated
  created_by,            # task.id
  depends_on: [...],     # другие Artifact.id
  produced_by: [...],    # task.id[] (может обновляться несколькими задачами)
  consumed_by: [...],    # task.id[], читавшие/использовавшие артефакт
}
```

- `plan.py`: схема задачи `+= artifacts: list[str]` (декларация того, что
  задача произведёт/тронет) — заполняется генератором плана и
  `_fallback_plan` (он и так знает, бот это или сайт — просто не пишет).
- **Замена словесных эвристик одна за другой:**
  - `plan.touches_site` читает `artifacts`, не `_NON_SITE_WORDS` — мьютекс
    сайта перестаёт зависеть от формулировки заголовка (дважды пойманный
    прод-баг).
  - `acceptance._is_site_task/_is_bot_task` читают `artifacts`.
  - Критик получает структурный контракт: `check_site()` возвращает
    `list[{code, severity, text}]` вместо строк; `_CRITICAL_MARKERS`-
    подстроки исчезают.

### 2b. Capability как реестр

- Новый `office/capability.py`: `{capability_id: "tiktok_publishing", status:
  "have"|"missing"|"acquiring"}` — источник: пересечение каталога
  `skills`+`integrations.registry` (что реально умеем) с тем, что требует
  план (`required_capabilities` — то же происхождение, что `artifacts`).
- `execution_policy.missing_for_plan()` перестаёт быть просто уведомлением —
  становится решением «приобрести способность» с вариантами из §5
  (установить Skill | подключить Provider | ask_user | делегировать).

**Definition of Done:** `grep -n "_NON_SITE_WORDS\|_SITE_WORDS\|_BOT_WORDS\|_CRITICAL_MARKERS" src/office/*.py`
пуст; `GET /api/capabilities` отдаёт реестр умений компании (не режимы
качества моделей — то имя освобождено в Phase 0); недостающая интеграция в
плане видна как явное решение, а не строка в ленте.

**Архитектура:** ⭐⭐⭐⭐ · **Пользователь ощущает:** ⚠️ (меньше «а почему он не
смог» сюрпризов — косвенная, не прямая фича)

## Phase 3 — Measurement Layer (2–3 недели, зависит от Phase 2)

*Переименовано из «Metrics»: BOS §3 называет этот шаг цикла именно
«Measurement», и периметр шире одних чисел — включает события, стоимость,
время выполнения, KPI. Физической консолидации существующих файлов
(`trace`/`costs`/`events`) в один стор не требуется — это логический слой
чтения поверх них, не переписывание хранилищ.*

Зависит от Phase 2, потому что Artifact даёт владельца (`owner_project`),
без которого метрика «привязана к чему» повисает в воздухе.

### 3a. Типизированный Brief

`onboarding.build_brief_structured`: поле `revenue` перестаёт склеиваться в
строку `assets` — разбить на `budget_usd: float`, `avg_check_usd: float` (с
best-effort парсингом существующих текстовых ответов, `None` если не число).
Существующие тенанты без числовых полей получают `None` — не блокирует
работу, просто нет прокси-экономики до следующего ответа клиента.

### 3b. Measurement v1

- Новый `office/metrics.py`: временные ряды `{metric_id, value, source:
  "факт"|"оценка", artifact_id, ts}` — хранилище по паттерну проекта,
  `data/tenants/<tid>/metrics.json`, append + потолок.
- Источники: `leads.count()` (факт), `leads.count() × brief.avg_check_usd`
  (оценка — прокси выручки), счётчик визитов сайта (факт, если появится).
- Автоматический Objective «Заявки в неделю» с реальным
  `measured_by="leads.count() за 7 дней"` создаётся при первой публикации
  сайта — `objectives.unmeasurable()` перестаёт быть пустой декларацией.
- `world.snapshot()` получает раздел `metrics` (сейчас его нет вовсе).

**Definition of Done:** `GET /api/world` содержит непустой `metrics` для
тенанта с хотя бы одним лидом; `objectives.measurable()` возвращает ≥1
запись без ручного создания владельцем.

**Архитектура:** ⭐⭐⭐⭐⭐ · **Пользователь ощущает:** ⚠️ (владелец видит числа,
но ещё без выводов из них — это следующая фаза)

**Приоритет: высочайший.** Без этой фазы Gap Analysis и L4-приёмка физически
нечем питать.

## Phase 4 — Gap Analysis + перепланирование + Acceptance L4 (2–3 недели, после Phase 3)

Замыкает измерительный полукруг кибернетического цикла (§3) — до этой фазы
система является честным Bootstrapping-режимом и не более.

- Новый `office/gap.py`: `compute() -> list[Gap]` — для каждого
  `objectives.measurable()` сравнивает `current_value` (из Measurement) с
  `desired`; вычислимая разница, не «ощущение CEO».
- `world.context_block()` получает раздел «Разрывы» — CEO видит их наравне с
  блокерами.
- **Перепланирование:** план выполнен, но `gap.compute()` непуст → вместо
  «жду указаний» CEO получает gap-и в `decide_company` и сам решает открыть
  отдел/создать задачу под конкретный gap (детерминированный маппинг
  «gap по заявкам» → задача marketer/salesman, тот же принцип, что в
  `_fallback_plan`).
- Переход Bootstrapping→Steady State из таблицы §3: как только у компании
  есть ≥1 measurable objective, `_bootstrap()` перестаёт быть единственным
  источником работы.
- **Acceptance L4** (Business): вердикт приёмки сверяется с ближайшим
  Objective через Gap — «сделано» начинает означать «двигает к цели», а не
  только «код собирается и форма шлёт заявки».

**Definition of Done:** тенант с закрытым планом и Objective «10
заявок/неделю» (metrics показывают 3) получает новую задачу от CEO без
вмешательства владельца; переход Bootstrapping→Steady State воспроизводится
в демо.

**Архитектура:** ⭐⭐⭐⭐⭐ (Gap) / ⭐⭐⭐ (L4) · **Пользователь ощущает:** ✅
(офис сам находит следующую работу к цели — это уже видимый продукт, не
инфраструктура)

**Приоритет: высокий, строго после Phase 3** — раньше нечего сравнивать.

## Phase 5 — Decision Engine как diff + Sandbox-механизм (3–4 недели, после Phase 4)

Сейчас `decide_company`/`interpret_directive` меняют мир напрямую;
`decisions.py` — журнал для UI «Почему?», а не механизм. Единственное
серьёзное несоответствие инварианту §14 п.3.

- `decisions.py`: каждое решение выражается как `PlanDiff {add_tasks,
  remove_tasks, milestone_ops, dept_ops}` — структура уже частично
  существует в `interpret_directive`, просто не унифицирована.
- **Sandbox строится как универсальный механизм, не как фича Decision.**
  BOS §9 прямо описывает его как `clone → check → merge/discard` над «любым
  предметом (код, стратегия, цены, бюджет, найм)». Интерфейс —
  `sandbox.run(subject, change, checks) -> Result` — Decision становится
  первым потребителем, но не единственным зашитым случаем.
  - Decision Sandbox: `snapshot = world.snapshot()` → применить diff к копии
    → детерминированные проверки (бюджет через `costs.would_exceed`,
    конфликт артефактов через Phase 2, вето Конституции через
    `constitution.override_for`) → merge или discard с объяснением.
  - LLM участвует только как один из чекеров с пометкой «оценка» — вето
    дают детерминированные проверки.
  - Sandbox Company (клон тенанта) — НЕ строить в эту фазу: не потому что
    механизм плох, а потому что сегодня нет конкретного потребителя
    (skill-разработка, A/B ветвление стратегии). Механизм готов принять
    такого потребителя, когда он появится — не строим ради полноты.

**Definition of Done:** директива владельца из чата проходит через
`Decision.propose() → Decision.check() → Decision.apply()|reject()`, не
пишет план напрямую; отклонённое решение (напр. превышающее бюджет) видно в
`/api/decisions` с причиной отказа.

**Архитектура:** ⭐⭐⭐⭐ · **Пользователь ощущает:** ⚠️ (видно только когда
решение отклонено с объяснением — иначе невидимо)

## Phase 6 — Execution Policy на Capability + расслоение loop.py (2–3 недели, параллельно с Phase 5)

Организационная фаза — низкий риск, если делать после Phase 2/4 (иначе
рефакторинг тащит строковые эвристики в новую структуру).

- Execution Policy окончательно читает цепочку `Task → Capability →
  Provider` вместо остатков `_TASK_CAPABILITY`-слов.
- `office/planning_engine.py` — маршрутизация по отделам, мьютекс (на
  `artifacts`), готовность по deps, capability-гейт.
- `office/execution.py` — жизненный цикл `_job` (Policy → бюджетный гейт →
  run_agent → приёмка → эскалация) как отдельная машина состояний.
- `loop.py` остаётся тонким шедулером: цикл, пауза, watchdog,
  bootstrap-оркестрация.
- Заодно, если файлы уже открыты: терминология `agent_id → worker_id`
  (backend с deprecated-алиасом 1–2 релиза; frontend `webapp/src/data/roles.ts`
  тип `Agent → Worker`) — спека привязывает эту миграцию к Project-этапу
  (уже сделан), дешевле совместить, чем выделять отдельный спринт.

**Definition of Done:** `loop.py` < 400 строк; `planning_engine.py`/
`execution.py` имеют собственные unit-тесты без поднятия полного цикла.

## Phase X — Learning Engine (не в графике, только документируется)

BOS не заканчивается на Gap Analysis. Принцип №2 §3 («непрерывная
ответственность»: deploy → monitoring → measurement → авто-инициативы) уже
указывает на горизонт за Steady State: компания, которая сама корректирует
**Strategy** на основе накопленных Decision-исходов и трендов Measurement —
не просто закрывает gap-и по одному, а меняет курс.

Это **не задача для реализации** сейчас — и не должна ей стать до появления
накопленной истории Decision/Measurement, на которой Learning Engine мог бы
чему-то учиться (данных пока физически нет). Пункт существует, чтобы roadmap
не выглядел так, будто BOS — это Gap Analysis и точка.

## Инфраструктура роста (фоном, без фазы и дедлайна)

Спека сама формулирует триггеры (§13) — не делать заранее:

| Что | Триггер |
|---|---|
| sqlite вместо JSON-файлов тенанта | первые десятки живых клиентов (сегодня — единицы) |
| embeddings retrieval вместо TF-перекрытия | `knowledge.json` регулярно упирается в потолок 60 фактов |
| Вынос живости (futures/watchdog) из памяти процесса в мир | переход на multi-worker/multi-process деплой (сегодня — один процесс) |
| Воркеры-процессы вместо asyncio.Task | нагрузка одного процесса становится бутылочным горлышком |

Держать список на виду — иначе «вынос живости» откладывается бесконечно,
хотя это прямое нарушение SSOT (принцип №2 `engineering-principles.md`).

молча ломать детерминированные гарантии друг у друга).

## Итоговое определение «идеального результата»

Проект становится полноценным BOS, когда:

1. Каждый компонент из таблицы Readiness (`docs/bos-architecture.md` §12/§18
   аудита) ≥ 80%, кроме Sandbox Company и Relationships — по спеке они
   остаются точками расширения, не обязательными для зрелости.
2. Оба полукруга кибернетического цикла (§3) замкнуты и наблюдаемы:
   `world.snapshot()` до/после решения показывает реальный diff, а не только
   факт «что-то поменялось».
3. Ни один system-промпт не собирается руками вне `prompt_builder.py`.
4. Ни одна бизнес-эвристика не определяется подстрокой в русском тексте там,
   где решение меняет мир (маршрутизация, мьютекс, приёмка, capability-гейт)
   — только там, где текст сам является легитимным вводом (LLM-генерация
   плана, диалог с клиентом), это нормально.
5. Второй тест архитектуры из §0 («убрать LLM — что переписать») проходит на
   ≥90%: сегодня ~80%, разрыв — Billing-provider интерфейс и tool-схемы в
   OpenAI-формате.

При параллелизации 20 разработчиками по графу выше — это реалистично на
**10–12 недель** до состояния, соответствующего собственной архитектуре BOS
на заявленном уровне зрелости Steady-State компании, а не на текущих ~45%.

**Решение технического директора (2026-07-03):** архитектурная стадия
закрыта. Фундаментальные изменения заморожены до появления конкретной
практической причины их пересматривать. Дальше — Phase 0.
