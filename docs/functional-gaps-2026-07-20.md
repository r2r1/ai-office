## P0 — пользователь физически не может завершить обещанный сценарий

### ❌ 1. На мобильном viewport нет доступа к чату вообще — ни с CEO, ни с агентами
**Живой прогон подтвердил.** `resize_window preset: mobile` (375×812) →
`read_page filter: interactive` — из UI пропали ВСЕ элементы чата: список
интерактивных элементов на весь экран — только шапка, статус-бар, вкладки
Обзора и нижняя навигация. `document.querySelectorAll('input[placeholder],
textarea[placeholder]')` → `[]` — ни одного текстового поля ввода на странице,
хотя раньше на десктопе именно там живёт поле «Сообщение офису…».

Код подтверждает причину: `webapp/src/app/App.tsx:583` —
```tsx
{isOffice && !isMobile && (
  <RightPanel collapsed={!panelOpen} onToggle={...} onOpenAgentChat={openChat} />
)}
{isMobile && (
  <div>...<NavRail orientation="horizontal" .../></div>
)}
```
На мобильном `RightPanel` (общий чат + личные чаты с агентами, вкладка
"feed"/"chat") не рендерится вообще — заменяется на нижнюю панель вкладок.
Дальше хуже: **блокирующие вопросы агентов (`ask_user`) отвечаются ТОЛЬКО
через `/api/ask` из личного чата** — я прогрепал весь `webapp/src/app` на
`api.answer(` (низкоуровневый эндпоинт для `/api/answer`) — ни одного вызова
нигде. Единственный путь ответить агенту — печатать в `ChatTab` внутри
`RightPanel`. Итог: если офис на мобильном задаёт блокирующий вопрос, у
пользователя физически нет кнопки, чтобы ответить — весь план встаёт, а
человек не понимает почему (никакого сообщения "откройте с компьютера" тоже
нет — просто тишина).

Отдельно: `OnboardingFlow.tsx` (первый диалог с CEO) НЕ зависит от `isMobile`
— онбординг на телефоне работает нормально. Ломается именно после выхода в
рабочий офис — то есть первое впечатление хорошее, а затем канал общения
исчезает.

**Фикс:** на мобильном нужен явный, доступный с любой вкладки способ открыть
чат (полноэкранный оверлей поверх `NavRail`, а не постоянная боковая панель)
— и отдельно: если у пользователя есть pending-вопрос, это должно быть видно
и достижимо с любого экрана (баннер уже есть на десктопе в `RightPanel`, его
нужно вынести выше уровня `isMobile`-ветки).

### ❌ 2. Нет загрузки файла/фото/аудио — ни в чат, ни в рабочую папку
Подтверждено грепом (без совпадений): ни одного `UploadFile`/`multipart`/
`File(` в `routers/`, ни одного `<input type="file">` ни в одном `.tsx`
файле `webapp/src`, ни `Paperclip`/📎/`attach` — нет даже иконки-намёка.
`RightPanel.tsx:224-236` — строка ввода чата это `<input>` + кнопка «отправить»,
без слота под вложение.

### ❌ 2b. Даже если бы загрузка появилась — модели не подключено «зрение»
Прогрепал `src/core/llm.py` и весь `src/` на `image`/`vision`/`transcribe`/
`audio`/`input_audio`/`multimodal` — ни одной такой функции нет вообще. Это
значит проблема не только в UI: единый LLM-клиент сейчас физически умеет
слать только текст. Пользователь не может показать агенту фото витрины,
скриншот конкурента, логотип для сайта, аудио голосового брифа — приходится
пересказывать текстом, что для части кейсов (макет дизайна, фото товара)
попросту невозможно пересказать адекватно.

**Фикс:** `POST /api/thread/{id}/upload` (multipart, лимит размера, whitelist
image/audio/pdf) → `workspace.write_file` + путь в сообщение; для картинок —
подмешивать `image_url`/base64 в тот же tool-loop `core/llm.py` (если текущая
модель это поддерживает — сверить с `apinet`), для аудио — минимум STT перед
отправкой текстом агенту.

## P1 — сценарий завершим, но нелогично или рискованно

### ⚠️ 3. Сообщения в общий чат и личные чаты не ограничены по длине
Тот же класс бага, что уже чинили в этой сессии для `investigation.py`
(`_MAX_MESSAGE_CHARS = 2000`), но **не тронули два соседних входа**:
- `routers/comms.py:76` `/api/ask` (личный чат с агентом) — `message =
  (data.get("message") or "").strip()`, без проверки длины, дальше
  безусловно уходит в `memory.remember(...)` (**подмешивается в промпт
  КАЖДОГО будущего агента до конца жизни тенанта**) и в `intent.capture`.
- `routers/comms.py` `_steer_from_chat` (общий `/api/chat`) — то же самое,
  `text` без проверки размера идёт в `intent_module.capture` и далее в
  CEO-триаж/`investigation.run_turn`.

Разрыв даже хуже, чем в онбординге: там раздутая строка живёт один раз в
одном месте, здесь — навсегда бустится в системный промпт каждого агента
через `memory.remember`. Двойной клик отправки/автозаполнение/склейка от
повторного набора (реально наблюдалось в прошлом живом прогоне этой сессии)
здесь будет стоить дороже.

**Фикс:** тот же `_MAX_MESSAGE_CHARS`-паттерн на входе `/api/ask` и
`_steer_from_chat`, до `memory.remember`/`intent.capture`.

### ❌ 4. Нет экспорта результатов — только отладочный дамп лога
Прогрепал весь `webapp/src` на `download=`/`createObjectURL` — 5 совпадений,
и все пять — это либо "открыть в новой вкладке" (`<a href={s.url}
target="_blank">` для сайтов), либо кнопка "копировать" в `AuthModal`. Единственный
реальный файл на скачивание во всём продукте —
`routers/team.py:244-249`, `Content-Disposition: attachment` — это
полнотекстовый ОТЛАДОЧНЫЙ лог работы офиса (бриф+трейс+результаты одним
txt-файлом), кнопка «Логи работы офиса» в Настройках.

Нет: CSV лидов (`ResultsView.tsx` — только список карточек, `api.leads()`
без экспорта), ZIP сайта/бота из `workspace/`, PDF отчёта. Пользователь,
которому нужно унести результат к себе (в CRM, инвестору показать), может
только копипастить руками или просить у агента txt-лог с ВСЕЙ внутренней
кухней сразу.

**Фикс (минимум):** `GET /api/leads/export.csv`; ZIP-экспорт активного
проекта (`workspace.write_file`-дерево проекта → `zipfile` в память →
`StreamingResponse`) — переиспользовать уже готовый паттерн из
`team.py:245-249`.

## Проверено и НЕ подтвердилось (чтобы не плодить ложные находки)

- **Пустые кнопки / dead handlers.** Грепом `onClick=\{\(\) => \{\}\}` по
  всему `webapp/src` — ноль совпадений. Единственная явно отключённая кнопка
  — «Пополнить» в Настройках (`SettingsView.tsx:593`, `disabled title="Скоро"`)
  — это честно помеченная заглушка биллинга, вне периметра этого аудита
  (интеграции/платежи сознательно TEST-mode, решение пользователя).
- **Чёрная область под контентом на мобильном скриншоте.** Проверил через
  `getBoundingClientRect`/`getComputedStyle` — DOM-дерево реально заполняет
  100vh (812px и корень, и первый дочерний контейнер), значит это артефакт
  самого инструмента скриншота (несовпадение заявленного viewport 375×812 и
  фактического размера картинки 469×1015), не баг продукта — не включаю в
  находки.
- **Переполнение нижней навигации на 375px.** Скриншот — все 7 иконок
  помещаются в одну строку без наложения.

## Не проверено в этом проходе (честно)

- Сценарии §10b/c/d из промпта (смена цели на середине, противоречивые

  живого прогона с реальными LLM-вызовами по нескольким веткам, не уложились
  в бюджет этого прохода (аудит и так не тратил деньги, кроме уже
  потраченного в прошлых прогонах). Рекомендую отдельным проходом.
- Клавиатурная доступность вне `Modal.tsx` (дропдаун `TopBar`, карточки
  инициатив, `SettingsView`) — не проверял Tab-обход вручную, только визуально.
- STT/vision на уровне apinet (есть ли у текущей модели/провайдера вообще
  мультимодальные эндпоинты) — не сверял с `GET /api/pricing`, только
