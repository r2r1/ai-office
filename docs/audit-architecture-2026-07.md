# Архитектурный аудит AI-Office

*Дата: 2026-07-02. Роль аудитора: Principal Architect / CTO с горизонтом поддержки 10 лет.
Формат — по aa.md: 20 разделов, для каждого замечания Проблема / Последствия / Решение / Приоритет.*

---

## Резюме (одним абзацем)

AI-Office — редкий случай, когда прод-опыт уже въелся в код: мьютексы артефактов, watchdog, анти-циклы, фолбэк-планы — это шрамы реальных прогонов, и они ценны. Но система построена как **монолитный single-process оркестратор поверх JSON-файлов**, где домен «компания» подменён доменом «сделать лендинг». Главные структурные риски: (1) вся персистентность — JSON-файлы + процессный кеш без транзакций и без версионирования, (2) состояние живости (`_thinking_since`, `_agent_task`, futures вопросов) живёт в памяти процесса и умирает с ним, (3) «компания» на самом деле — конечный автомат с одним терминальным продуктом (сайт/бот), захардкоженным в десятке мест, (4) масштабирование ограничено одним asyncio-процессом навсегда, пока нет очереди задач и внешнего стейта. Ниже — детально.

---

## 1. DOMAIN MODEL

**Что есть:** Tenant → Brief → Strategy/TechDesign (тексты) → Milestones → Plan(Task) → Agent/Department → Deliverable/Site/Lead → Events → Decisions → Initiatives → Trust → Costs.

### 1.1 Проблема: «Проект» как сущность отсутствует
План-граф (`plan.json`) — плоский список задач **одного** engagement. Нет сущности Project/Engagement: «сделали лендинг, теперь делаем бота» — это либо дозапись задач в тот же граф, либо reset. `_engagement_complete()` = «все задачи done» — модель одного спринта, а не живой компании.

**Последствия.** Через полгода, когда клиент захочет 2-й и 3-й продукт, история первого проекта, его задачи и его метрики смешаются в один plan.json. Невозможно ответить «что офис сделал за квартал по проектам», невозможно параллелить два независимых проекта (мьютекс сайта глобальный на тенанта). Роадмап «компания развивается сама» упирается в отсутствие единицы работы крупнее задачи.

**Решение.** Ввести `Project {id, goal, status, plan, artifacts, created}` между Brief и Plan. Plan становится per-project. Milestones — per-project. `_engagement_complete` → `project.complete`. Это дёшево сейчас и почти невозможно ретрофитнуть после года накопленных данных тенантов.

**Приоритет: Critical** (одно из «необратимых» решений, см. §21).

### 1.2 Проблема: две параллельные модели прогресса (Milestones vs Plan)
Milestones признаны «производным индикатором» (коммент в loop.py прямо говорит, что они расходились с доской — баг A3), но код всё ещё ведёт их отдельно: CEO их «закрывает», loop их синхронизирует вручную, `_engagement_complete` их игнорирует. Это две записи об одном факте.

**Последствия.** Каждый новый разработчик (или агент-LLM, генерирующий решения CEO) будет путать, что первично. Уже ловили баг рассинхрона; будут ещё.

**Решение.** Milestones = view над Plan (группировка задач по этапу, прогресс вычисляется). Убрать `milestone_done` из решений CEO.

**Приоритет: High.**

### 1.3 Хорошее решение: Goal ≠ Niche
Разделение «цель прогона офиса» и «что продаёт бизнес» с явными подписями в промптах — правильно и выстрадано (баг «натяжные потолки продают упаковку бизнеса»). Но это **соглашение, размазанное по 6 файлам**, а не тип. Правильнее — единый `BriefContext` dataclass с методом `prompt_block()`, который единственный умеет сериализовать бриф в промпт. Сейчас каждый новый вызов LLM — шанс повторить баг. **Приоритет: High.**

### 1.4 Лишние/сомнительные сущности
`initiatives`, `board` («совет директоров»), `trust`, `constitution`, `philosophy`, `understanding` — шесть модулей, каждый со своим JSON, ради UX-театра вокруг одного и того же: «CEO не знает, что делать». Это не домен, это декорации домена (подробнее §16).

## 2. BUSINESS LOGIC

**Как рождается задача:** LLM-генерация плана при bootstrap → фолбэк-план → `add_task` от коллег/критика/директив. **Как принимаются решения:** CEO раз в 3 цикла выбирает из 4 действий (open/close/delegate/wait). **Как закрываются:** непустой текстовый результат агента = done (плюс критик для сайтов).

### 2.1 Проблема: критерий выполнения задачи — «непустая строка»
`_job` в loop.py: `if (result or "").strip(): plan.complete(task_id)`. `done_criterion` есть в модели задачи, подмешивается в промпт, но **никем не проверяется** — кроме сайтов, где есть критик. Агент, написавший «сделал, всё хорошо» без единого tool-call, закрывает задачу.

**Последствия.** По мере ухода от «сайт за прогон» к произвольным задачам (маркетинг, аутрич, интеграции) доска будет зеленеть фиктивными «done». Это фундаментальная дыра автономности: система не отличает работу от рассказа о работе — притом что инвариант проекта «реальный результат, а не пересказ».

**Решение.** Acceptance-слой: каждая задача закрывается верификатором, а не сдачей. Иерархия верификаторов: (а) программный (файл существует / код компилируется / HTTP 200 / интеграция вызвана — по типу задачи), (б) LLM-критик по `done_criterion` с доступом к артефактам, (в) для нечёткого — подтверждение лидера отдела. Критик для сайтов — уже прототип (а); обобщить его в `acceptance.py` с диспетчеризацией по типу артефакта.

**Приоритет: Critical.**

### 2.2 Проблема: эффективность не оценивается вообще
Trust Score считает «задача сдана/агент завис», но нигде нет связи **результат → бизнес-метрика**. Лиды собираются (`leads.py`), но ни CEO, ни план не читают «лидов 0 за неделю → лендинг не работает → инициатива». Петля обратной связи, ради которой всё затевалось («развивать бизнес владельца»), разомкнута.

**Последствия.** Офис навсегда останется «фабрикой первых версий»: сделал → уснул → ждёт указаний. Это прямо противоречит видению из aa.md («главная задача — не выполнять задачи, а развивать бизнес»).

**Решение.** Metrics loop: периодическая задача-«ревизия» (лиды/визиты/ответы клиента за период → событие `signal` → CEO). Технически всё уже есть (events, initiatives) — не хватает единственного продюсера метрик.

**Приоритет: High** — это и есть продукт.

### 2.3 Циклические зависимости и ответственность
Циклических импортов, судя по структуре, избегали (локальные import'ы внутри функций — рабочий, но симптоматичный приём: `loop` знает про `questions`, `threads`, `events`, `decisions`, `trace`, `trust`, `board`, `initiatives`...). `loop.py` на 1228 строк — это God Object: менеджер тенантов + bootstrap + цикл + watchdog + публикация сайта + приёмка + аппрувы + бот-логика. **Нарушение SRP не косметическое:** каждая правка цикла проходит через файл, в котором 15 ответственностей.

**Решение.** Разрезать на: `tenant_manager.py`, `bootstrap.py`, `cycle.py`, `acceptance.py`, `publishing.py`, `watchdog.py`. **Приоритет: Medium** (рефакторинг, не поведение).

## 3. COMPANY MODEL

### 3.1 Проблема: скопирована человеческая компания, а не спроектирована цифровая
Отделы tech/marketing/sales с лидерами CTO/CMO — метафора для UI, но она **втащена в исполнение**: лидер — это лишний LLM-хоп (который сами же выключили: «детерминированный путь без LLM — главный ускоритель», 119 пустых вызовов CTO). Значит лидер как агент не нужен — маршрутизация задач по роли и так детерминированная. Лидер остался как визуальный персонаж и как legacy-LLM-путь «пока плана нет».

**Последствия.** Двойная модель управления (CEO-тир + лидер-тир), в которой один тир декоративный. Новые контрибьюторы будут «усиливать» лидеров, добавляя им LLM-решения — и возвращать хаос, от которого уже ушли.

**Решение.** Честно разделить: **исполнительная модель** (плоская: план-граф → роль → воркер, никаких лидеров) и **презентационная модель** (отделы и персонажи — метафора в UI). Лидер-LLM-путь удалить; «лидер» становится view-группировкой. CEO остаётся единственным решателем.

**Приоритет: High.**

### 3.2 Отсутствующие роли
- **QA/Acceptance** — есть критик для сайтов, нет универсального (см. 2.1).
- **Account manager / клиентский интерфейс** — сейчас вопросы клиенту задают все подряд через `ask_user`; нет владельца отношений с клиентом, дозирующего вопросы (есть только дедуп).
- **Ops/наблюдатель метрик** (см. 2.2).

Лишние: analyst как отдельная роль (задачи ремапятся, роль полумёртвая — `_ROLE_REMAP` уже мапит researcher→analyst, но analyst-задачи «пропускаются» как orphan). Либо дать analyst отдел, либо удалить.

## 4. AI ARCHITECTURE

### 4.1 Абстракции: Agent / Department / Skill / Provider / Worker
- **Agent** — фактически (роль-промпт + tool-loop + запись в registry). Нормально.
- **Skill** — правильная и лучшая абстракция в проекте: «как» отделено от «кто», файловое хранение, динамическая подмешка по роли, тот же формат для built-in и клиентских. Это масштабируется. ✅
- **Provider** — НЕ существует как абстракция: есть один OpenAI-совместимый клиент (`core/llm.py`) с per-tenant кредами. Пока шлюз apinet прячет за собой все модели — терпимо, но это привязка (см. §12).
- **Worker (внешний исполнитель)** — заявлен в видении и в `kind: external` скиллов, но исполнение external-скилла — «плейбук говорит делегировать». Нет контракта: как ставится задача внешнему исполнителю, как принимается результат, как платится. Это плейсхолдер, а не абстракция.

### 4.2 Проблема: дублирование Tool Router ↔ Skills matcher
`use_capability` и `use_skill` — два независимых механизма «потребность словами → скоринг по keywords → лидер или топ-N». Один и тот же паттерн, два кода, два словаря синонимов.

**Последствия.** Через год — два расходящихся качества матчинга, двойная поддержка синонимов, агенты путают, что куда.

**Решение.** Единый `need_resolver(need, kind={capability|skill})` с общим скорером; словари синонимов — данные, не код.

**Приоритет: Medium.**

### 4.3 Проблема: keyword-матчинг как долговременная стратегия
И роутер, и скиллы, и фолбэк-план (`wants_bot`/`wants_site` по подстрокам!), и `touches_site` (мьютекс по словам «телеграм» в заголовке), и `_engagement_needs_bot` — всё на substring-эвристиках по русскому тексту. Комментарии в plan.py честно описывают, как эвристика мьютекса уже ловилась дважды.

**Последствия.** Каждая новая формулировка задачи — рулетка. Немецкоязычный клиент — тотальный промах. Это класс багов, который будет воспроизводиться бесконечно.

**Решение.** (а) Там, где решает семантика — дешёвые embeddings (один вызов на задачу, кешируется) вместо substring. (б) Там, где решает **факт** — убрать угадывание: мьютекс сайта должен строиться не по заголовку задачи, а по **декларации артефактов задачи** (`task.artifacts: ["site/"]`), которую заполняет генератор плана; конфликт = пересечение артефактов. Это заодно универсальный механизм для любых будущих гонок (два агента в одном файле кода — та же проблема, мьютекс `site/` её не покрывает).

**Приоритет: High** (артефакт-декларации), Medium (embeddings).

### 4.4 Нужны ли агенты вообще?
Да — но меньше, чем кажется. Реально LLM-агентность нужна: воркерам (исполнение задач инструментами), CEO (интерпретация событий/директив), критику. НЕ нужна: лидерам (уже выключены), «совету директоров» (LLM-спектакль), генератору инициатив можно оставить как один вызов, не персону. Здоровый вектор — **меньше персон, больше детерминированных механизмов** — уже выбран в коде; довести до конца.

## 5. DECISION SYSTEM

### 5.1 Что есть
CEO: один LLM-вызов раз в 3 цикла, 4 действия. `decisions.record()` — журнал с confidence/risks/alternatives (хорошо для explainability). `autonomy.needs_approval` — уровни автономности. `board.run_session` — эскалация при 3 wait подряд.

### 5.2 Проблема: Decision Engine — это switch на 4 ветки, а решения-числа — самоотчёт LLM
`confidence: 60` из LLM — не вероятность, а жанровое украшение. ROI нигде не считается (initiatives имеют «expected_outcome» текстом). Рисков — список строк. Согласование — только бинарный `needs_approval("publish_site")`.

**Последствия.** Пока действий 4 — терпимо. Как только появятся деньги (платные интеграции, реклама, внешние исполнители) — решения с бюджетом без модели стоимости/ценности опасны: офис сможет тратить квоту клиента на инициативы с выдуманным ROI.

**Решение.** Не строить «Decision Engine» как отдельный сервис (оверинжиниринг сейчас), а ввести **бюджет решения**: каждое действие с расходом имеет `estimated_cost` (LLM-токены считаются уже; интеграции — прайс), сверяется с остатком квоты (costs.over_limit уже есть) и лимитом на инициативу. Confidence из LLM — убрать или перестать показывать как число.

**Приоритет: Medium** сейчас, **Critical** до включения любых платных действий.

### 5.3 Хорошее: жизненный цикл вопроса клиенту
`questions.py` (дедуп, futures, разблокировка задач через `/api/ask`) — правильная модель блокирующего согласования. Но futures **в памяти процесса**: рестарт сервера = все ждущие агенты потеряли свои вопросы (см. §10/§21).

## 6. MEMORY

### 6.1 Что есть — честная оценка
Трёхслойка (GLOBAL из источников истины, DEPARTMENT в knowledge.json, RETRIEVAL как способ подачи) — **архитектурно верная идея**, и решение не дублировать GLOBAL в хранилище (читать из brief/memory) — правильно, рассинхрона нет. Резервирование 2 слотов под глобальное + ранжирование остального по релевантности — грамотный фикс реальной проблемы (A4/A5).

### 6.2 Проблема: retrieval — это токен-overlap по русскому без морфологии
`_tokens()` — точное совпадение слов длиной >2. Русский флективный: «лендинга»/«лендинг», «потолков»/«потолки» — не совпадут. Плюс потолок 60 фактов с вытеснением FIFO — на годовом горизонте компания «помнит» два последних месяца.

**Последствия.** С ростом фактов релевантность деградирует незаметно (нет метрики качества retrieval), агенты снова начнут «забывать», и это спишут на модель.

**Решение.** Минимум: стемминг (snowball/pymorphy — лёгкие) сейчас. Стратегически: embeddings-индекс per-tenant (facts до тысяч — считается на лету, даже без векторной БД). Вытеснение — не FIFO, а консолидация: периодический LLM-проход «сожми 60 фактов в 30, убери противоречия» (тот же паттерн, что consolidate-memory). Противоречия сейчас не обрабатываются никак — дедуп только по точному тексту.

**Приоритет: High.**

### 6.3 Проблема: история не хранится
Память хранит «что знаем», но не «что происходило» в машиночитаемом виде (state.py — лента для UI, trace.py — отладочный лог). Нет event-sourcing минимума: «почему сайт такой» через месяц не восстановить иначе как из decisions.json кусочно.

**Решение.** Не строить event sourcing целиком; достаточно append-only `journal.jsonl` per-tenant/per-project (задача взята/сдана/принята, решение, публикация, ответ клиента) — trace.py почти это, надо возвести из «отладки» в «источник истории» и читать из него дайджест/уроки. **Приоритет: Medium.**

## 7. FILE SYSTEM

### 7.1 Разделение верное, но неявное
Фактически сложились три класса: **артефакты** (workspace/ — код, site/), **знания** (knowledge.json, lessons, strategy.md, tech_design.md), **операционный стейт** (plan.json, events.json, registry...). Проблема — они лежат вперемешку в `data/tenants/<tid>/` плоско, и стратегия/ТЗ — это markdown-файлы, которые агенты могут перезаписать инструментом write_file? — нет, workspace изолирован, хорошо. Но `docs/site_content.md` живёт В workspace и является каналом маркетинг→дизайн — знание, хранящееся как артефакт.

**Решение.** Зафиксировать структуру: `workspace/` (артефакты, доступны агентам), `knowledge/` (документы офиса: strategy, tech_design, site_content — доступны на чтение всем, на запись через выделенный инструмент), `state/` (json-стейт, агентам недоступен). Документ = имеет владельца и ревизии; знание = факт в памяти; артефакт = продукт для клиента. **Приоритет: Medium**, но делать ДО того как формат директории тенанта станет необратимым (§21).

### 7.2 Проблема: JSON-файлы как БД — без атомарности
`write_json` — прямой `write_text`. Убитый процесс посреди записи = битый plan.json = офис тенанта мёртв тихо (read_json вернёт default — «плана нет» → сгенерирует новый, потеряв прогресс!). Это не гипотеза: `except (json.JSONDecodeError...) : return default` — битый файл **молча подменяется дефолтом**.

**Последствия.** Редкий, невоспроизводимый, разрушительный класс багов: «офис забыл всё и начал заново».

**Решение.** Сейчас: атомарная запись (tmp + `os.replace`) — 5 строк. И на битом JSON — не default, а карантин файла + громкое событие. Стратегически — sqlite per-tenant (см. §10).

**Приоритет: Critical (фикс дешёвый, риск разрушительный).**

## 8. EXECUTION

### 8.1 Выбор исполнителя/способа
Иерархия де-факто: план назначает роль → воркер сам решает, брать ли скилл (use_skill) → инструменты/интеграции (use_capability). Это правильная топология. Чего нет:

- **Стоимость выполнения не участвует в выборе.** Модель на агента выбирается вручную/глобально (`models.py`), нет правила «планирование — дорогой моделью, рутинная задача — дешёвой». Costs считаются постфактум.
- **Репозитории/external workers** — см. 4.1, плейсхолдер.
- **Ретраи однородные:** упавшая задача возвращается в очередь и будет исполнена так же. Нет счётчика попыток задачи и эскалации «3 фейла → другой скилл/модель/вопрос клиенту». Watchdog чинит агента, но не стратегию.

**Решение.** `task.attempts`; политика эскалации по попыткам; cost-tier моделей в `models.py` (map роль/тип задачи → tier). **Приоритет: High** (attempts — иначе возможен вечный цикл fail→revert→fail, который сейчас ограничен только бюджет-лимитом).

### 8.2 Хорошее
Верификация кода расширена на JS/ESM (реальный баг закрыт), observation masking в llm.py, инкрементальный учёт расхода — зрелые решения. ✅

## 9. EVENT SYSTEM

**Нужна ли EDA?** Для одного тенанта в одном процессе — «событие» здесь просто очередь заметок для CEO, и это **правильный лайтвейт**, а не Kafka-карго-культ. Оценка: адекватно.

Проблемы:
- **Один consumer.** События читает только CEO раз в N циклов; `opportunity` обрабатываются max 2 за цикл, остальные kind'ы (`problem`, `blocker`) — только через context_block в промпт CEO, т.е. их обработка = «может быть, LLM заметит». Блокер, требующий реакции, не имеет гарантированного пути. **Решение:** детерминированный диспатч по kind (blocker → пауза ветки плана/вопрос клиенту), LLM-интерпретация — только для signal/info. **Приоритет: High.**
- **Системные и доменные события не разделены** терминологически: bus.py (SSE в UI) и events.py (домен) — ок, но watchdog/critic/publish пишут в bus напрямую текстами, а не поднимают доменные события — история компании неполна (см. 6.3).

## 10. SCALABILITY

Это самый жёсткий раздел.

### 10.1 100 компаний — уже больно
Один процесс asyncio. На каждого активного тенанта — цикл раз в 10 с, LLM-вызовы по 30–240 с, tool-loop'ы с `run_command` (subprocess!), `node --check`. При 100 активных офисах: сотни параллельных LLM-вызовов из одного event loop — упрётся не в CPU, а в: (а) файловый I/O JSON без блокировок, (б) `_cache` в context.py — глобальный, растёт неограниченно, deepcopy на каждый read_json больших планов, (в) один процесс = одно ядро для всего парсинга/deepcopy.

### 10.2 1000+ — архитектура не выживает без переписывания
Точки отказа в порядке наступления:
1. **In-memory стейт** (`_office_tasks`, `_thinking_since`, futures вопросов) — уже сейчас запрещает и рестарт без потерь, и второй процесс. Это бутылочное горлышко №1 и оно же — препятствие деплою (zero-downtime невозможен в принципе).
2. **JSON-per-tenant без блокировок** — два процесса = гонки записи; следовательно, горизонтальное масштабирование запрещено самой моделью хранения.
3. **Планировщик-опрос** (`run()` каждые 5 с обходит всех тенантов) — O(N) обход, включая спящих; при 10k тенантов сам обход станет работой.
4. **Секреты**: Fernet от одного APP_SECRET — ротация ключа = перешифровка всего; терпимо, но заложить key-id в шифротекст сейчас дёшево.

### 10.3 Решение (поэтапное, без big-bang)
- **Этап 0 (сейчас, дёшево):** атомарные записи; вынести futures вопросов в файл (вопрос = запись со статусом, агент поллит/ждёт через событие) — это заодно чинит потерю вопросов при рестарте.
- **Этап 1:** sqlite per-tenant (или одна sqlite с tenant_id) вместо JSON — сохраняет файловую философию, даёт транзакции. `ctx.read_json/write_json` — уже единственная точка входа, замена локальна. Именно поэтому это надо делать **до** роста: интерфейс готов, данные ещё маленькие.
- **Этап 2:** офис-цикл как воркер, читающий из очереди «тенанты, которым пора» (redis/pg skip-locked). Состояние живости — в БД. Тогда N воркеров = N процессов, тенант закреплён за воркером эфемерно.
- Никогда не делать: микросервисы по отделам, Kafka, k8s-оператор на текущем этапе — это смерть темпа.

**Приоритет: Этап 0 — Critical, Этап 1 — High (до 50+ платных тенантов), Этап 2 — при реальном росте.**

## 11. PROMPT ARCHITECTURE

### 11.1 Текущее — на 70% правильное
Роли («кто/что нельзя») в `roles.py`, «как» — в скиллах-файлах, каталог подмешивается динамически по роли, контекст задачи собирается `_task_with_context` из слоёв. Это хорошая рамка. Проблемы:

- **Prompt Builder размазан:** `_task_with_context` (loop), `_TEAM_PREAMBLE`/`_AUTONOMY_RULES`/`_brief_context` (agent_factory), `knowledge.context_block`, `events.context_block`, `skills.prompt_block` — итоговый промпт воркера не собирается ни в одном месте и **его никто никогда не видел целиком**. Отладка «почему агент сделал глупость» требует ментальной сборки из 5 файлов.
- **Роли — Python-литералы**, хотя скиллы уже переехали в .md. Непоследовательно: политики (автономия, преамбула) тоже зашиты строками в agent_factory.

**Решение.** Единый `prompt_builder.build(role, task, ...) -> Prompt` со слотами (identity / policies / brief / knowledge / skills / task), логирующий собранный промпт в trace. Роли и политики — в `.md` рядом со скиллами (тот же парсер). Динамические слои: knowledge, events, план, доска. Статические: identity, policies, формат ответа. **Приоритет: High** — это одновременно observability и защита от размазанных багов типа goal/niche.

## 12. API ARCHITECTURE

- **Один OpenAI-совместимый клиент + шлюз apinet** — прагматично: шлюз и есть «мультипровайдер». Риск: привязка не к API-формату (он де-факто стандарт), а к **бизнесу apinet** — прайс, per-tenant токены (`provision_tenant_key`), квоты. Это single point of failure всего SaaS: apinet упал/закрылся → все тенанты мертвы, включая биллинг-логику.
- **Решение:** абстракция не «Provider» (формат один), а **«Billing/Key provider»**: интерфейс `issue_tenant_key / balance / pricing` с реализацией apinet + возможностью прямых ключей клиента (частично есть в llm_settings). Прайс — снапшот с TTL, не хардкод (уже усвоено — median-fallback хорош).
- **tool-loop свой** (llm.py) — правильно, не тащить langchain. ✅

**Приоритет: Medium.**

## 13. UI ARCHITECTURE

По коду (webapp/): вкладки «Проект/Чаты/Команда/Результаты/Лиды/Код/Доступы/События/Дашборд» — UI показывает **внутренности** (события, план-граф, память через /api/knowledge, трейс решений). Для dev-инструмента отлично; для клиента-предпринимателя из видения — перегруз техническими сущностями: клиент не должен думать про «план-граф» и «уровень автономности», он думает «что вы сделали, что мне решить, сколько потратили».

**Решение.** Два режима: «клиент» (дайджест, вопросы-решения, результаты, расход) и «под капотом» (всё нынешнее). Уже есть digest и initiatives — ядро клиентского режима готово. **Приоритет: Medium**, но до первых внешних клиентов.

Известные UX-долги из MEMORY.md (баннер перекрывает, подписи налезают) — починить, мелочь. **Low.**

## 14. PRODUCT THINKING (взгляд инвестора)

**Купил бы?** На seed — да, с условиями. **Восторг:** (1) слой скиллов с клиентской установкой — это App Store-механика и реальный moat-кандидат; (2) выстраданные механизмы надёжности (watchdog, мьютексы, критик) — то, чего нет у демо-конкурентов; (3) вертикальная интеграция до живых лидов — результат, а не чат.

**Сомнения:** (1) unit-экономика — прогон офиса на LLM-вызовах каждые 10 с стоит денег постоянно; модель «офис всегда крутится» должна стать «офис просыпается по событию», иначе маржа отрицательная на спящих тенантах (частично есть: `_has_actionable_move`); (2) продукт сейчас умеет ровно «лендинг + бот» — обещание «цифровая компания» пока витрина; (3) выполнение задач без приёмки (2.1) — риск репутации «AI наделал мусора».

**Легко скопировать:** оркестрацию, изометрический UI, набор интеграций. **Трудно скопировать:** накопленные lessons/скиллы/эвристики из прод-прогонов и — если построить — петлю метрики→инициативы (2.2). Данные о том, «что реально работает для ниши X», — единственный несмываемый moat. Значит их надо начать собирать структурированно **сейчас** (сквозная телеметрия исходов по нишам).

## 15. DEAD ENDS (сейчас кажется хорошей идеей — через год катастрофа)

1. **JSON-файлы + процессный кеш как БД** (context.py). Кеш валиден только пока процесс один — это записано в комментарии как допущение, и оно **тихо ломается** первым же `uvicorn --workers 2` или фоновым скриптом. Через год данных станет много, формат — необратим. → sqlite (10.3), **Critical**.
2. **In-memory futures и живость** — уже сегодня рестарт теряет вопросы клиенту; через год это будет главная жалоба («агент спросил и исчез»). **Critical.**
3. **Substring-эвристики как управляющая логика** (fallback-план, мьютекс, needs_bot) — каждая уже стреляла; их число растёт. → артефакт-декларации задач + embeddings. **High.**
4. **«done = непустой текст»** — по мере расширения типов задач превратит доску в театр. **Critical.**
5. **Лидер-тир как LLM-агенты** — мёртвый код, который будут реанимировать. Удалить. **Medium.**
6. **`_fallback_plan` с русскими подстроками** — при выходе за RU-рынок молча деградирует в «спроси клиента» всегда. **Low сейчас.**
7. **Плоский plan.json без Project** — необратимость формата данных тенантов (1.1). **Critical.**

## 16. OVERENGINEERING (удалить/слить)

- **board.py («совет директоров»)** — LLM-сессия при 3 wait подряд. Wait-стрик — симптом «нет хода»; правильная реакция детерминирована (вопрос клиенту / ревизия плана), а не второй LLM-спектакль поверх первого. → слить в политику эскалации.
- **trust.py + understanding.py + philosophy.py + constitution.py** — четыре псевдо-домена. Constitution (лимиты) — оставить как настройки; trust — свести к счётчикам per-department без «предложений повышения автономии» (это UX, не домен); philosophy — это просто часть системного промпта.
- **initiatives.py** — оставить, но это не отдельная сущность, а `task` со статусом `proposed`. Две доски (план + инициативы) сольются рано или поздно — лучше рано.
- **Лидеры как агенты** (см. 3.1).
- **milestones как хранимое состояние** (см. 1.2).

Итого: ~6 модулей и 3 JSON-файла на тенанта можно убрать, сократив число сущностей, которые обязан понимать каждый следующий разработчик, примерно на треть.

## 17. MISSING COMPONENTS (без чего система не сможет существовать)

1. **Acceptance-слой** (2.1) — без него автономность фиктивна.
2. **Атомарная персистентность** (7.2) — без неё данные тенантов ненадёжны by design.
3. **Durable-вопросы/живость** (10.3 этап 0) — без них невозможен даже деплой новой версии.
4. **Metrics→decision петля** (2.2) — без неё продукт не соответствует собственному определению.
5. **Тесты.** «Тестов и линтера нет» (CLAUDE.md) при 12.6k строк управляющей логики с выстраданными инвариантами — каждый инвариант, описанный комментарием («не выпиливай», «реальный баг из прода»), должен быть тестом, иначе он будет выпилен. Начать с чистых модулей: plan, knowledge, events, costs — они file-backed и тестируются тривиально через tmp tenant-dir. **Critical по совокупности.**
6. **Биллинг клиента** — costs считает расход, но нет тарифа/оплаты; для SaaS это существование.

## 21. Необратимые решения (по финальному требованию aa.md)

| Решение | Риск ошибки | Дорого менять потому что | Более устойчивая альтернатива |
|---|---|---|---|
| **Формат данных тенанта** (плоские JSON, без Project, без версий схемы) | Высокий | Данные живых клиентов; миграции без транзакций и без `schema_version` — вслепую | Добавить `schema_version` в каждый файл СЕЙЧАС; Project; затем sqlite |

Дёшево сейчас, невозможно после накопления threads/истории |

| **API-слой = apinet** | Средний | Биллинг и provisioning тенантов завязаны на одного вендора | Billing-provider интерфейс (§12) |
| **Язык = русский в эвристиках** | Низкий сейчас | Подстроки размазаны по коду | Централизовать словари как данные; семантика — embeddings |
| **Skills-формат (.md frontmatter, npx skills-совместимый)** | Низкий | Клиентские скиллы уже в этом формате | Хороший выбор — совместимость с внешней экосистемой. Оставить ✅ |
