# AI-Office — аудит реальных способностей (не по плану, а по факту)

**Дата:** 2026-07-16. **Метод:** чтение кода каждого модуля-способности (не докстрингов, а реальных
HTTP-вызовов/заглушек), проверка окружения этого конкретного деплоя (`.env`, наличие Docker),
осмотр РЕАЛЬНЫХ артефактов, оставленных прошлым живым прогоном офиса (`data/tenants/ws_*`,
см. [pre-release-audit-2026-07-15.md](pre-release-audit-2026-07-15.md) §10) — не гипотез, а того,
что офис реально написал на диск в прошлый раз, когда работал по-настоящему.

Формат: для каждой способности — **что заявлено** (CLAUDE.md/докстринг) vs **что происходит по факту**,
с пометкой ✅ реально работает / ⚠️ работает частично или с оговоркой / ❌ не работает в этом деплое.

---

## 1. Ядро: автономный цикл, мультиагентность, ролевая структура

✅ **Реально работает**, живьём подтверждено в этой же сессии (реальный `office-real` прогон,
не демо): CEO открывает отделы по необходимости → лидер нанимает работников → работники пишут
файлы, переговариваются между собой (`ask_colleague`, реальный обмен `@cto` ↔ CTO), CEO задаёт
блокирующий вопрос и ждёт ответа владельца перед публикацией. Один агент на роль (`MAX_PER_ROLE=1`)
соблюдается кодом (`registry.has_role`), не только на словах.

⚠️ **Оговорка**: вся эта модель проверена на ОДНОМ реальном сквозном прогоне с относительно
простой нишей (деревянные разделочные доски). Поведение при по-настоящему сложном/многошаговом
брифе, при параллельных 3 активных проектах одновременно, при реальном сбое LLM-провайдера
посреди цикла — не проверялось живьём в этой сессии, только через юнит-тесты с моками.

## 2. Tool Router / Skills Layer

✅ **Реально работает**: `use_capability`/`use_skill` — не просто маршрутизация по ключевым словам
в вакууме, а живьём подтверждённый выбор (`landing_conversion`, `brand_book` реально применялись
в прошлом прогоне — есть их результат на диске: `docs/brand_book.md`, `docs/offer.md`).
22 встроенных скилла, каждый отдельным `.md`-файлом — структура, заявленная в CLAUDE.md §3.6.1,
подтверждается напрямую (`ls src/office/builtin_skills/` → 22 файла).

⚠️ **Реальный разрыв план/факт**: системный сайт-скилл называется `vite_react_site.md` и
описывает **React + Vite (настоящая сборка) + Motion**. По факту оба сайта, реально построенных
живым офисом в прошлом прогоне (`data/tenants/ws_3709a821603f/workspace/*/site/`), — это
**голые `index.html` + `styles.css` + `script.js` без единого `package.json`, `vite.config`,
`.jsx`-файла или `node_modules`**. Разработчик написал качественный, нешаблонный статический сайт
(проверено: реальный, нишевый текст, а не рыба), но НЕ тот стек, который заявлен как системный.
Наиболее вероятная причина — `ALLOW_CODE_EXECUTION=0` в этом деплое (см. §5 ниже): реальная
сборка через `npm run build` требует исполнения кода, а LLM-агент, столкнувшись с этим
ограничением или просто не имея повода запускать сборку, ушёл на путь наименьшего сопротивления
(статические файлы вместо реального Vite-проекта), и ничего в системе этого не отследило —
`site_builder.py`/`critic.py` принимают готовый статический сайт как валидный результат.
**Вывод: заявленный системный стек соблюдается кодом (скилл существует, роли его видят), но НЕ
гарантированно соблюдается результатом — нужна либо явная проверка «это действительно Vite-проект»
в acceptance, либо честная перекалибровка ожиданий («статический сайт — тоже валидный исход
скилла», а не расхождение).**

## 3. World Model / Acceptance / Specification / Decision Engine

✅ **Реально работает**, живьём подтверждено: `/api/world` в прошлом прогоне отдавал корректный
срез (задачи, проекты, объекты) в реальном времени; `acceptance.check` реально блокировал попытку

это код, который в реальный момент реально отказал агенту и реально пропустил его после решения
человека.

## 4. Интеграции — честная разбивка «настоящее / симуляция»

В реестре (`src/integrations/registry.py`) 16 интеграций. Проверка каждой на реальные HTTP-вызовы
внешнего API вместо внутренней имитации:

**✅ Настоящие (реальные HTTP-вызовы к внешнему API):**
- `telegram` — Bot API (`api.telegram.org`), реально проверено (`get_me`/`send_message`).
- `telegram_personal` — MTProto через Telethon (реальный личный аккаунт, не бот).
- `github` — Contents API (`push`/`create_repo`), реальный OAuth/PAT.
- `google_sheets`, `gmail`, `google_calendar` — реальные Google API endpoints, реальный OAuth.
- `crm_bitrix24`, `bitrix24` — реальный REST/вебхук Bitrix24, включая OAuth-вариант.
- `erp_1c` — реальный HTTP + Basic Auth к 1С OData-серверу клиента.
- `figma` — реальное чтение `api.figma.com/v1/files/...`.
- `website` — не внешний сервис, а собственный self-hosted паблишинг (`/site/{slug}`) — реален
  по построению, отдельного «настоящего/поддельного» разделения тут нет.

**❌ Симуляция (внутренний детерминированный стаб, `cred_fields=[]`, НИКАКОГО внешнего вызова):**
- `payments` — «test-режим», деньги никуда не уходят и не приходят.
- `deploy` — «создание деплоя» — фиктивный статус, ничего реально не деплоится.
- `invoicing` — счёт генерируется, но PDF — заглушка (`# заглушка — реальный PDF не генерируется`
  прямо в коде).
- `ads` — статистика кампании — `_deterministic_stats()`, вычисляется по формуле от времени, не
  от реального рекламного кабинета.
- `crm` (обобщённый, отличный от `crm_bitrix24`) — «экспорт лида» пишет только во внутреннее
  хранилище тенанта, не в реальную внешнюю CRM.

**Вывод**: из 16 заявленных интеграций **10 реальны, 5 — намеренные симуляции «для полноты
демонстрации способности», 1 (website) — реален по определению**. Сам код честно называет их
«test-режим» в комментариях — это не сокрытый баг, а осознанный дизайн (дать компании
«способность» продавать/рекламировать до того, как клиент подключит настоящего провайдера).
Но если клиент не прочитает код, он может решить, что "оплата" или "запуск рекламы" реально
работают — на UI это визуально неотличимо от настоящих интеграций (нет пометки «демо-режим»
у самой способности, только у неподключённых `cred_fields`-провайдеров). **Реальный UX-риск,
не отражённый в предыдущих аудитах.**

## 5. Sandbox / исполнение кода / MCP tenant-серверы / hosted apps

❌ **Не функционирует в ЭТОМ КОНКРЕТНОМ деплое прямо сейчас** (не «баг кода», а фактическое
состояние окружения):
- `ALLOW_CODE_EXECUTION` не задан в `.env` → по умолчанию `"0"` (`workspace.py:81`) —
  `execute_code`/`run_command` (терминал) физически выключены для всех агентов.
- `.env` содержит `SANDBOX_MODE=docker`, но в этом окружении **Docker не запущен/недоступен**
  (`docker version` не отвечает) и **образ `ai-office-sandbox` не собран**. `mcp_bridge.
  _tenant_sandbox_ready()` = `sbx.mode() == "docker" and sbx.docker_available()` — оба условия
  не выполняются одновременно только формально («режим — docker», но «docker недоступен»), и
  код корректно деградирует (не падает, тихо возвращает пустой список), но по факту это значит:
  **регистрация тенантских MCP-серверов, `register_external_api`, `host_app`
  (запуск сторонних приложений через docker-compose) — все три реально недоступны прямо
  сейчас**, несмотря на то, что код для них полностью написан и покрыт тестами (юнит-тесты
  мокают Docker, поэтому «зелёный CI» не значит «реально работает в этом деплое»).
- Отдельно созданная в этой же сессии Docker-инфраструктура (`Dockerfile`, `docker-compose.yml`)
  — для деплоя САМОГО AI-Office, не для песочницы агентов — тоже ни разу не запускалась вживую
  (честно задокументировано при создании).

**Вывод**: заявленная в CLAUDE.md песочница («docker = контейнер без сети/read-only ФС») —
это реальный, полностью реализованный код, который **прямо сейчас не активен в этом окружении**.
Любая способность, зависящая от неё (сторонние MCP-коннекторы, кастомные внешние API, hosted
apps), для сегодняшнего клиента этого конкретного деплоя недоступна, пока оператор не поднимет
Docker и не соберёт образ, либо явно не переключит на `SANDBOX_MODE=direct` (с осознанным
security-компромиссом, который сам CLAUDE.md называет "security-долг").

## 6. Публикация сайтов, лид-форма, CRM-мини-система

✅ **Реально работает end-to-end**, живьём подтверждено дважды в этой сессии: реальная HTML-форма

независимо опубликовать два разных сайта одному бизнесу — теперь заблокировано (переиспользование
существующего сайт-проекта).

**Главный вывод**: ядро продукта (оркестрация, память мира, приёмка, публикация, лиды) —
не витрина, это реально работающий, живьём многократно подтверждённый код. Но заявленная
«широта» способностей компании (продажи через рекламу, приём оплат, деплой стороннего кода,
подключение любого MCP-сервиса) в значительной части — либо намеренная симуляция без предупреждения
об этом клиенту, либо код, для которого этому конкретному деплою не хватает включённой
инфраструктуры (Docker, `ALLOW_CODE_EXECUTION`). Разница между «офис умеет N вещей» (маркетинговая
формулировка) и «офис реально делает N вещей прямо сейчас в этом окружении» (то, что увидит
живой клиент) — заметно меньше N, чем кажется на первый взгляд по одному только CLAUDE.md.
