# Аудит enforcement инвариантов — текст промпта vs программный гейт

Дата: 17.07.2026. PR-4 из `docs/technical-due-diligence-2026-07-17.md` §12.

Задача: для каждого инварианта из CLAUDE.md §4 и ключевых текстовых
требований `builtin_roles/*.md` / `builtin_skills/*.md` — определить,
держится ли он **программно** (тест или рантайм-гейт, который физически
не даёт системе нарушить правило) или **только текстом промпта** (LLM
юридически волен проигнорировать).

Два реальных случая в этой сессии (designer не спрашивает про дизайн,
integrator не спрашивает про недостающие данные) были найдены именно как
"текст без гейта" и закрыты программно — это прецедент для остальной
таблицы.

Статусы: **✅ enforced** (код физически не даёт нарушить) · **⚠️
partial** (частично — гейт есть, но не покрывает все пути нарушения) ·
**❌ text-only** (только промпт/документация, LLM может проигнорировать).

## Инварианты CLAUDE.md §4

| Инвариант | Статус | Механизм / где дыра |
|---|---|---|
| Автономность (`get_connection` → OAuth-подсказка → `ask_user` за ключом) | ⚠️ partial | `use_integration`/`list_integrations` подсказывают правильный путь программно (см. `agents/integration_tool_handlers.py`), но ничто не мешает агенту всё равно спросить ключ для OAuth-интеграции по памяти вместо OAuth-кнопки — это поведенческий баг, который CLAUDE.md сам описывает как «реальный баг» без указания, что закрыт кодом |
| Артефакты только через инструменты (`write_file`, не ```-блоки в ответе) | ❌ text-only | Инструкция живёт в `office/policies/team.md`. Программного гейта, отклоняющего сдачу с ```-блоком кода в тексте ответа, не найдено — `acceptance._is_process_chatter` ловит другой паттерн (реплики процесса), не код в ответе |
| Три слоя, три места (домен/HTTP/персистентность) | ❌ text-only, но соблюдается | Архитектурная конвенция, не проверяемая автоматически (нет линтера, запрещающего `open()`/`json.dump` вне `context.py` или бизнес-логику в `server.py`). Дисциплина держится качеством ревью, не кодом — риск регресса при росте команды (см. Due Diligence §3.2.2) |
| Весь промпт собирает Prompt Builder | ✅ enforced по факту структуры кода | `prompt_builder.py` — единственная точка, все роли реально идут через `build()`/`task_context()`; проверить обратное (кто-то собирает промпт в обход) можно только ревью/grep, но структурно альтернативного пути в коде не создано |
| Роль — «кто/что нельзя», не «как» | ⚠️ partial | Для `designer` есть программный `ROLE_DENY_PREFIXES`/`path_denied()` в `roles.py` (единственная роль с явным письменным запретом). Для остальных ролей граница — только текст в `builtin_roles/*.md`, ничем не enforced |
| Цель прогона офиса ≠ то, что продаёт бизнес клиента (`goal` vs `niche`) | ❌ text-only | `brief_context`, `chat.py`, `critic.review_site_llm`, `orchestrator.interpret_directive` — везде подмешивается по тексту промпта («это НЕ то, что продаёт компания»), нет структурной проверки, что сгенерированный контент ссылается на `niche`, а не на `goal` |
| **Задача закрывается только приёмкой** | ✅ enforced | `acceptance.check()` — реальный программный гейт, `execution.py` не переводит задачу в `done` без `verdict["passed"]`. Сильнейшее звено системы (и место, куда добавлены оба новых гейта этой сессии) |
| Plan-driven always (`_fallback_plan`) | ✅ enforced | `loop.py`/`planning_engine.py` — при сбое LLM-генерации плана используется детерминированный fallback, покрыто тестами (`test_planning_engine.py`) |
| Общие доступы (`get_connection` доступен любому агенту) | ✅ enforced | Единое хранилище `connections.py`, нет per-role фильтрации в коде — соответствует инварианту по построению |
| Единая ответственность (`MAX_PER_ROLE=1`) | ✅ enforced | `free_worker_of_role()` в `planning_engine.py` — перед наймом проверяет отсутствие свободного/занятого агента этой роли в проекте; создать второго агента одной роли параллельно в коде нельзя |
| Приоритет указаний клиента (`memory.all_entries()`) | ⚠️ partial | Реально подмешивается в промпт (`prompt_builder`), но это **промпт-приоритет**, не программный — ничто не блокирует агента, который всё равно нарушит прямой запрет клиента (например, дважды использовал платный конструктор вопреки правилу) кроме отдельного детерминированного вето в `decision_engine._constitution_check` — которое покрывает только раздел «Инициативы/PlanDiff», не все пути исполнения задачи |
| Реальный код, не описание; push только после одобрения владельца | ❌ **text-only — самый серьёзный найденный разрыв** | См. отдельный разбор ниже |
| Дедупликация вопросов/подключений | ✅ enforced | `questions.py` (`_find_similar`, Jaccard ≥0.6 на токенах) и `connections.save()` (сравнение всех полей) — оба реальные программные механизмы с тестовым покрытием |
| Кулдаун, не дедлок (`AGENT_COOLDOWN_SECS`) | ✅ enforced | `planning_engine.py` — прямая проверка `now - last_run_for(agent_id) < AGENT_COOLDOWN_SECS` перед назначением, не текст |
| Multi-tenancy (без глобалей с состоянием тенанта) | ❌ **нарушается системно на уровне процесса** | См. Due Diligence §2.1 — module-level `dict[tenant_id -> ...]` в `loop.py`/`execution.py`/`questions.py`/`bus.py` и др. Формально это `dict`, ключ — tenant_id, данные не текут МЕЖДУ тенантами внутри одного процесса — но сам инвариант, как написан в CLAUDE.md («никаких глобалей с состоянием тенанта»), нарушается буквально: это глобальные словари, просто с изоляцией по ключу, а не полное отсутствие глобального состояния. Разница существенна для горизонтального масштабирования (см. Due Diligence §2.1) |
| Учёт расхода инкрементальный (`costs.record` внутри цикла) | ✅ enforced | `core/llm.py` — `costs.record()` вызывается после каждого ответа API внутри `run_agent`, не в конце функции — зомби-прогон не крадёт деньги молча (реальный инвариант, реально соблюдён) |
| Прайс apinet — единственный источник правды | ⚠️ partial | `costs.PRICES` — статический словарь в коде, не живой запрос к `GET /api/pricing`. «Единственный источник правды» в архитектурном смысле не автоматизирован — обновление цены требует ручной правки `PRICES`, риск рассинхронизации с реальным прайсом apinet остаётся структурным, только смягчён консервативной оценкой по умолчанию (`price_for()`) |
| Убивать процессы за собой | ❌ text-only (операционная практика) | Не код-инвариант — процедура для оператора/агента-ассистента, не для продукта. Вне области программного enforcement по определению |

## Самый серьёзный найденный разрыв: push в GitHub — гейт есть, но неверно настроен

**Статус: исправлено** (`src/office/autonomy.py`, коммит после этого документа).

CLAUDE.md §4 формулирует явно: *«разработчик пишет в workspace/, верифицирует
(verify_code), и пушит в GitHub только после одобрения клиента (через
ask_user)»*.

Первичная проверка ошибочно заключила «гейта нет вообще» — при повторном,
более внимательном чтении оказалось, что единый гейт **есть**:
`_execute_integration()` в `integration_tool_handlers.py` для КАЖДОГО
вызова интеграции (кроме `website`, у неё свой путь) зовёт
`autonomy.needs_approval(action_type)`, и при `True` действие не
выполняется — агенту возвращается инструкция спросить владельца.
Проблема была не в отсутствии гейта, а в его **конфигурации**:
`autonomy._action_type_for()` классифицировал `push` тем же типом
действия, что «создать пустой репозиторий» (`create_repo`), а порог
`create_repo` — уровень «guided», который **и есть уровень по умолчанию**
(`autonomy._DEFAULT_LEVEL = "guided"`). Итог: на дефолтных настройках
`needs_approval("create_repo")` возвращает `False`, и push реально
выполнялся без единого вопроса владельцу — гейт физически существовал,
но не срабатывал для этого действия ни разу при обычной конфигурации.

(Отдельно проверено: `constitution._DEFAULT_RULES["create_repo"] = True`
выглядит как встречный гейт, но по докстрингу самого `override_for()` эти
дефолты НЕ подмешиваются в решение — это заготовка для отображения в
Settings UI, не реальный enforcement. Реальное решение принимает только
`autonomy.can_auto()`/`was_approved_once()`.)

**Исправление:** `push` вынесен в отдельный `action_type = "push_code"` с
собственным порогом `"trusted"` — тем же, что у `publish_site` (самого
строгого действия платформы). На дефолтном уровне «guided» push теперь
корректно требует вопроса владельцу; `create_repo` (создание пустого
репозитория — менее рискованное действие) остался на прежнем пороге.
Покрыто `tests/test_autonomy.py` (5 тестов, первое тестовое покрытие
этого модуля).

## Итоговый список для следующей волны программных гейтов (по приоритету)

1. **GitHub push без подтверждённого согласия владельца** (выше) — самый
   серьёзный, наибольшее расхождение между обещанием клиенту и
   гарантией кода.
2. **```-блоки кода в тексте ответа агента** вместо `write_file` —
   инвариант «артефакты только через инструменты» не проверяется
   программно; ответ с ```python...``` может пройти приёмку, если он не
   пустой и не «реплика процесса».
3. **Платные конструкторы вне PlanDiff-пути** — `decision_engine.
   _constitution_check` ловит запрещённые слова только для diff'ов
   инициатив, не для прямых `use_integration`/`use_capability` вызовов
   агента посреди обычной задачи.
4. **`niche` vs `goal` подмена** — риск смешения остаётся структурным
   (много мест, где `goal` идёт в промпт); нужен единый сериализатор
   контекста бизнеса (аналог `brief_block`), через который ОБЯЗАН идти
   любой промпт, упоминающий цель прогона офиса — а не точечные
   комментарии-напоминания в каждом файле по отдельности.

Каждый из четырёх — самостоятельный PR, не связанный с остальными,
следует тому же паттерну, что уже применён и протестирован в этой сессии
(`tests/test_acceptance.py`).
