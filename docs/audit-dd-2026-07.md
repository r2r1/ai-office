# Due Diligence: AI-Office

*Technical audit for acquisition decision. 2026-07-03, после завершения Phases 0–6
дорожной карты. Кодовая база: ~16 200 строк Python (backend) + ~6 000 строк TS
(frontend), 18 policy-файлов, 18 скиллов, 9 ролей, 11 юнит-тестов.
Выполнен по заданию `docs/анализ_промпт.md`. Предыдущий аудит
(`docs/audit-architecture-2026-07.md`, оценка ~45%) проводился ДО реализации фаз
и устарел — данный документ замещает его выводы.*

---

## 1. Общая архитектура

**Текущее состояние.** Система — мультиарендный автономный цикл над файловой
персистентностью. Жизнь начинается в `lifespan` FastAPI: стартует менеджер,
который каждые 5с опрашивает тенантов; у тенанта с готовым брифом поднимается
собственная asyncio-задача офиса. Внутри: одноразовый bootstrap
(ресёрч→стратегия→ТЗ→план) → вечный цикл «пауза/бюджет/завершение → watchdog →
маршрутизация → исполнение → приёмка». Жизнь заканчивается не завершением
процесса, а **режимом мониторинга**: план закрыт → gap-анализ → либо новая
работа под разрыв, либо «жду указаний». После Phase 6 подсистемы реально
разделены: `loop` (шедулер, 324 строки) → `bootstrap` / `planning_engine` /
`execution` / `decision_engine`+`sandbox` / `acceptance` /
`world`+`metrics`+`gap` / `observability`. Направления импортов односторонние.

```
HTTP/SSE (server.py) ──► Intent capture ──► Decision Engine ──► Sandbox checks ──► Plan diff
                                                                                      │
Манеджер тенантов ──► loop (шедулер) ──► bootstrap (1 раз)                            ▼
                          │                                                     PLAN (SSOT работы)
                          ├──► planning_engine (маршрутизация, CEO-гейт) ◄──────────┘
                          └──► execution (Policy → бюджет-гейт → LLM-worker → acceptance)
                                     │                                    │
                               workspace/ (артефакты)              metrics → gap → replan
                                     └──── critic/publish ──► sites/leads ──┘
Все журналы (trace/prompts/decisions/snapshots) ──► observability.timeline / decision_chain
```

**Хорошо:** ядро отделено от UI по-настоящему; каждое ребро цикла — ответ на
задокументированный прод-инцидент. **Плохо:** `server.py` — 1791 строка
эндпоинтов-монолит; `agent_factory.py` (875) — второй кандидат на расслоение.
**Риск:** жизненный цикл офиса всё ещё привязан к жизни одного процесса.
**BOS:** соответствует §3/§12 в основном контуре. **Изменить:** расслоить
server.py по доменам роутеров. **Приоритет: средний.**

## 2. Бизнес-модель

**Состояние.** AI-Office продаёт не «агентов», а результат: клиент формулирует
цель, система исследует рынок, планирует, производит артефакты (сайт/бот),
собирает лиды и — с Phase 4 — сама находит следующую работу, если цель не
достигнута. Граница ответственности зафиксирована кодом: внешне-видимые
действия проходят autonomy/Constitution-гейты, деньги — бюджетные лимиты,
публикация — одобрение владельца.

**Хорошо:** «Принцип №2 BOS» (ответственность за достижение цели, а не за
артефакт) впервые реально исполним — есть метрика лидов, gap и авто-replan.
**Плохо:** экономика прокси-уровня (лиды×чек); реальной выручки система не
видит и не увидит без интеграций с платежами. **Риск:** обещание «растим
бизнес» упирается в то, что каналы привлечения (реклама, соцсети) не
подключены — офис может улучшать лендинг бесконечно, не двигая трафик.
**Приоритет закрытия: высокий продуктово, не архитектурно.**

## 3. Domain Model

```
Tenant (saas)
└─ Company (по-прежнему НЕявная — сумма файлов тенанта)
   ├─ Identity: Philosophy + Constitution (не слиты в DNA, без версий)
   ├─ Brief (типизирован частично: budget_usd/avg_check_usd добавлены)
   ├─ Intent (журнал, оба входа чатов)
   ├─ Objectives (measured_by; авто-цель «заявки/неделю»)
   ├─ Strategy/TechDesign (ТЕКСТЫ — по-прежнему не сущности)
   ├─ Project ─ Task {…, artifacts[], required_capabilities[], acceptance, attempts}
   ├─ Capability (реестр have/missing/available — НОВОЕ)
   ├─ Metrics (факт|оценка — НОВОЕ) ─ Gap (вычислимый — НОВОЕ)
   ├─ Decision (diff + checks + status — НОВОЕ) / Sandbox (механизм)
   ├─ Events / Knowledge / Lessons / Trust / Autonomy / Costs
   └─ Артефакты: workspace-файлы + Sites + Leads   ← РЕЕСТРА ВСЁ ЕЩЁ НЕТ
```

**Отсутствуют:** Artifact как сущность с owner/status/depends_on (есть только
декларации `task.artifacts` — типы, не экземпляры); Company; History
(унифицированная); Workflow; Relationships. **Смешаны:** milestone (индикатор)
и Objective местами дублируют смысл «цели». **Лишние:** `board.py`/`trust.py`
живут как домены, хотя §11 велит им быть view. **Приоритет: Artifact-реестр —
высокий** (это «валюта компании», и на нём стоят метрики per-artifact).

## 4. World Model

**Состояние.** `world.snapshot()` агрегирует 15 источников + `metrics` (новое);
diff/журнал срезов работают и реально используются (Observability, закрытие
проектов, привязка решений). **SSOT в JSON:** план, проекты, цели, интенты,
события, знания, метрики, решения, доверие, бюджет. **В памяти процесса
(нарушения):** futures вопросов, watchdog-словари (`execution`), анти-цикл
лидеров (`planning_engine._last_leader_sig`), `_office_tasks`, `ctx._cache`
(легален, но **не ограничен** — при 1000 тенантов это утечка). **В промптах:**
остатки — стратегия/ТЗ как текст; правила в policy-.md (легально по §7).
**В коде:** словесные эвристики нового поколения — см. §20.

**Вердикт:** World Model перестала быть «витриной» — на ней стоят
Gap/Decision/Observability. Живость в RAM — признанный, каталогизированный
долг с триггером (multi-process). **Приоритет выноса: по триггеру, не раньше.**

## 5. Поток данных (полный)

Сообщение владельца → `/api/chat` → `office_channel.post` + SSE → фоновый
CEO-триаж: `intent.capture` → (нет брифа → discovery-интейк → бриф → старт
офиса) | (есть → `interpret_directive` LLM → **PlanDiff** →
`decision_engine.decide`: Sandbox-проверки бюджет/артефакт-конфликт/Конституция
→ applied (план мутирует, срез мира фиксируется, decision←prompt_id) |
rejected (причина в ленту и журнал)) → менеджер/цикл видит новую задачу →
`planning_engine.run_leaders` детерминированно назначает свободному воркеру →
`execution.assign` (синхронный захват статуса) → `run_task`: Execution Policy
(модель по задаче) → бюджет-гейт → `prompt_builder.build/task_context` (лог
prompt_id) → `llm.run_agent` tool-loop (маскирование старых observations,
инкрементальный учёт $) → артефакты в `workspace/` → для сайтов: критик
(структурные severity) + ≤2 доработки + автопубликация → `acceptance.check`
L1/L2/L3(/L4) → done | revert(feedback) | 3×→blocked(+чат CEO) → лид с сайта →
`/api/site-lead` (public) → leads + `metrics.collect` → план закрыт →
финальная верификация → `gap.replan` → новая задача ИЛИ проект закрыт с
left_behind + срезом мира. Каждый шаг наблюдаем в `observability.timeline`.

Дыр в потоке не нашёл; единственный обходной путь — `decide_company` (см. §7).

## 6. Planning Engine

**Состояние.** Теперь это модуль, а не «часть loop»: генерация (LLM
`ceo_plan.md` + детерминированный фолбэк), нормализация (роль→исполнимая,
booking-бот→integrator принудительно, чистка deps, **декларации
artifacts/required_capabilities при создании**), исполнение (готовность по
deps, мьютекс по декларации, параллелизм отделов, попытки/блокировки),
пополнение (делегирование, директивы-через-Decision, инициативы, fix-задачи,
**gap-replan**). **Это уже движок, а не эвристики** — порождение остаётся
одноразовым LLM-вызовом, но перепланирование по разрыву существует.

**Плохо:** `gap._work_for_gap` — одна захардкоженная ветка (лиды→marketer);
replan не удаляет/не реприоритизирует существующие задачи (только add).
**BOS:** 🟡→ близко к ✅. **Изменить:** расширять резолвер по мере новых
измеримых целей. **Приоритет: по мере появления целей.**

## 7. Decision Engine

**Детерминированно:** маршрутизация, мьютекс, эскалация приёмки, watchdog,
бюджет-гейты (цикл + пред-исполнение + **пред-решение**), вето Конституции,
закрытие blocker-событий, автостарт tech, gap-replan. **Через LLM:**
содержимое плана/вех, триаж директив (но применение — только через Sandbox),
инициативы, совет директоров, LLM-ревью сайта (не имеет вето — только
рекомендации). **Через if:** классификация рутины, capability-вывод.
**Никак:** приоритизация задач между собой (порядок = порядок в плане);
решение «закрыть проект досрочно».

**Главный остаток:** `decide_company` (open/close/delegate отделов) мутирует
оргструктуру напрямую, мимо `decision_engine` — единственный систематический
обход инварианта §14 п.3. Риск низкий (структурные операции валидируются),
но это дыра в единообразии. **Приоритет: средний, зафиксирован в handoff.**

## 8. Execution Layer

**Состояние.** Полная машина состояний в `execution.py`: Policy выбирает модель
по задаче (оверрайды владельца > рутина→дешёвая > capability роли),
`estimated_cost` сверяется с остатком до старта, лестница исполнителей
проходится воркером через use_skill/use_capability/ask_user. **Плохо:**
лестница §6 по-прежнему неформализована как код policy — «детерминированный
код вместо LLM» решается на уровне подсистем, не задач; `review_and_maybe_fix`
гоняет полный критик+Playwright синхронно внутри исполнения (блокирующие
subprocess-вызовы в event loop). **Приоритет: средний.**

## 9. Prompt System — карта

Все system-промпты — файлы: 3 командные политики + 6 CEO (`ceo_*.md`) +
лидерский + 4 сервисных + 2 онбординга + критик = **18 .md**, собираются двумя
функциями (`build` для воркеров, `company_system` для штабных), каждый лог
получает `prompt_id`, связанный с Decision. Грепом промпт-литералов в `src/`
нет. `chat.py` берёт роли из `roles.render` (+ ограниченная `_SERVICE_PERSONA`
для штабных). **Что ещё должно переехать в мир:** стратегия/ТЗ (режутся
`[:1500]`/`[:3000]` — знание теряется молча); правила из `ceo_plan.md» («не
выдумывай продукт») продублированы вето-проверками лишь частично.
**Это лучшая подсистема проекта: 95% соответствия §7.**

## 10. Memory

GLOBAL (бриф+ответы владельца, из источников) / DEPARTMENT (факты, 60) /
результаты (отдельный журнал) / LESSONS (12×роль) / история чатов (12) /
observation masking в tool-loop. Retrieval — TF-перекрытие с резервом под
иерархию воль. **Отсутствуют:** confidence/decay/summary у фактов, embeddings
(триггеры зафиксированы в спеке), память «между проектами» (lessons живут
per-tenant, не per-project). **Оценка: работает и дёшево; не трогать до
триггеров.**

## 11. Acceptance

L1 (сверка со спецификацией — warn+confidence) + L2 (build по файлам ЭТОЙ
задачи) + L3 (критик со структурной severity; боты — статически) + L4
(business: разрыв открыт → warning) + L5 (непустая сдача). Провал→revert с
фидбеком, 3×→blocked+чат владельца. Watchdog-закрытие тоже идёт через
мини-приёмку. **Доверять результату можно** в границах: «сайт собирается,
форма шлёт, критических проблем нет» — да; «сайт хорош для бизнеса» — только
после накопления метрик. **Отсутствует:** функциональная приёмка ботов (нужна
песочница), непрерывный пост-деплой мониторинг. **Приоритет: L3-боты после
Sandbox-исполнения.**

## 12. Артефакты

**Слабейшее место домена.** Типы (`site`,`bot`,`doc`,`integration`) существуют
как строки-декларации задач; экземпляры — россыпь: файлы workspace (без
владельца), sites.json (ревизии+changelog — хорошо), leads.json. **Нет:**
реестра, owner_project у файлов, depends_on/produced_by/consumed_by, статусов.
Артефакт «бот» вообще не имеет записи о себе после запуска. **Последствие
через год:** мультипроектность невозможна — нельзя ответить «какие артефакты
оставил проект №2». **Приоритет: высокий — следующая крупная сущность.**

## 13. Capability Layer

Реестр `have/missing/available` + acquire-варианты + гейт плана + декларации
задач — верхняя половина §5 появилась. **Плохо:** каталог — захардкоженный
dict на 6 записей, дублирующий знание integrations.registry (новая интеграция
НЕ появится в capability автоматически — нарушение духа «каталог из
метаданных»); `_NEED_WORDS` — снова словесные списки. **Добавить способность:**
интеграция (1 модуль + регистрация) появится в роутере автоматически, но в
capability — только через правку `_CATALOG`. **Изменить:** генерировать
каталог из integrations.registry + skills. **Приоритет: средний, дёшево.**

## 14. Provider Layer

Замена GPT↔Claude↔Gemini — конфиг (OpenAI-совместимый шлюз, `models.json`,
прайс). Замена на локальную модель с OpenAI-API — тоже конфиг. Замена на
**не**-OpenAI-формат: переписать `core/llm.py` (один модуль) + tool-схемы в
`agent_factory` (формат OpenAI functions зашит в 20 определений) +
`costs.PRICES` (привязан к apinet, Billing-provider интерфейса нет).
Бизнес-логика не пострадает. **Оценка: 85% по второму тесту §0.**

## 15. Event System

Доменные события с kind-контрактом, замкнутым детерминированно:
blocker→блок задачи+чат владельца+закрытие при разблокировке;
opportunity→инициативы; problem/signal/info→CEO-гейт с пометкой после показа.
UI-события — отдельная шина (проекция). **Это event-inbox одного потребителя,
не EDA** — подписок нет, и для текущего масштаба это правильно (честно
задокументировано). **Приоритет расширения: низкий.**

## 16. Наблюдаемость

trace+prompts+decisions+world-снапшоты сшиты `prompt_id`/`snapshot_id`;
`decision_chain(did)` отдаёт промпт→решение→trace→world.diff одним запросом;
`timeline` сливает 4 источника. **Невозможно отладить:** worker-цепочку с
точностью до промпта (prompt_id не прошит сквозь run_agent — сшивка по
времени/агенту); всё, что случилось в памяти процесса между рестартами.
**Оценка: сильно выше среднего для проекта этой стадии.**

## 17. Безопасность — самый жёсткий раздел

- **Tenant isolation данных — образцовая** (ContextVar + файлы, ни одной
  глобали с данными).
- **НО: `/api/terminal` и `execute_code` ломают изоляцию исполнением.**
  `run_command(shell=True)` любого аутентифицированного пользователя
  выполняется с правами процесса сервера:
  `cat ../../<чужой-tenant>/connections.json` (Fernet-ключи), чтение `.env`,
  `python -c` с полным доступом к ФС. cwd — не песочница. Для
  однопользовательской беты приемлемо; **для мультиарендного SaaS —
  критическая уязвимость №1.** То же касается агентского кода (`execute_code`
  запускает написанный LLM python без изоляции).
- `APP_SECRET` в .env — дефолтная строка «dev-change-this…» → подделка сессий
  + расшифровка секретов при утечке диска.
- Атомарность: `write_json` атомарен (tmp+replace), карантин битых файлов
  есть; **транзакций между файлами нет** (plan+agents+events обновляются
  раздельно — рассинхрон при падении между записями возможен, компенсируется
  восстановительной логикой первого цикла). Rollback нет; recovery — сбросы
  статусов/revert, работает.

**Приоритет: терминал/execute_code за фичефлаг оператора или в контейнер —
до первого внешнего клиента. Критический.**

## 18. Масштабирование

- **100 компаний:** выдержит. Узкое — синхронные подпроцессы (node --check,
  Playwright, py_compile) в event loop: приёмки начнут задерживать чужие SSE.
- **1000:** упрётся. `ctx._cache` без потолка (вся история всех тенантов в RAM
  с deepcopy на каждое чтение — CPU+память); `state.record` переписывает
  state.json целиком на каждое событие ленты; manager-опрос всех воркспейсов
  каждые 5с; один event loop на все LLM-циклы.
- **10000:** невозможно без шардирования процессов и sqlite/PG. Хорошая
  новость: файловая модель «tenant=каталог» шардируется тривиально, а вынос
  живости уже спроектирован как триггерный долг.

**Приоритет: потолок `ctx._cache` — дёшево и нужно уже при сотнях.**

## 26. Сильные и слабые стороны (взгляд инвестора/платформенного архитектора)

**Сильные.** (1) **Инженерная память** — каждый инвариант привязан к
инциденту, handoff/principles/roadmap ведутся дисциплинированно: это редкость
уровня «единицы процентов проектов», прямое конкурентное преимущество при
найме и передаче. Сохранять любой ценой. (2) **LLM-заменяемость по
построению** — детерминированный скелет с LLM-вставками, а не наоборот;
выдержит смену поколений моделей — визитная карточка категории BOS.
(3) **Observability решений** (промпт→решение→diff мира) — так не умеют даже
зрелые агент-фреймворки. (4) Файловая персистентность tenant=каталог —
недооценена: даёт бесплатный Sandbox Company (копия каталога), тривиальный
бэкап, человекочитаемую отладку.

**Слабые.** (1) Продуктовая петля привлечения не замкнута — офис делает
лендинг, но не приводит трафик; через год это главный вопрос клиентов.
(2) Один процесс = все клиенты; инцидент любого тенанта (OOM от Playwright)
кладёт всех. (3) Экономика прокси — «оценка» честно помечена, но продавать
«растим выручку» на лидах×чеке нельзя. (4) Тестов 11 — приёмочный контур не
защищён от регрессий никак, кроме дисциплины.

**Удивило:** анти-negation в скорере («сайт без 3D»); watchdog, отличающий
«ждёт клиента» от «завис»; мини-приёмка внутри самого watchdog; сшивка
журналов по времени как фолбэк до появления id.

**Переусложнено:** trust/board/initiatives — три UX-механики с собственными
хранилищами при спорной продуктовой отдаче; двойная сайт-приёмка.

**Недооценено:** декларации `task.artifacts` — сейчас служат мьютексу, а
являются заготовкой всей будущей артефакт-экономики; `sandbox.run` — 40 строк,
которые станут основой Sandbox Company без переписывания.

**Три главных риска:** (1) security-изоляция исполнения — вероятность
инцидента при внешних клиентах высокая, последствия фатальные для доверия,
митигируется фичефлагом за день; (2) энтропия эвристик — вероятность высокая
(уже происходит), митигируется правилом ревью «новый `_WORDS`-список =
обоснование в PR»; (3) капкан прокси-метрик — средняя вероятность, что
gap-петля будет оптимизировать лиды, а не бизнес; митигируется интеграцией
хотя бы одного реального источника выручки.

**Если бы проект был моим:** не менял бы — ядро цикла, prompt-архитектуру,
файловую модель, дисциплину документов; переписал бы — server.py на роутеры,
capability-каталог на derived; отложил — embeddings, sqlite, мультипроектность
до Artifact-реестра; начал немедленно — изоляцию исполнения и CI.

**Финальная честная оценка:** зрелость архитектуры **7/10** (для стадии —
исключительно высоко; минус за тесты/безопасность исполнения). Отличие от
«обычных AI-агентов» — категорийное: это операционный цикл с приёмкой и
измерением, а не чат с инструментами. Шанс на категорию BOS — реален, при
условии закрытия петли привлечения. Уникальное: decision-as-diff с
детерминированным вето; наблюдаемость мышления; инженерная память.
Стандартное: tool-loop, retrieval, SSE, мультиарендность на ContextVar.
Как инвестор — да, заинтересовал бы: техническая база опережает продуктовую
упаковку, это правильная асимметрия для seed. Как CTO — согласился бы: редкий
случай, когда предстоит строить на фундаменте, а не разгребать. Самое
сильное — детерминированное ядро + культура фиксации знаний; самое слабое —
безопасность исполнения кода. **Одним предложением:** дисциплинированно
построенная файловая BOS с детерминированным скелетом и заменяемым LLM-мозгом,
которой до продукта не хватает изоляции исполнения, замкнутой петли трафика и
реестра артефактов — и ни одна из этих трёх вещей не требует переписывания
того, что уже есть.
