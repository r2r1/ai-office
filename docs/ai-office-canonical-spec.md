# Часть 1. Vision

## 1.1 Фундаментальная проблема

Владелец малого/среднего бизнеса живёт в состоянии **когнитивного дефицита**: он
одновременно продукт-менеджер, маркетолог, продавец, финансист и HR. У него нет
недостатка в инструментах — у него недостаток в **понимании** («что происходит в
моём бизнесе и что делать дальше») и в **исполнительной мощности** («кто это сделает»).

Все существующие категории софта решают куски этой проблемы, и ни одна — её саму:

**Почему AI-чаты недостаточны.** Чат — это сессия. Он ничего не помнит о бизнесе
между разговорами, не действует сам, не несёт ответственности за результат. Чат
отвечает на вопросы; бизнесу нужен субъект, который сам задаёт правильные вопросы.
Главный дефект чата — вся работа по «сборке контекста» остаётся на человеке:
каждый разговор начинается с пересказа компании заново.

**Почему агенты недостаточны.** Агент (Devin, Manus, OpenHands) — исполнитель
задачи. Ему нужна поставленная задача, и его мир заканчивается на её границе.
Рынок 2026 показал: агенты отлично закрывают «сделай X», но никто из них не
отвечает на вопрос «а что вообще нужно делать?». У агента нет модели бизнеса —
есть контекст задачи. Ответственность за декомпозицию цели в задачи, за
приоритеты, за «мы вообще туда идём?» остаётся на человеке.

**Почему workflow недостаточны.** n8n/Zapier автоматизируют то, что человек уже
придумал и формализовал. Workflow — это застывшее решение: он не замечает, что
мир изменился, не предлагает новых цепочек, не понимает «зачем». Workflow-платформа
масштабирует руки, но не голову.

**Почему CRM недостаточны.** CRM (и вообще системы записи — ERP, таск-трекеры,
Notion) хранят то, что в них внесли. Это зеркала: они отражают бизнес настолько,
насколько человек дисциплинированно их ведёт. Они не порождают понимания и не
действуют. Пустая CRM — самый честный артефакт этой категории.

**Почему нужен именно автономный офис.** Потому что проблема владельца — не
«нет инструмента», а «нет второй головы и вторых рук, которые постоянно держат
в уме весь бизнес». Решение должно объединять четыре свойства, которые ни одна
категория не даёт вместе:

1. **Постоянная модель бизнеса** (а не сессионный контекст) — знание накапливается.
2. **Собственная инициатива** (а не ожидание задач) — система действует первой.
3. **Реальное исполнение** (а не советы) — код, сайты, сообщения, лиды.
4. **Заслуживаемое доверие** (а не бинарный «автопилот») — автономия растёт с результатами.

## 1.2 Ответ на вопрос «зачем, если есть все эти продукты»

После исследования рынка ответ формулируется одной оппозицией:

> **Все существующие продукты организованы вокруг работы. AI Office организован
> вокруг компании.**

Cursor/Claude Code/Devin — вокруг кодовой базы. Linear — вокруг задач команды.
n8n — вокруг процесса. Lovable/Bolt — вокруг артефакта (приложения). Perplexity —
вокруг вопроса. У каждого единица смысла — «работа»; компания существует лишь как
контекст в голове пользователя.

AI Office делает **компанию** первоклассной сущностью системы: Company World Model —
постоянно растущая, измеримая, версионируемая модель бизнеса — является источником
задач, критерием приёмки и накопителем опыта. Работа — производная от модели мира,
а не наоборот. Это и есть moat: артефакт, который дорожает со временем
(как кодовая база у Cursor или граф знаний у Notion), но принадлежит домену,
где ни один из 22 исследованных продуктов не строит ничего накопительного.

Второй структурный ответ: все agentic-продукты 2026 обслуживают **технических
пользователей** или требуют, чтобы пользователь сам формулировал задачи. Сегмент
«владелец SMB, который не хочет управлять системой» — самый быстрорастущий по
принятию AI (42% SMB в 2026 против 23% в 2024) — остаётся без продукта, который
берёт на себя саму функцию управления.

## 1.3 Формула продукта

**AI Office — операционная система компании: постоянно работающий автономный
офис, который понимает бизнес лучше, чем он понимает себя сам, и превращает это
понимание в выполненную работу.**

Из формулы следуют три несводимых слоя продукта (и это — верхний уровень всей
архитектуры):

```
┌─────────────────────────────────────────────────────┐
│  UNDERSTANDING   Company World Model + Understanding │  ← moat
│                  Engine: что офис знает и почему      │
├─────────────────────────────────────────────────────┤
│  DECISION        Autonomous Engine: цели → гипотезы  │  ← мозг
│                  → инициативы → решения → планы       │
├─────────────────────────────────────────────────────┤
│  EXECUTION       Work Engine + Agents + Capabilities │  ← руки
│                  реальные артефакты, приёмка, уроки   │
└─────────────────────────────────────────────────────┘
```

Каждый слой заменяем независимо (LLM — деталь реализации слоёв 2–3, не архитектуры).
Продукт жив, пока верхний слой накапливает ценность даже при простое нижних.

# Часть 2. Product Philosophy

Принципы разбиты на пять групп. Каждый принцип — проверяемое правило для ревью
фич («нарушает/не нарушает»), а не лозунг.

## 2.1 Автономия

1. **AI действует первым.** Дефолт любого экрана и любого цикла — офис уже что-то
   сделал или предлагает сделать; пользователь реагирует, а не инициирует.
2. **Пустой экран — баг.** Если офису нечего показать, он обязан показать, что
   он сейчас узнаёт/делает, или честно объяснить, чем заблокирован.
3. **Вопрос пользователю — дорогая операция.** Каждый `ask_user` тратит доверие.
   Спрашивать можно только то, что нельзя узнать самостоятельно дешевле.
4. **Автономия зарабатывается, не выдаётся.** Уровни scout → guided → trusted →
   autonomous; движение вверх — через результаты (trust), вниз — мгновенно по
   желанию владельца. (Реализовано: `autonomy.py`, `trust.py` — сохранить.)
5. **Просьба сделать руками запрещена.** У агента есть инструмент — он его вызывает;
   нет доступа — запрашивает доступ, а не работу.
6. **Ничего внешне-видимого без мандата.** Публикация, рассылка, пуш кода — через
   governance-гейт (Конституция + автономия), детерминированный, не «промптовый».

## 2.2 Понимание

7. **Контекст важнее задач.** Задача без модели мира — источник мусорной работы;
   лучше цикл потратить на понимание, чем на исполнение вслепую.
8. **Компания важнее документов.** Знание живёт в World Model, документы — проекции.
   Стратегия.md — снимок рассуждения, а не источник истины.
9. **Факт ≠ оценка ≠ слова клиента.** У каждого знания есть происхождение и
   уровень доверия; решение на оценке не имеет права выглядеть уверенным, как на
   факте. (Уже проведено в `metrics.py` — расширить на всё знание.)
10. **Офис сомневается вслух.** Низкая уверенность — это состояние, которое видно
    в UI и влияет на поведение (осторожные действия, проверка гипотез), а не
    внутренний флаг.
11. **Знание должно устаревать.** У фактов есть срок жизни и события-инвалидаторы;
    модель мира без забывания — свалка.
12. **Понимание измеримо.** Understanding Score и Confidence — продуктовые метрики
    первого класса; рост понимания — самостоятельная ценность, за которую офис
    вправе тратить циклы.

## 2.3 Работа

13. **Реальный результат, а не пересказ.** Артефакты создаются инструментами;
    текст в чате результатом не является. (Инвариант `policies/team.md` — сохранить.)
14. **Сдача ≠ приёмка.** Задача закрыта только пройдя приёмку; «выглядит готовым» —
    не статус. (Реализовано: `acceptance.py` — сохранить и углублять уровни.)
15. **Работа бывает трёх видов и они не смешиваются:** Project (завершается),
    Process (не завершается никогда), Initiative (идея до решения). Разные
    жизненные циклы — разные сущности. (BOS §5 — сохранить.)
16. **План всегда существует.** LLM упала — есть детерминированный fallback;
    офис без плана уходит в хаос. (Реализовано — сохранить.)
17. **Каждое действие имеет цену до исполнения.** Execution Policy оценивает
    стоимость и выбирает модель по задаче; бюджет — жёсткий гейт.
18. **Провал — это данные.** Провал приёмки порождает фидбек исполнителю и урок
    роли; третий провал — эскалация, а не бесконечный цикл.

## 2.4 Отношения с пользователем

19. **Пользователь не управляет системой — он работает рядом с ней.** Интерфейс
    проектируется как отношения с командой, не как панель управления машиной.
20. **Указания клиента — закон.** Прямая просьба главнее стратегии, ТЗ и планов;
    «не BotsBox» — запрет, а не рекомендация. (Инвариант — сохранить.)
21. **Каждое решение объяснимо.** «Почему?» доступно у любого решения: варианты,
    уверенность, риски, использованные данные. (Реализовано: `decisions.py`.)
22. **Офис должен удивлять — предсказуемо.** Вау-эффект («мы уже изучили ваш сайт»)
    — фича первых минут; в долгой жизни ценится обратное: отсутствие сюрпризов
    во внешне-видимых действиях.
23. **Уважение ко времени — асимметрично.** Офис может потратить час своих циклов,
    чтобы сэкономить минуту владельца, и не наоборот.
24. **Плохие новости — первыми.** Блокеры, провалы и перерасход бюджета видны
    раньше и заметнее успехов.

## 2.5 Платформа и инженерия

25. **Развязка через реестры.** Новый провайдер способности/скилл/тип результата/
    артефакта подхватывается регистрацией, без правки потребителей. (Проведено
    в `tool_router`, `skills`, `results`, `artifact`, `process_instances` — это
    главный внутренний паттерн, возвести в закон платформы.)
26. **«Как делать» живёт в скиллах, «кто я» — в ролях.** Плейбуки заменяемы и
    устанавливаемы; роли стабильны.
27. **LLM — заменяемая деталь.** Ни одна архитектурная граница не должна проходить
    внутри промпта; всё детерминируемое — детерминировано (вето, гейты, fallback).
28. **Весь промпт собирает один компилятор.** Prompt Builder — единственная точка
    сборки контекста; каждый собранный промпт логируется. (Сохранить.)
29. **Мультиарендность без глобалей.** Всё состояние тенанта — через контекст;
    один процесс — много изолированных миров. (Сохранить, вынести живость из RAM.)
30. **Наблюдаемость — часть продукта, а не операций.** Журнал срезов мира,
    решения, промпты, расход — это и есть материал для «Почему?» и обучения.

# Часть 3. Mental Model

## 3.1 Чем продукт НЕ является

Не приложение (его не «открывают, чтобы поработать»), не панель управления
(нечем управлять — офис управляет собой), не таск-менеджер (задачи создаёт
преимущественно сам офис), не CRM (данные собирает сам офис), не чат (чат — лишь
один из каналов связи с сотрудниками).

## 3.2 Чем является: «компания-в-компании»

Ментальная модель пользователя: **«я нанял управляющую команду, которая работает
круглосуточно и отчитывается мне»**. Из неё следуют все интерфейсные метафоры:

- Заходить в AI Office — как **зайти в офис к своей команде**: увидеть, кто чем
  занят, что произошло без тебя (Morning Digest), что требует твоего решения.
- Общаться — как **с сотрудниками**, а не с ботом: у ролей есть имена, зоны
  ответственности и право сказать «это вопрос не ко мне, спрошу маркетолога».
- Управлять — как **совет директоров**, а не как оператор: владелец задаёт
  философию (DNA), конституцию (что нельзя), цели (Objectives) и принимает/
  отклоняет инициативы. Он не раздаёт задачи — он выражает намерения (Intent).
- Доверять — как **новому подрядчику**: сначала смотреть каждое действие,
  потом отпустить.

Изометрический офис — не украшение, а носитель этой модели: он делает труд
видимым («агент сидит за столом и думает») и превращает абстрактный демон-цикл
в место, куда можно «зайти». Это ответ продукта на главный риск категории —
недоверие к чёрному ящику.

## 3.3 Три вопроса, на которые продукт отвечает всегда

Любой экран в любой момент должен позволять ответить за ≤5 секунд:

1. **Что офис знает о моём бизнесе?** (Understanding)
2. **Что офис сейчас делает и почему?** (Decision + Work)
3. **Что офису нужно от меня?** (вопросы, одобрения, доступы)

Если экран не служит ни одному из трёх вопросов — его не должно быть.

# Часть 4. Company World Model

Сердце продукта. Текущая реализация (`world.py` — SSOT-агрегатор со snapshot/diff)
— правильный фундамент v1; эта часть задаёт целевую модель v2, которая её
надстраивает, не ломая.

## 4.1 Определение

**Company World Model (CWM)** — версионируемое, типизированное, измеримое
представление всего, что офис знает о компании и её окружении. Формально:

```
CWM = (Identity, State, Knowledge, Trajectory)

Identity   — кто мы: DNA (философия+конституция), бриф, ниша, аудитория
State      — где мы сейчас: метрики, артефакты, план, команда, бюджет, блокеры
Knowledge  — что мы знаем: факты, гипотезы, уроки, наблюдения (с провенансом)
Trajectory — куда идём и как шли: цели, разрывы (gap), журнал срезов, решения
```

Identity и State уже собраны в `world.snapshot()`. Knowledge сегодня размазан
(knowledge.json, lessons.json, memory, brief.scan) — v2 подводит его под единый
контракт факта. Trajectory собрана наполовину (snapshots + decisions есть,
связность «решение → diff мира» есть, петля обучения — нет).

## 4.2 Единица знания: Fact

Каноническая форма любого элемента Knowledge:

```jsonc
{
  "id": "f_9c2e",
  "statement": "Средний чек клиента ≈ 40 000 ₽",   // одно утверждение
  "kind": "fact | estimate | hypothesis | lesson | observation",
  "domain": "business | marketing | sales | finance | team | product",
  "provenance": {                                   // откуда знание
    "source": "owner_said | scanned | measured | inferred | researched | outcome",
    "ref": "intent:in42 | scan:2026-07-01 | metric:leads_7d | decision:d_11",
    "at": 1789000000
  },
  "confidence": 0.35,        // 0..1, из веса источника (см. Часть 5)
  "ttl": "P90D | null",      // срок годности; null = инвалидация только событием
  "invalidated_by": ["site_changed", "owner_correction"],  // события-инвалидаторы
  "supersedes": "f_1a07",    // конфликт решён: это утверждение заменило старое
  "emb": [...]               // эмбеддинг для retrieval (считается при записи)
}
```

Правила жизненного цикла:

- **Появление.** Факт создаётся только с провенансом. Анонимное знание запрещено —
  это уже закон в metrics.py («факт|оценка»), распространяем на всё.
- **Обновление.** Новое утверждение о том же предмете не редактирует старое, а
  создаёт запись с `supersedes` — история рассуждений сохраняется, retrieval
  видит только актуальную версию.
- **Конфликт.** Два живых факта противоречат → офис обязан (в порядке дешевизны):
  (1) сравнить confidence и провенанс — измеренное бьёт сказанное, свежее бьёт
  старое; (2) если веса сопоставимы — создать задачу верификации (проверить самому);
  (3) если верифицировать нельзя — спросить владельца одним вопросом с обоими
  вариантами. Конфликт никогда не решается «молча взяли последнее».
- **Устаревание.** По TTL факт деградирует в статус stale (confidence × 0.5, в
  промпт попадает с пометкой «возможно устарело»), затем архивируется. События-
  инвалидаторы (смена сайта, явная поправка владельца) убивают факт немедленно.
- **Гипотеза → факт.** `hypothesis` — единственный kind, который офис создаёт из
  рассуждения без внешнего источника. Гипотеза не участвует в решениях с внешним
  эффектом, пока не подтверждена измерением/проверкой (тогда kind → fact,
  provenance.source → outcome) или не опровергнута (архив + урок).

## 4.3 Snapshot, Diff, Journal (сохранить и развить)

Механика v1 остаётся канонической:

- `snapshot()` — детерминированный полный срез CWM, кешируется на цикл;
- `diff(a, b)` — плоское сравнение срезов; фундамент Sandbox («решение проверяется
  на копии среза, merge — применение diff») и Observability («что изменило это
  решение»);
- журнал срезов (`world_snapshots.jsonl`) + связка decision → snapshot_id.

v2 добавляет: (1) секцию `knowledge` в снапшот (сводные счётчики + топ-факты по
доменам, не всё хранилище); (2) **causal chain** — материализованная цепочка
`intent → decision → plan_diff → world_diff → outcome`, которая сегодня
восстановима только вручную по трём журналам. Это ключ к Части 6 (обучение).

## 4.4 Knowledge Graph — эволюция, не революция

Полноценный граф знаний (узлы-сущности, рёбра-отношения) — Version 3 (Часть 16).
До него доводить нельзя: текущий масштаб знаний (десятки фактов на тенанта) не
окупает графовую машинерию, а `supersedes`/`domain`/эмбеддинги уже дают 80%
пользы. Критерий перехода к графу: retrieval начинает систематически промахиваться
из-за отсутствия связей «факт о клиенте X ↔ сделка X» — то есть когда появятся
интеграционные данные объёмом в тысячи сущностей (CRM-синхронизация).

## 4.5 CQRS-закон (сохранить дословно)

Query — только `world.py`; Command — модуль-источник. Нужен новый факт в промпте —
это новое поле снапшота, а не ad-hoc чтение источника в обход агрегатора. Нужно
изменить мир — правь модуль-источник. Этот закон уже предотвращает главный
системный риск (два места по-разному собирают один факт) и не подлежит пересмотру.

# Часть 5. Company Understanding Engine

Understanding Engine — подсистема, которая превращает сырые сигналы в Facts CWM
и измеряет качество понимания. Текущие компоненты: `company_scan.py` (Instant
Learning), `understanding.py` (score + confidence + чек-лист), `investigation.py`
(живое CEO-интервью), `knowledge.py` (retrieval). Целевая модель собирает их в
явный конвейер.

## 5.1 Конвейер понимания

```
Источники → Ingestion → Нормализация в Fact → Верификация/Конфликты
          → CWM.Knowledge → Gap Analysis понимания → Задачи на изучение
```

## 5.2 Источники данных и их вес (Confidence по провенансу)

Вес источника — единая таблица (сегодня зачатки в `understanding._confidence`):

| Источник | source | Базовый confidence | Пример |
|---|---|---|---|
| Измерено самим офисом | measured | 0.9 | лиды с собственного лендинга |
| Подтверждённый исход решения | outcome | 0.85 | «оффер Б конвертит лучше А» |
| Автоскан/интеграция (реальные данные) | scanned | 0.7 | CMS/аналитика на сайте, CRM-выгрузка |
| Внешнее исследование | researched | 0.5 | web-ресёрч рынка |
| Слова владельца | owner_said | 0.45 | бриф, ответы в чате |
| Вывод модели | inferred | 0.3 | гипотеза из рассуждения |

Принципы: (1) проверенное офисом всегда весит больше самоотчёта — уже
сформулировано в `understanding.py`, возводится в закон; (2) слова владельца —
закон для **ограничений** («не BotsBox» = confidence 1.0 как правило поведения),
но лишь сигнал для **фактов о мире** («у нас конверсия 10%» — 0.45, проверить);
(3) confidence факта может только расти через верификацию, не через повторение.

## 5.3 Слои обучения

- **Instant Learning** (есть, `company_scan.py`) — $0-скан сайта в онбординге:
  соцсети, CMS, аналитика, CTA, контакты. Вау-эффект первых секунд. Развитие:
  скан конкурентов из выдачи, повторный скан по расписанию (инвалидатор
  `site_changed`).
- **Interview Learning** (есть, `investigation.py`) — агентский диалог CEO: сам
  решает, спросить или найти через web_search, завершает брифом с confidence.
  Развитие: интервью не одноразовое — Understanding Gap порождает микро-вопросы
  порционно (не более одного за digest).
- **Infrastructure Learning** (частично) — знания из подключённых интеграций:
  CRM-стадии, календарь занятости, письма → факты с source=scanned. Каждая новая
  интеграция обязана декларировать, какие факты она умеет добывать (расширение
  контракта `Integration`).
- **Behavior Learning** (нет) — наблюдение за поведением владельца: что он
  правит в артефактах, какие инициативы отклоняет, на какие вопросы не отвечает.
  Отклонение — сигнал о вкусе; правка — урок исполнителю. Источник inferred-фактов.
- **Outcome Learning** (половина) — замыкание причинной цепочки: решение →
  diff мира → метрики через N дней → факт/урок. Механика срезов есть; петли
  «через N дней вернись и посмотри» нет — это главный недостроенный контур (§6.5).

## 5.4 Gap Analysis понимания

Симметрично `gap.py` (разрыв до целей) вводится **Understanding Gap** — разрыв
знаний: по каждому домену чек-листа (`understanding._checklist`) непокрытый пункт
с высокой ценностью для активных решений порождает работу «узнать» (скан,
ресёрч, интеграция, вопрос) с оценкой стоимости. Понимание перестаёт быть
пассивным индикатором и становится источником задач — это то, что отличает
«офис изучает компанию постоянно» от «офис заполнил бриф один раз».

## 5.5 Метрики движка

- **Understanding Score** (широта, 0–100) и **Confidence** (достоверность) — есть,
  сохранить разделение.
- **Freshness** (новое) — доля живых фактов моложе своего TTL.
- **Verification rate** (новое) — доля owner_said-фактов, подтверждённых проверкой.
- Цель продукта: рост Confidence без роста числа вопросов владельцу.

# Часть 6. Autonomous Engine

Как офис думает. Целевая модель — явный кибернетический цикл (BOS §3), в котором
каждая стадия — отдельный, тестируемый компонент.

## 6.1 Цикл принятия решений

```
        ┌──────────────────────────────────────────────┐
        │              Company World Model             │
        └───────┬──────────────────────────────▲───────┘
                │ snapshot                     │ facts/lessons
                ▼                              │
  Sense ──► Orient ──► Hypothesize ──► Decide ──► Act ──► Measure
  (events,  (gap:      (initiatives,   (Sandbox:  (Work    (metrics,
   intents,  цели и     research)       propose→   Engine)   outcome
   metrics)  понимание)                 check→apply)          learning)
```

- **Sense.** Входы: события отделов (`events.py`), намерения владельца
  (`intent.capture` — единый вход, сохранить), метрики, вопросы/ответы.
- **Orient.** Gap Analysis по целям (`gap.py`) + Understanding Gap (§5.4) +
  Business State. Выход — ранжированный список разрывов.
- **Hypothesize.** Разрыв → гипотеза о причине → инициатива с обязательной
  стадией research (есть: `initiatives.py`, researching → pending →
  accepted/rejected; отрицательный вердикт research блокирует accept без
  override — сохранить, это редкая на рынке честность).
- **Decide.** Решение — транзакция: PlanDiff через propose → check → apply|reject
  (есть: `decision_engine.py` + `sandbox.py`). Вето детерминированные: бюджет,
  Конституция, конфликт артефактов, запрещённые конструкторы. LLM предлагает —
  правила решают. Записывается в `decisions.py` с альтернативами, уверенностью,
  рисками.
- **Act.** Work Engine (Часть 7).
- **Measure.** Срез мира после применения, diff «до/после» привязан к решению.

## 6.2 Риски

Оценка риска решения — детерминированная функция, не мнение модели:
risk = внешняя видимость × необратимость × цена. Внешне-видимое и
необратимое (рассылка по живой базе) требует мандата всегда; внутреннее и
дешёвое (write_file) — никогда. Текущая карта action-типов в `autonomy.py` —
v1 этой функции; v2 добавляет измерение «необратимость» (публикацию сайта можно
откатить, письмо — нет → письмо строже при равной видимости).

## 6.3 Отмена решений

У каждого применённого решения — определённый способ отката: PlanDiff обратим
по построению (задачи снимаются), артефакты версионируются (`sites.revision`),
внешние действия — компенсируются (follow-up) или помечаются необратимыми.
Кнопка «отменить» у решения в UI — обязательство архитектуры, а не фича.

## 6.4 Планирование

CEO не оптимизирует всё сразу; на цикл — ОДНО решение компании (сохранить: это
антихаос-инвариант) + маршрутизация лидерами. Приоритет разрывов: блокеры >
явные Intent владельца > цели по priority > понимание > гигиена.

## 6.5 Обучение (замыкание петли) — главный недостроенный контур

Через N дней после решения планировщик создаёт задачу Measure: сравнить метрики
с expected_effect из `decisions.py`. Исход: (1) эффект достигнут → урок
«подход работает», trust растёт; (2) нет → урок + гипотеза о причине; (3) хуже →
предложение отката. Так `lessons.py` начинает пополняться из исходов бизнеса,
а не только из провалов приёмки, и Trajectory CWM становится обучающей выборкой.

# Часть 7. Work Engine

## 7.1 Иерархия работы (BOS §5 — сохранить, достроить связки)

```
Intent (воля до интерпретации)
  └─► Objective (измеримая цель; measured_by + резолвер)
        └─► Initiative (идея до решения; research-гейт)
              └─► Project (завершимая работа; left_behind при закрытии)
                    └─► Task (атом исполнения; role, deps, done_criterion)
        └─► Process (незавершимая работа: recurring / instance-поток)
```

Правила: у каждой Task есть Project; у каждого Project — Objective или явное
«гигиена»; Process порождает Task-и по кадансу (сегодня every_cycle; v2 — cron-
выражения, когда появится реальная потребность). Instance-потоки (продажи,
тикеты) — через `process_instances.register()` (сохранить: leads.py как первая
специализация — правильный образец).

## 7.2 Task lifecycle

```
queued → assigned → in_progress → submitted → [Acceptance] → done
                         │                        │ fail(feedback)
                         │ stuck (watchdog)       ▼
                         ▼                    retry (до 3) → blocked + событие
                       healed/requeued
```

Сохранить: `last_feedback` виден при переназначении; 3 провала → блокер, не цикл;
watchdog по AGENT_MAX_THINK_SECS. Достроить: состояние живости — в мир (файл),
не в RAM процесса (признанный SSOT-долг `execution._thinking_since`).

## 7.3 Acceptance — пять уровней (BOS §9)

L1 build (компиляция py/js — есть) → L2 functional (критик сайта/бота — есть) →
L3 specification (соответствие контракту `specification.py` — есть базово) →
L4 business (артефакт служит цели: правильная ниша/оффер — частично, LLM-ревью
критика) → L5 outcome (изменил ли метрики — это §6.5). Вердикт пишется в задачу;
«done = непустая строка» запрещён навсегда.

## 7.4 Scheduling / приоритеты / ресурсы

- Очередь на роль (MAX_PER_ROLE=1 — сохранить: единая ответственность важнее
  ложного параллелизма); занят → ждём.
- Приоритет задач наследуется от приоритета разрыва (§6.4); блокер-фиксы вне
  очереди.
- Ресурсы = бюджет: Execution Policy до запуска (модель по задаче: рутина —
  дешёвая, оверрайды владельца главнее; `estimate_cost`; capability-гейт плана —
  недостающие доступы видны сразу). Всё есть — сохранить.

## 7.5 Dependency / Execution Graph

План-граф (`plan.py`: id, role, deps, done_criterion) — сохранить. Достроить:
готовность задачи = deps done ∧ capability доступна ∧ бюджет позволяет; фронт
рисует граф из того же источника (`/api/plan`), никакой второй модели графа.

# Часть 8. Agent Architecture

## 8.1 Оргмодель (сохранить)

CEO (структура и цели отделам, не задачи людям) → лидеры отделов (распределение)
→ работники (исполнение). Сервисные роли вне отделов: researcher, strategist,
architect, hr. Слово «агент» — только внутренний термин; в UI — роли и
исполнители.

## 8.2 Разделение «кто/как/чем» (главный закон слоя)

- **Роль** (`builtin_roles/*.md`) — кто я, миссия, границы, что нельзя.
- **Скилл** (`builtin_skills/*.md`, `skill_store.py`) — как делать; выбирается
  через use_skill(потребность), каталог подмешивается динамически по роли.
- **Способность** (`tool_router.use_capability`) — чем делать; интеграцию
  выбирает роутер по описанию потребности словами.

Тройка «роль/скилл/способность» — это API платформы (Часть 14); менять её
формат — только через RFC.

## 8.3 Коммуникация

- Отделы не дёргают друг друга: событие → CEO интерпретирует (сохранить).
- Точечное знание — ask_colleague(role, вопрос) (есть; пример: стиль сайта у
  маркетолога — правильный паттерн, закрывший «AI-дефолтную палитру»).
- Общий чат офиса — broadcast для владельца; личные треды — вопросы/беседы.

## 8.4 Разрешение конфликтов

Конфликт исполнителей (два отдела претендуют на артефакт) — детерминированное
вето Sandbox (конфликт артефактов) + решение CEO следующим циклом. Конфликт
знаний — §4.2. Конфликт с владельцем невозможен по построению: указания клиента
— закон (инвариант 20).

## 8.5 Контекст работника

`prompt_builder.task_context` — единственный сборщик: бриф (с подписью
goal ≠ niche — выстраданный инвариант, сохранить), указания клиента, ТЗ,
retrieval-факты, уроки роли, дайджест отдела, скиллы по роли. Новый слой
контекста = новый слот билдера. Полный лог в prompts.jsonl.

# Часть 9. Memory Architecture

Память — не один сторадж, а семейство с разными законами жизни. Целевая карта
(в скобках — текущий носитель):

| Тип | Что хранит | Закон жизни | Сегодня |
|---|---|---|---|
| Working | контекст текущей задачи | живёт цикл задачи | tool-loop `llm.py` + task_context |
| Company (semantic) | Facts CWM о бизнесе | provenance, TTL, supersedes | `knowledge.json` (v1, без TTL) |
| Decision | решения+альтернативы+исход | append-only, связка со срезами | `decisions.py` + `world_snapshots.jsonl` |
| Procedural | как делать (плейбуки) | версионируемые .md, устанавливаемые | `builtin_skills/`, `skill_store.py` |
| Behavior | предпочтения владельца | учится по правкам/отклонениям | нет (§5.3) |
| Agent (lessons) | уроки по ролям | last-N, дедуп | `lessons.py` |
| Observation | сырые события/дайджесты | ring-buffer | `state.py`, `digest.py` |
| User directives | указания клиента | закон, не забывается | `memory.py` |

Законы: (1) retrieval — один (`knowledge.retrieve`: резерв под глобальное +
TF+эмбеддинги, деградация к TF без провайдера — сохранить); (2) результаты
работы — не знания (отдельный журнал, низкий вес — выстраданное, сохранить);
(3) каждая память имеет потолок и вытеснение — бесконечных хранилищ нет;
(4) межпамятные переносы явные: outcome → lesson, lesson → fact (если
подтверждён многократно), behavior → directive (если владелец подтвердил).

# Часть 10. UX

## 10.1 Первый запуск (сохранить каркас, ужесточить принцип)

Лендинг → вход → онбординг тремя сценариями (business/launch/idea) → **Instant
Learning по URL до первого вопроса** («мы уже изучили вас») → короткое
CEO-интервью только о том, что не удалось узнать → рождение офиса → BOOTSTRAP
на глазах (ресёрч → стратегия → ТЗ → план). Принцип: к концу первой сессии
владелец видит (а) что офис понял, (б) что офис уже делает, (в) первый вопрос
к нему — не раньше.

## 10.2 Главный экран

«Обзор» — дефолт (есть): здоровье, инициативы-на-решение, прогресс целей,
«что нужно от вас». Правило одной страницы: три вопроса §3.3 закрыты без
скролла. Изометрический офис — второй таб, эмоциональный якорь и живость.

## 10.3 Навигация (7 вкладок — сохранить IA-пересборку)

Офис · Обзор · Работа · Команда · Результаты (реестровые вкладки + ui_prefs) ·
Ресурсы · Настройки. Новые типы результатов появляются регистрацией, не правкой
навигации — закон.

## 10.4 Ключевые сценарии

- **Инициатива:** карточка = заголовок + research-вывод + рекомендация + цена;
  accept/reject одним действием; reject — сигнал Behavior Learning.
- **Вопрос офиса:** блокирующие вопросы — в тредах, дедуп, ответ разблокирует
  задачу немедленно (есть). Порционность: не более одного нового вопроса на digest.
- **Возвращение:** Morning Digest «пока вас не было» + «на чём остановились»
  при автопаузе (есть — сохранить).
- **«Почему?»:** у каждого решения/действия — след до данных (decisions +
  prompts.jsonl + world diff).
- **Память:** владелец видит факты офиса (вкладка знаний), может поправить —
  поправка = директива с confidence 1.0.

## 10.5 Anti-UX (запрещено)

Формы там, где офис может узнать сам; настройки, которые никто не менял

# Часть 11. UI

## 11.1 Дизайн-система

Единая точка — `webapp/src/styles/design.css` (токены) + `app/views/ui.tsx`
(Button/TextInput/TextArea — единственные примитивы форм; инлайн-стили для
кнопок/инпутов запрещены, кроме бренд-заблокированных исключений — закон из

Токены: пространство по 4px-шкале (4/8/12/16/24/32); радиусы sm/md/lg;
поверхности surface/surface-soft/overlay; типографика — системный гротеск,
шкала 13/14/16/20/28; семантические цвета статусов (ok/warn/danger/info) —
единственный источник цветового кодирования статусов задач/агентов/здоровья.

## 11.2 Композиция

Карточка — базовый контейнер смысла (инициатива, решение, вопрос, артефакт):
заголовок → факт-строка → действие. Максимум одно primary-действие на карточку.
Списки виртуализируются после 50 элементов. Плотность — «Linear, не Notion»:
интерфейс для чтения состояния, не для редактирования документов.

## 11.3 Realtime и анимации

SSE — единственный канал живости (есть); все вкладки читают один стейт
провайдера, рефетчи — только throttled (урок шторма DashboardView — закон).
Анимации (motion/react): длительность 150–250ms в UI / до 600ms в сцене офиса;
анимируется появление и смена статуса, не постоянное движение; изометрическая
сцена — единственное место амбиентной анимации. prefers-reduced-motion уважается.

## 11.4 Состояния

Каждый экран обязан определить: loading (скелетоны, не спиннеры), empty
(что офис делает, чтобы это появилось), error (что случилось + что офис
предпримет), partial (данные есть, но confidence низкий — визуально отличимо).

## 11.5 Accessibility

Клавиатурная навигация по карточкам и действиям; контраст AA; статусы кодируются
цветом+иконкой+текстом (не только цветом); фокус-стили из токенов.

# Часть 14. Plugin Platform

Платформенность уже заложена реестрами — это и есть SDK v0:

| Точка расширения | Контракт | Сегодня |
|---|---|---|
| Интеграция (capability provider) | объект INTEGRATION (cred_fields, how_to, actions+schema+handler) | `integrations/*` + registry |

| Тип результата/артефакта | register() + normalize | `results.py`, `artifact.py` |
| Процесс | register(stages, labels) | `process_instances.py` |

Дорога к платформе: (1) **формализовать** эти шесть контрактов как публичный
Extension API с версионированием (semver манифеста); (2) **пакет** — папка
`aioffice-ext-*/` с манифестом, объявляющим любые из шести точек; (3)
**Marketplace** — сначала просто каталог git-репозиториев (как ранний Obsidian/
Raycast), установка per-tenant или глобально; (4) доверие: расширения с кодом —
только в sandbox (Docker), декларативные (.md-скиллы, роли) — свободно;
(5) новая интеграция обязана декларировать добываемые факты (§5.3) — расширения
кормят World Model, а не только руки.

Правило платформы: **ядро (CWM, Decision, Work, Acceptance) не расширяется
плагинами** — расширяются способности, знания и типы результатов. Это защищает
концептуальную целостность от судьбы «всё-конструкторов».

# Часть 16. Roadmap (эволюция, не список задач)

**V1 — «Офис, которому можно доверить сайт и лиды» (сейчас, добить):**

**V2 — «Офис, который учится»:** Fact-контракт с провенансом/TTL (§4.2);
Understanding Gap как источник задач (§5.4); Outcome Learning — петля Measure
через N дней (§6.5); Behavior Learning; durable-очередь отложенных задач;
живость в мир, не в RAM. Критерий: Confidence растёт без роста вопросов,
уроки пополняются из исходов.

**V3 — «Офис как платформа»:** Extension API v1 (шесть контрактов, semver);
каталог расширений; интеграции декларируют добываемые факты; Knowledge Graph
при появлении CRM-объёмов данных; SQLite/FTS под знаниями. Критерий: сторонний
разработчик добавляет интеграцию+скилл без PR в ядро.

**Enterprise / Cloud / Self-hosted:** одна кодовая база, три поставки: cloud
(мультиарендный SaaS — текущее устройство), self-hosted (docker-compose,
DEMO/собственные ключи), enterprise (SSO, аудит-экспорт, изолированные воркеры,
SANDBOX_MODE=docker обязателен). Ветвление поставок — конфигурацией, не форками.

**AI Ecosystem:** офисы обмениваются анонимизированными уроками (opt-in) —
«коллективный опыт» как сетевой эффект; External Workers (kind=external у
скиллов — задел уже есть) — офис делегирует работу другим сервисам/людям через
тот же Acceptance.
