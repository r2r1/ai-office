## 1. Продукт и пользовательские сценарии

### 1.1 Механизм доверия не работает по-настоящему
Подтверждение спецификации перед стартом работ **ничего не блокирует** —
`office/specification.py` прямо называет себя «опциональным действием»,
`office/loop.py` только публикует сообщение о готовой спецификации, бюджет-гейт
идёт своим путём через `costs.would_exceed()` независимо от того, подтвердил
владелец план или нет. Это подрывает главное обещание продукта («офис не
потратит впустую ваши деньги») — технически подтверждения нет, есть только
текст на экране.
**Нужно:** сделать `specification.confirmed` реальным условием старта
исполнения задач проекта (не публикации, а факта старта).

### 1.2 Нет кнопки «Ответить» на блокирующий вопрос агента
`ChatsView.tsx` — вопрос агента (`m.kind === "question"`) помечается лейблом
«· вопрос» и рамкой слева, но поле ввода снизу — обычный `<input>` без единого
визуального отличия «отвечаю на конкретный вопрос» от «пишу новое сообщение».
Пользователь должен догадаться сам.
**Нужно:** когда есть открытый вопрос — явный режим «Ответить на: …» над
полем ввода, компоузер должен визуально показывать, какому вопросу отвечает.

### 1.3 Продукт работает только «на вытягивание», не «на push»
Morning Digest — чисто клиентский поллинг (`GET /api/digest`), нет ни одного
пути наружу (email/Telegram) сообщить владельцу, что офис что-то сделал, пока
его не было. Это прямо противоречит позиционированию «работает без вас» —
узнать об этом можно только вернувшись и открыв вкладку.
**Нужно:** минимум — email/Telegram-уведомление о готовом Morning Digest и о
новом блокирующем вопросе (`ask_user`). Не обязательно строить полноценную
систему уведомлений — достаточно одного канала для двух этих событий.

### 1.4 Нет второго пользователя на один офис
Схема `saas/db.py`: `workspaces.owner_user_id` — ровно один владелец, join-таблицы
для команды нет. Если у клиента есть партнёр/сотрудник, который должен видеть
тот же офис — сценарий отсутствует полностью.
**Нужно:** оценить, нужен ли это для первой волны клиентов (соло-предприниматели
vs команды) — если да, потребуется миграция схемы (`workspace_users`), не только UI.

### 1.5 Мелкий, но реальный визуальный баг
Подписи агентов на изометрической сцене — статичные координаты
(`OfficeView.tsx`, `ROLE_HOME`/`DESKS`), без anti-collision. При нескольких
воркерах у одного стола (параллельные проекты, например два `developer` в
разных проектах) подписи накладываются друг на друга и становятся нечитаемыми.
**Нужно:** разнести позиции или скрывать/сокращать подпись при коллизии.

### 1.6 Метрики «Здоровье» vs «Понимание компании» всё ещё рядом
Две разные шкалы 0-100 показываются пользователю на одном экране. Сейчас есть
поясняющая сноска («не путать со Здоровьем работы выше», `App.tsx`), но два
разных числа рядом по-прежнему требуют лишнего объяснения в интерфейсе, где
должно хватать одного взгляда.
**Нужно:** решить, нужны ли оба числа одновременно, или одно из них должно
жить только «под капотом»/во вкладке диагностики.

## 2. Доверие, данные и монетизация

### 2.1 Нет входа по email + паролю
Сегодня — только GitHub Device Flow и dev-login. Целевой пользователь
(нетехнический владелец бизнеса) может не иметь GitHub-аккаунта вообще — это
стена на входе, не мелочь. `ALLOW_DEV_LOGIN` по умолчанию включён (`"1"`,
`auth.py`) — критично выключить в проде явным образом.
**Нужно:** email+пароль или magic-link как основной способ входа;
GitHub — опциональный (для тех, кто позже захочет пуш кода).

### 2.2 Легал-страниц нет вообще
Не заглушки — полное отсутствие: ни одного файла/страницы terms/privacy во
всём фронтенде, в модалке входа — просто текст про согласие без единой ссылки.
**Нужно:** реальные страницы «Условия использования» и «Политика
конфиденциальности» до первого внешнего пользователя — это не полировка,
а юридическое требование для сервиса с доступом к GitHub-репозиториям и
бизнес-данным клиента.

### 2.3 Нет биллинга
Ноль кода оплаты (Stripe/Paddle/checkout/subscription — 0 совпадений в
репозитории). `workspace.plan` жёстко `"free"` при создании, апгрейда нет.
**Нужно:** минимум — Stripe Checkout на один фиксированный платный тариф,
без сложной логики тарифных сеток на старте.

### 2.4 Нет аналитики поведения пользователей
Ноль совпадений на analytics/mixpanel/amplitude/posthog/gtag во всём
репозитории — узнать, где реальные люди бросают продукт (на онбординге?
на первом результате? при оплате?), сегодня буквально нечем.
**Нужно:** базовая воронка событий (просмотр лендинга → онбординг начат →
онбординг завершён → первый результат увиден → оплата) до следующего раунда
продуктовых решений — иначе они снова вслепую.

## 3. Технический фундамент (не блокирует запуск, но ограничивает рост)

- **Sandbox для исполнения кода не проверен вживую.** `exec_sandbox.py` сам
  признаёт: docker-режим «не проверен живым запуском реального Docker»; по
  умолчанию `SANDBOX_MODE=direct` — без изоляции. Не критично, пока
  `ALLOW_CODE_EXECUTION=0` по умолчанию, но открывать этот флаг в проде
  нельзя до реальной проверки docker-режима.
- **`world.py` (ядро World Model) не имеет ни одного прямого юнит-теста** —
  только косвенное покрытие через `test_loop_heartbeat.py`/`test_planning_engine.py`.
  Регрессии в самом ядре BOS не поймаются автотестами.
- **Rate limiting есть, но в памяти процесса** (`server.py`, свой bucket-лимитер
  на `/api/lead`, `/api/run`, `/api/terminal`, `/auth/*`) — не переживает
  рестарт и не будет работать при горизонтальном масштабировании на несколько
  процессов. Не проблема для одного тенанта сейчас, проблема при росте.
- **`DEV_MODE=1` тихо подставляет небезопасный `APP_SECRET`** — операционный
  риск (не забыть держать выключенным в проде), не архитектурная дыра: без
  `DEV_MODE` сервер сам падает с `RuntimeError` без секрета.

## Порядок действий

Сначала продукт (раздел 1) — это то, что почувствует первый живой пользователь
за первые 10 минут и что либо подтвердит, либо опровергнет ценностное
предложение. Раздел 2 — обязательное условие пустить трафик легально и не
работать бесплатно вслепую. Раздел 3 — не блокирует первую волну клиентов, но
must-fix до попытки масштабировать сверх одного процесса/сотни тенантов.
