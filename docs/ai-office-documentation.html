Документация

Общее об AI-Office

AI-Office — мультиарендный SaaS, в котором у каждого клиента появляется автономный AI-офис: несколько агентов разных ролей самостоятельно ведут его бизнес, а сам офис визуализирован как изометрическая (псевдо-3D) игра в браузере.

Клиент не ставит задачи поштучно — он формулирует цель (через живое интервью с CEO-агентом при онбординге или позже в чате), а офис сам:

  • исследует рынок и формирует стратегию;
  • проектирует техническое решение (ТЗ);
  • разбивает путь к цели на этапы и задачи (план-граф);
  • открывает нужные отделы (tech / marketing / sales / finance) и нанимает специалистов;
  • выполняет задачи реальными инструментами — пишет код в рабочую папку, публикует лендинги, шлёт сообщения через интеграции, собирает живых лидов;
  • задаёт клиенту блокирующие вопросы, когда без него нельзя двигаться дальше;
  • сам платит за свои LLM-вызовы из бюджета тенанта.

Чем это отличается от «AI-ассистента»

Инструменты вроде SUIN.AI или ChatGPT-конструкторов ассистентов требуют, чтобы пользователь сам собрал сценарий: написал системный промпт, вручную подключил базу знаний, вручную позвал ассистента в чат. AI-Office устроен наоборот — пользователь формулирует результат, а какие роли нанять, какие инструменты вызвать и в каком порядке — решает сама система.

Ключевые принципы

  • Автономность — агент вызывает инструмент сам, не просит «сделать руками».
  • Реальный результат — код в файлах, сайты опубликованы, письма отправлены. Текст в чате — не результат.
  • Приоритет указаний клиента — ответы пользователя главнее стратегии и ТЗ.
  • Единая ответственность — на каждую роль один агент одновременно.

Развязка через события и способности

  • Отделы не дёргают друг друга напрямую — сигналят события, CEO интерпретирует.
  • Агент описывает потребность словами (use_capability("опубликовать лендинг")), а какую конкретно интеграцию вызвать — решает роутер.
Язык продукта, UI и коммуникации агентов — русский. Главная архитектурная спецификация проекта — docs/bos-architecture.md (Business Operating System): любой новый код сначала находит своё место там, а уже потом пишется.
Документация / Начало

Начало работы

Шаг 1. Регистрация и вход

  • Вход через GitHub OAuth либо dev-логин (по email без пароля — только в локальной разработке, флаг ALLOW_DEV_LOGIN).
  • Каждому новому тенанту при регистрации автоматически начисляется бонусный бюджет на LLM-вызовы (по умолчанию $5, настраивается через BONUS_BALANCE_USD).

Шаг 2. Онбординг — живое интервью, а не форма

В отличие от классических визардов «заполните 5 полей», здесь с клиентом сразу говорит агент-CEO. Он сам решает — спросить коротко в чате или найти ответ через веб-поиск (например, просканировать сайт компании клиента) — и завершает интервью, только когда уверен, что бриф достаточно полон. Итоговый бриф содержит:

  • niche / audience — что реально продаёт бизнес клиента конечным покупателям;
  • goal — какой результат клиент хочет получить от офиса (это не одно и то же с нишей — офис не должен продавать «услугу автоматизации» вместо того, что продаёт бизнес клиента);
  • business_stage — идея / запуск / рост / зрелый бизнес, с обоснованием и степенью уверенности;
  • confidence — насколько CEO уверен, что собранных данных достаточно, чтобы начинать работу.

Шаг 3. Офис запускается

Как только бриф готов, стартует автономный цикл: исследование рынка → стратегия → техническое задание → план-граф задач → найм агентов по отделам → выполнение. Прогресс виден сразу на вкладке «Обзор».

Шаг 4. Вмешательство по необходимости

Клиент не обязан ничего делать вручную. Он подключается, когда:

  • агент задал блокирующий вопрос (нужен ключ доступа, подтверждение решения) — приходит как обычное сообщение в чат с агентом;
  • хочет посмотреть результат — лиды, сайт, код;
  • хочет дать прямое указание — оно автоматически становится приоритетнее стратегии.
Все данные строго изолированы по тенанту. Никакого общего пространства между клиентами — у каждого свой офис, свои агенты, своя память, свой бюджет.
Документация / Начало

Жизненный цикл клиента

лендинг → авторизация (GitHub / dev-вход) → онбординг (живое интервью CEO)
       → бриф готов → офис-цикл запускается → BOOTSTRAP → циклы CEO
       → результат: лендинг/бот/код в рабочей папке + лиды + платежи

BOOTSTRAP (один раз на тенанта)

  1. Ресёрчер проводит глубокое исследование рынка;
  2. Стратег формирует стратегию бизнеса;
  3. Архитектор пишет техническое задание;
  4. CEO разбивает путь на бизнес-этапы (milestones) и генерирует план-граф задач — если LLM-генерация плана не удалась, берётся детерминированный резервный план, чтобы офис всегда оставался plan-driven, а не скатывался в хаос.

Циклы (раз в интервал опроса)

  1. Проверка, не поставлен ли офис на паузу;
  2. Проверка завершения плана — если всё сделано, офис публикует сайт, делает финальную верификацию, при критических проблемах добавляет задачу на исправление, иначе уходит в режим ожидания;
  3. «Самолечение» зависших агентов (watchdog по максимальному времени размышления);
  4. CEO принимает одно решение за цикл: открыть/закрыть отдел, поставить задачу отделу, подождать;
  5. Лидеры отделов распределяют задачи плана между подчинёнными;
  6. Исполнитель выполняет задачу с подмешанным контекстом (бриф, указания клиента, ТЗ, релевантная память, уроки прошлых прогонов, дайджест отдела).
Документация / Продукт

Офис

Изометрическая псевдо-3D сцена — визуальный якорь бренда: агенты сидят за столами в своих отделах, видно кто чем занят прямо сейчас.

Внутри раздела есть переключение вида: изометрическая сцена и органиграмма (оргструктура компании) — это один и тот же «слепок» компании под разными углами, не два разных раздела.

Оргструктура

CEO (orchestrator)        — структура компании: открывает/закрывает отделы, ставит цели
  ├── tech (CTO)          — продукт, код, боты, сайты
  │     ├── developer     — код (Python/JS)
  │     ├── integrator    — внешние API, запуск ботов
  │     └── designer      — UI/UX, верстка
  ├── marketing (CMO)     — контент, реклама, бренд
  │     ├── marketer
  │     └── analyst
  ├── sales (Head of Sales) — клиенты, переговоры, CRM
  │     └── salesman
  └── finance (CFO)       — учёт, ERP/1С, юнит-экономика
        └── accountant

Сервисные роли (вне отделов): researcher, strategist, architect, hr

CEO не ставит задачи людям напрямую — он ставит цели отделам. Лидер отдела распределяет задачи внутри своей команды. На каждую рабочую роль в моменте — только один агент.

Документация / Продукт

Обзор

Дефолтная вкладка после входа — «за 30 секунд понятно, что происходит с компанией».

  • Здоровье компании — сводный индикатор состояния;
  • Инициативы — что сейчас в фокусе;
  • Прозрачность — что офис сделал, пока клиента не было (утренний дайджест);
  • Индикатор паузы/бюджета — виден статус, если офис приостановлен (например, закончился бюджет на LLM) или ждёт ответа клиента.
Документация / Продукт

Работа

План-граф задач, проекты и артефакты — то, что раньше называлось «Итоги», теперь принадлежит конкретному проекту, а не общему котлу на всю компанию.

Проекты

Проект — единица работы крупнее одной задачи. Задачи плана принадлежат проекту; когда проект закрывается, фиксируется, что офис «оставил после себя» — срез мира на этот момент.

План-граф

Каждая задача имеет id, роль-исполнителя, зависимости от других задач, критерий готовности (done_criterion) и статус. Задача не может быть готова просто потому, что исполнитель написал «готово» текстом.

Артефакты

Код, сайты, документы конкретного проекта — доступны прямо на карточке проекта, а не на отдельной общей вкладке.

Документация / Продукт

Результаты

Реестр типов результата, которые производит работа команды — сейчас Лиды и Сайты, дальше подключится всё, что зарегистрируется в реестре результатов, без правки навигации.

  • Лиды — мини-CRM: живые заявки, собранные с опубликованных лендингов клиента;
  • Сайты — опубликованные лендинги, доступны по публичной ссылке /site/{тенант}/{slug}, с формой сбора лида.

Порядок и видимость под-вкладок персонализируется владельцем поверх того, что доступно в реестре.

Документация / Продукт

Ресурсы

Всё, что офис использует «под капотом», собрано в одном месте — под-вкладки: Хранилище, Доступы, Приложения, MCP-серверы.

Хранилище

Разбивка занятого места по тенанту: папки проектов, системные данные, служебные контейнеры.

Доступы (интеграции)

Любой ключ доступен любому агенту через общий механизм — CEO не выбирает исполнителя «потому что у него есть ключ». Доступные интеграции:

СервисТипНазначение
Websiteбез кредовпубликация лендинга, приём лидов через встроенную форму
Telegram (бот)API-ключотправка сообщений, шаблонный бот записи
Telegram (личный)вход по номеруработа от имени личного аккаунта
GitHubOAuth / PATсоздание репозитория, пуш кода рабочей папки

Если ключа нет — агент никогда не «зависает молча»: он запрашивает доступ у клиента (ask_user) с точной инструкцией — «нажми войти через X» для OAuth-сервисов или «вставь ключ» для остальных. Агент никогда не просит API-ключ там, где сервис работает через OAuth.

Приложения и MCP-серверы

Подключение сторонних инструментов через Model Context Protocol — расширяет набор доступных агентам действий без изменения кода ролей.

Документация / Продукт

Настройки

Под-разделы: Профиль, Цели, Интеллект, Лимиты, Аккаунт.

  • Профиль — данные владельца;
  • Цели — измеримые желаемые состояния бизнеса (Objectives); цель без способа измерения не участвует в анализе разрывов, а становится источником отдельной работы «обеспечить измеримость»;
  • Интеллект — выбор LLM-модели глобально или на конкретного агента;
  • Лимиты — бюджет на LLM-расходы, автопауза при исчерпании;
  • Аккаунт — вход, выход, безопасность.
Документация / Как это работает

Событийный слой и Tool Router

Event Layer

Отделы не дёргают друг друга напрямую. Агент, увидевший проблему или возможность вне своей задачи, публикует событие. CEO на следующем цикле читает накопленные события, интерпретирует их и решает, что делать дальше — сам факт события не означает автоматического действия.

Tool Router — способности вместо интеграций

Агенты не привязаны к конкретным именам интеграций. Вместо прямого вызова конкретного сервиса они формулируют потребность словами:

use_capability("опубликовать лендинг", params)

Роутер собирает каталог способностей из всех подключённых интеграций, скорит кандидатов по словам запроса и словарю синонимов («лендинг» → website, «письмо» → gmail, «таблица» → google_sheets…), и либо выполняет явного лидера, либо возвращает варианты на выбор. Если под капотом сменить интеграцию — агент этого не заметит; новая интеграция подхватывается автоматически.

Документация / Как это работает

Skills-слой

Роль описывает «кто я / что мне нельзя», а «как именно делать» живёт отдельно — в скилле.

Меняется способ работы (например, каким стеком строить сайт) — правится один файл скилла, а не промпт роли. Новый способ выполнения задачи — это новый скилл, роли остаются нетронутыми.

Как воркер выбирает скилл

задача воркеру («сделай красивый лендинг»)
        │
use_skill("3D-лендинг с анимациями")   ← потребность словами
        │
   поиск подходящего скилла по ключевым словам, с фильтром по роли
        │
  уверенный лидер → плейбук скилла, воркер исполняет своими инструментами
  неоднозначно     → топ-N вариантов на выбор воркеру

Каталог скиллов не зашит в промпты ролей целиком — в промпт попадают только скиллы, релевантные конкретной роли, поэтому большой каталог не раздувает контекст агента.

Системный скилл сайта — единая связка React + Vite (настоящая сборка) + Motion для анимаций, доступная ролям дизайнера и разработчика. Дизайн-скилл сознательно не выбирает палитру сам — это решение маркетинга, чтобы сайт не скатывался в один из типовых «AI-дефолтов» дизайна.

Документация / Как это работает

Память и контекст

В задачу каждого работника подмешивается не «всё подряд», а точечно нужный контекст.

  • Бриф клиента — цель, ниша, ограничения;
  • Указания пользователя — приоритет над стратегией и ТЗ;
  • ТЗ архитектора;
  • Трёхслойная память — топ-N фактов, релевантных именно этой задаче:
    • Global — бриф и ответы клиента, высокий приоритет;
    • Department — что уже узнал отдел;
    • Retrieval — подбор по конкретной задаче (гибрид TF-скора и эмбеддингов);
  • Уроки прошлых прогонов по роли исполнителя;
  • Дайджест отдела — что коллеги уже сделали.

Это защищает агента от двух проблем сразу: он не тонет в простыне лишнего контекста и не забывает важное между циклами.

Документация / Как это работает

Приёмка задач

Задача закрывается только приёмкой — сдача исполнителем и приёмка это два разных события.

Результат прогоняется через уровни проверки:

  • Build — компиляция Python/JS, включая инлайн-скрипты на сайтах;
  • Functional — критик проверяет сайт/бота по существу (формы, ссылки, позиционирование);
  • Базовый уровень.

Провал возвращает задачу в очередь с конкретным фидбеком, который видит исполнитель при переназначении. Третий провал подряд блокирует задачу и поднимает событие для CEO. «Done» никогда не принимается просто как непустая строка текста.

Тарифы, кредиты и оплата

Как считается расход

Каждый вызов LLM учитывается инкрементально — сразу после ответа модели, а не по завершении всего прогона. Иначе прерванный или зависший прогон тратил бы реальные деньги, а индикатор расхода в интерфейсе показывал бы $0.

Прайс сверяется с прайсом провайдера apinet.cloud напрямую. Для моделей без явно прописанной цены система не показывает $0 — берётся консервативная оценка (медиана известных цен), чтобы не занижать реальный расход.

Стартовый бонус

Новый тенант при регистрации автоматически получает бонусный бюджет — по умолчанию $5 (настраивается на бэкенде через BONUS_BALANCE_USD; значение 0 отключает бонус). Это единственный «баланс» до появления полноценной платёжной системы.

Пауза при исчерпании бюджета

Когда бюджет тенанта заканчивается или провайдер отвечает ошибкой квоты, офис автоматически ставится на паузу — это видно прямо в верхней панели интерфейса, а не выясняется постфактум по пустому логу.

Полноценного биллинга (тарифные планы, докупка кредитов, автосписание с карты) в системе пока нет — есть только базовый бюджетный лимит и стартовый бонус.
Документация / Деньги и доступ

Админ-панель оператора

Отдельная панель для оператора платформы (не для клиента) — обзор по всем тенантам сразу.

  • Баланс и расход по каждому тенанту;
  • Ошибки прогонов;
  • Пауза/возобновление конкретного тенанта;
  • Per-tenant настройка прокси для исходящих LLM-запросов (нужно, если сервер на IP, который провайдер не принимает напрямую).

Открывается отдельным bearer-токеном (ADMIN_API_KEY), никак не связанным с пользовательской авторизацией; без ключа — 503. Фронт панели — отдельный статический файл, разворачивается на изолированном URL, не часть основного веб-приложения.

Мультиарендность (src/saas/)

Всё, что относится к данным офиса — per-tenant и stateless. Домен-модули читают и пишут файлы через общий контекст тенанта, никаких глобальных словарей состояния — иначе утечка данных между клиентами.

Интеграции (src/integrations/)

Декларативное описание сервиса: нужные креды, инструкция подключения, действия с JSON-схемой и async-обработчиком. Новая интеграция регистрируется в общем каталоге — фронт и Tool Router подхватывают её автоматически, без правки агентов.

Frontend (webapp/)

React + Vite + TypeScript + Motion. Изометрический офис — компонент сцены; SSE-стрим доставляет события в реальном времени в единый стейт приложения. Навигация верхнего уровня сгруппирована по логическому смыслу (Офис / Обзор / Работа / Команда / Результаты / Ресурсы / Настройки), а не по историческому наслоению фич.

Документация / Для разработчиков

Запуск и окружение

pip install -r requirements.txt
python scripts/run.py                # бэкенд + SPA на http://localhost:8000
DEMO_MODE=1 python scripts/run.py    # демо без расхода токенов
python main.py                       # CLI: ресёрчер → стратег, без игры
Не запускать uvicorn server:app --reload напрямую — reload следит за всем деревом, включая рабочие папки тенантов, куда агенты постоянно пишут код. Любая запись файла агентом перезапускала бы сервер и роняла идущий офис-цикл. scripts/run.py включает reload только для исходников.

Frontend для активной разработки: cd webapp && npm run dev.

Проверка перед коммитом

python -m py_compile $(git ls-files '*.py')   # синтаксис Python
cd webapp && npx tsc --noEmit                  # типы React-приложения
python tests/run_all.py                        # юнит-тесты, без LLM, $0
Документация / Для разработчиков

Инварианты — не ломать

  • Автономность. Нужен сервис → проверка доступа → OAuth-подсказка «нажми Войти через X» или запрос ключа с инструкцией. Никогда не просить ключ там, где сервис работает через OAuth.
  • Артефакты — только через инструменты. Код/HTML создаются только вызовом инструмента записи файла. Ответ агента — короткое резюме, не код-блок в тексте.
  • Цель прогона ≠ то, что продаёт бизнес клиента. goal (что клиент хочет от офиса) и niche/audience (что бизнес продаёт покупателям) — разные поля; смешение — известный класс бага.
  • Задача закрывается только приёмкой — не самим фактом «сдачи».
  • Plan-driven всегда — при сбое генерации плана берётся детерминированный резервный план.
  • Общие доступы — любой ключ доступен любому агенту, CEO не выбирает исполнителя «потому что у него ключ».
  • Единая ответственность — один агент на роль одновременно, без клонов «для параллельности».
  • Приоритет указаний клиента — прямая просьба клиента отменяет любую стратегию.
  • Реальный код, не описание — пуш в GitHub только после явного одобрения клиента.
  • Учёт расхода — инкрементальный, не по итогам прогона.
  • Multi-tenancy — никаких глобальных переменных состояния тенанта.

Полная и всегда актуальная версия правил — в CLAUDE.md корня репозитория; этот документ — читаемый снимок для человека, а не замена ему.
