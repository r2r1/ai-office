# System Audit Prompt — ai-office

*Спецификация промпта (не проза) — по дисциплине `.claude/skills/prompt-engineer/SKILL.md`:
точный формат вывода, явные ограничения, few-shot примеры хорошей/расплывчатой
находки, критерии успеха, версионирование с changelog. Использование:
скопировать блок «PROMPT v2» целиком в новую сессию Claude Code как первое
сообщение (self-directed — Claude Code проводит аудит сам себя, без внешнего
судьи).*

---

## Зачем отдельный файл, а не просто «повтори прошлый аудит»

Прошлый прогон (см. `docs/audit-dd-2026-07-06.md`) уже показал два конкретных
провала неспецифицированного промпта:

1. Первая версия утверждала «ноль автотестов» — галлюцинация уверенности:
   промпт не требовал `grep`/`ls` по `tests/` ПЕРЕД выводом, модель обобщила
   по паттерну «типичный проект такого размера».
2. Раздел про безопасность не поймал `_utf8_env()` = `dict(os.environ)`
   (полный env в сабпроцесс) — нашлось только при отдельном целевом проходе.

Оба — не «модель плохая», а спецификация была расплывчатой (ровно тот случай,
который описывает `prompt-engineer`: «If the model didn't do what you wanted,
the spec was ambiguous — not the model's fault»). v1 фиксировала исправленную
спецификацию для ТЕХНИЧЕСКОЙ части.

**v2 расширяет её на три вещи, которых v1 явно не требовала** (тот же принцип
«расплывчатая спецификация — не вина модели»): v1 не заставляла проверять
бизнес-логику (Objectives/Gap/Initiatives/BOS-цикл) отдельно от кода,
не заставляла явно проследить, ГДЕ бизнес-логика и код друг на друга влияют
(а не просто перечислить оба списком), и не требовала выхода в виде
конкретного плана действий — только диагноз без рецепта. v2 добавляет три
обязательных раздела вывода под это (см. PROMPT v2 ниже).

## Constraints (что проверяется ПЕРЕД тем, как промпт считается готовым к прогону)

- Формат вывода: Markdown, ровно те заголовки `##`, что в шаблоне ниже — не
  меньше и не больше разделов (иначе выход нельзя diff'ить между прогонами).
- Каждая находка (Finding) — ТОЛЬКО в формате `[СТАТУС] file:line — Заявление
  — Как проверено`. Заявление без `file:line` ИЛИ без явного «команда для
  проверки» в разделе Reasoning — недопустимо (см. Example 2 ниже).
- Длина: краткое резюме (Executive Summary) ≤ 400 слов. Основная часть без
  верхнего предела — но каждый абзац обязан ссылаться на конкретный
  артефакт (файл, коммит, тест), а не общие рассуждения.
- Тон: технический, без маркетинговых усилителей («потрясающе», «критично
  важно» без количественной опоры). Оценки — числом (баллы, %, счётчики), не
  прилагательными.
- Scope: только этот репозиторий (`ai-office`) по состоянию HEAD на момент
  запуска. Не сравнивать с гипотетическими «типичными проектами» — только с
  тем, что реально было в прошлом аудите (для diff) и с самим кодом.
- Бизнес-логика — НЕ отдельный от техники трек, а обязательная колонка
  «на что влияет технически» в каждой находке про Objectives/Gap/Plan/
  Acceptance/Execution Policy/Costs. Находка вида «Gap Analysis не учитывает
  X» без указания, какой КОД это реализует (`src/office/gap.py:NN`) и с чем
  из технических находок это связано — недопустима, ровно как и техническая
  находка без file:line.
- «Путь до идеального SaaS» — не список пожеланий. Каждый пункт roadmap
  ОБЯЗАН ссылаться на конкретную находку (техническую ИЛИ бизнес-логическую)
  из этого же прогона и явно называть, что ИМЕННО меняется в коде/данных/
  процессе. Пункт без привязки к находке — недопустим (тот же принцип, что
  и для Findings: заявление без опоры на проверку не публикуется).

## Reasoning (обязательная последовательность ДО вывода)

1. `git log --oneline -20` — что изменилось с прошлого аудита (если он есть).
2. Для КАЖДОГО раздела ниже — сначала команда проверки (`grep`/`ls`/чтение
   файла/`python tests/run_all.py`), потом вывод. Раздел без выполненной
   команды не пишется вообще, а помечается `[НЕ ПРОВЕРЕНО]` с указанием, что
   именно нужно запустить.
3. Если предыдущий аудит существует (`docs/audit-dd-*.md`) — явно сверить
   каждое КРИТИЧЕСКОЕ утверждение оттуда: подтвердилось / исправлено /
   устарело. Не переписывать секцию с нуля, если предыдущая всё ещё верна —
   ссылаться на неё и фиксировать «без изменений».
4. Разделять факт и мнение: раздел «Найдено» (что показала команда) отдельно
   от раздела «Значит» (интерпретация/риск).
5. Бизнес-логика трассируется от сущности к коду, не наоборот: для каждой
   бизнес-концепции (Objective, Gap, Initiative, Plan/Task, Acceptance,
   Execution Policy, Costs, World Model) — найти РЕАЛИЗУЮЩИЙ модуль
   (`src/office/objectives.py`, `gap.py`, `initiatives.py`, `plan.py`,
   `acceptance.py`, `execution_policy.py`, `costs.py`, `world.py`), прочитать
   его, и только потом писать находку. Затем явно проследить СВЯЗИ между
   модулями (например: `gap.py` читает `objectives.py` + `metrics.py` →
   пишет задачи в `plan.py` → `execution.py` их выполняет → `acceptance.py`
   закрывает → `world.py` фиксирует срез → `gap.py` пересчитывает на
   следующем цикле) — это ЦИКЛ, а не список независимых модулей.
6. Roadmap строится СНИЗУ ВВЕРХ от находок, а не сверху вниз от идеала:
   сначала выписать все находки [КРИТИЧНО]/[ВАЖНО], потом сгруппировать их
   в шаги roadmap, а не придумывать идеальную архитектуру и потом искать под
   неё оправдания в находках.

## PROMPT v2

```
Ты проводишь аудит репозитория ai-office (Claude Code, эта же сессия имеет
полный доступ к файловой системе и bash) — ТЕХНИЧЕСКИЙ и БИЗНЕС-ЛОГИЧЕСКИЙ
одновременно, с явным прослеживанием, как они друг на друга влияют. Это НЕ
ролевая игра «представь себя VC-панелью» — ты реальный агент с реальными
инструментами, и главное требование этой спецификации: НИ ОДНОЙ находки без
выполненной проверочной команды, и НИ ОДНОГО пункта плана без опоры на
находку из этого же прогона.

ПЕРЕД любым выводом:
1. `git log --oneline -20` и `git status --short`.
2. Если существует `docs/audit-dd-*.md` — прочитай последний по дате,
   выпиши каждое утверждение с пометкой [КРИТИЧНО]/[ВАЖНО] в чек-лист.
3. Прогони `python -m py_compile $(git ls-files '*.py')`,
   `python tests/run_all.py`, `cd webapp && npx tsc --noEmit`.
   Зафиксируй точные числа (сколько файлов/тестов прошло/упало).
4. Прочитай реализацию каждой бизнес-концепции ПЕРЕД тем, как писать про
   неё: `src/office/objectives.py`, `gap.py`, `initiatives.py`, `plan.py`,
   `acceptance.py`, `execution_policy.py`, `costs.py`, `world.py`,
   `milestones.py`. Составь граф вызовов между ними (кто кого читает/пишет)
   реальными grep/чтением, не по памяти о том, как «обычно» устроен BOS-цикл.

ФОРМАТ ВЫВОДА (ровно эти разделы, в этом порядке):

## Diff с прошлым аудитом
Для каждого [КРИТИЧНО]/[ВАЖНО] пункта из docs/audit-dd-*.md (если есть):
`[ПОДТВЕРЖДЕНО|ИСПРАВЛЕНО|УСТАРЕЛО] <пункт> — <команда, которой проверил>`

## Технические находки
Каждая строго в формате:
`[СТАТУС] path/to/file.py:123 — <заявление одним предложением> — <команда/наблюдение, которым подтверждено>`
СТАТУС ∈ {КРИТИЧНО, ВАЖНО, ЖЕЛАТЕЛЬНО, КОСМЕТИКА}.
Находка без `file:line` ИЛИ без явно названной команды проверки — брак,
не включать в вывод.

## Бизнес-логика: находки
Тот же формат `[СТАТУС] file:line — заявление — как проверено`, но заявление
— про бизнес-концепцию (Objective/Gap/Initiative/Plan/Acceptance/Execution
Policy/Costs/World Model), и file:line указывает на РЕАЛИЗУЮЩИЙ код, а не на
абстрактное рассуждение о процессе. Пример правильной находки: `[ВАЖНО]
src/office/gap.py:42 — replan() создаёт задачу под невыполненную Objective,
но не проверяет, не создана ли уже ИДЕНТИЧНАЯ задача другим циклом —
подтверждено чтением replan() и отсутствием дедуп-проверки по тексту задачи`.

## Как бизнес-логика и техника взаимодействуют
Не список, а граф/цепочка (можно текстом со стрелками): для каждого
значимого цикла (BOS-цикл целиком, Acceptance-гейт, Cost/Budget-гейт,
Skill/Capability-роутинг) — какие МОДУЛИ участвуют, в каком порядке, что
именно каждый читает и что пишет, и — САМОЕ ВАЖНОЕ — где в этой цепочке
технический дефект (из «Технических находок» выше) РЕАЛЬНО ломает бизнес-
результат (не гипотетически, а «вот конкретно этот баг → вот к какому
неверному бизнес-исходу он приводит»), и наоборот — где бизнес-требование
(например «указания клиента главнее стратегии») реализовано КАКИМ ИМЕННО
кодом и что будет, если этот код удалить/сломать.

## Путь до идеального SaaS
Roadmap из ШАГОВ, каждый шаг — 1 абзац строго в формате:
`### Шаг N: <название>
Опирается на находки: <список конкретных находок из разделов выше, по id/цитате>
Что меняется технически: <конкретные файлы/модули/данные>
Что меняется в бизнес-логике/процессе: <конкретно, не «стало лучше»>
Как узнать, что шаг сделан: <проверяемый критерий — тест, метрика, файл>`
Шаги упорядочены по зависимости (не по важности) — шаг N не может требовать
результата шага N+1. Явно пометь, какие шаги независимы и могут идти
параллельно. «Идеальный SaaS» здесь — не маркетинговая метафора, а
конкретное конечное состояние: определи его 3-5 измеримыми характеристиками
(например: горизонтально масштабируется до N тенантов без переархитектуры,
0 критических находок из этого прогона, автоматический regression-прогон в
CI, реальные метрики использования вместо one-off аудита) ДО того, как
писать шаги — и каждый шаг явно продвигает к одной или нескольким из них.

## Что НЕ проверено
Явный список: какие разделы (архитектура/security/performance/бизнес-логика/
взаимодействие/roadmap) в этот раз не покрыты и почему (не было времени /
нужен внешний доступ / требует реального прогона с деньгами) — не делать
вид, что покрыто всё.

## Executive Summary
≤ 400 слов. 3-5 предложений про state кодовой базы И бизнес-логики вместе
(не раздельно), 3-5 про главные риски (включая риски на стыке техники и
бизнес-логики, не только чисто технические), 2-3 про то, какие 1-2 шага
roadmap делать первыми и почему — с опорой на находки выше, без новых
непроверенных заявлений.

Если по итогу что-то из чек-листа прошлого аудита не удалось перепроверить
(например тест не запускается на этой машине) — так и напиши в разделе
«Что НЕ проверено», НЕ придумывай правдоподобный результат.
```

`[ИСПРАВЛЕНО] src/office/workspace.py:301 — _utf8_env() больше не делает dict(os.environ) целиком, использует allowlist из 13 переменных — подтверждено чтением функции + git log показывает коммит 93d0630 "execute_code/run_command больше не прокидывают в подпроцесс полное окружение"`

<example id="bad">
Вход: тот же файл, но модель НЕ читала его, а обобщила по паттерну «в
похожих проектах обычно так».

Расплывчатая находка (НЕ ДЕЛАТЬ ТАК):
`[ВАЖНО] Исполнение кода вероятно небезопасно, стоит проверить окружение процесса`

Почему это брак: нет `file:line`, нет команды проверки, "вероятно" — именно

писать находку, или пометить раздел `[НЕ ПРОВЕРЕНО]`, если не было времени.
</example>

Реальный кейс из прошлого прогона, который эта спецификация должна ловить
СТРУКТУРНО (не полагаясь на память модели):
`[КРИТИЧНО→ИСПРАВЛЕНО] Первая версия аудита (2026-07-06, до правки) заявила "ноль автотестов" без grep по tests/ — 11 файлов/71 тест существовали. Причина: раздел "Code Quality" не требовал явной команды `ls tests/` перед выводом. v1 этого промпта требует команду ПЕРЕД каждым разделом (см. </example>

<example id="business-interaction-good">
Хорошая запись во «Как бизнес-логика и техника взаимодействуют» (используй
как эталон структуры — конкретные модули/направления, не абстракция):

`BOS-цикл gap→plan→execution→acceptance→world→gap: gap.py:XX читает
objectives.py (desired state) + metrics.py (текущее значение) → при разрыве
вызывает plan.add_task() (plan.py:YY) → planning_engine.py маршрутизирует
задачу исполнителю → execution.py вызывает agent_factory.create() →
acceptance.py:ZZ гейтит закрытие задачи (build/functional/business) →
world.py:WW фиксирует срез после закрытия → на следующем цикле gap.py
пересчитывает разрыв по новому срезу. ТОЧКА ОТКАЗА: если acceptance.py
пропускает задачу без реальной проверки (см. техническую находку [ID]),
world.py зафиксирует срез, который НЕ отражает реальность — Gap Analysis на
следующем цикле будет считать цель достигнутой, хотя она не достигнута
(бизнес-исход: клиент не получает результат, а система думает, что всё ок).`

Расплывчатая версия того же (НЕ ДЕЛАТЬ ТАК): «Модули бизнес-логики связаны
между собой и влияют на технические компоненты» — нет ни одного имени файла,
ни направления связи, ни конкретной точки отказа.
</example>

## Test cases (прогони на промпте ПЕРЕД тем, как считать его готовым — по
дисциплине prompt-engineer: happy path + edge + failure mode)

1. **Happy path**: репозиторий с существующим `docs/audit-dd-*.md` и чистым
   `git status`. Ожидание: раздел «Diff с прошлым аудитом» заполнен, каждая
   находка содержит `file:line`, `tests/run_all.py` реально запущен (числа
   в выводе совпадают с тем, что видно в консоли).
2. **Edge — нет предыдущего аудита**: свежий клон без `docs/audit-dd-*.md`.
   Ожидание: раздел «Diff с прошлым аудитом» — одна строка «предыдущего
   аудита нет, полный прогон с нуля», не выдумывать несуществующий diff.
3. **Failure mode — тесты не запускаются на машине** (например Docker/npm
   недоступны для части проверок): раздел «Что НЕ проверено» явно называет,
   что именно не удалось прогнать и почему — вывод не должен утверждать
   "все тесты прошли", если команда не выполнялась.
4. **Edge — бизнес-логика без явного технического бага**: если ни одна
   техническая находка не влияет на конкретный бизнес-цикл — раздел «Как
   бизнес-логика и техника взаимодействуют» всё равно описывает граф связей
   (кто кого читает/пишет) и явно пишет «точек отказа не найдено в этом
   прогоне», а не пропускает раздел.
5. **Failure mode — находка без места в roadmap**: если находка [КОСМЕТИКА]
   не тянет на отдельный шаг roadmap — либо объединяется с соседней в один
   шаг, либо явно помечается «не включено в roadmap этой версии — низкий
   приоритет» в разделе «Что НЕ проверено». Находка не должна просто
   пропасть между разделом находок и roadmap без объяснения.

## Success criteria

- 100% находок (технических И бизнес-логических) содержат `file:line` +
  названную команду проверки (см. Constraints §2) — 0% находок в форме
  "вероятно"/"скорее всего"/"обычно".
- Diff-раздел покрывает КАЖДЫЙ пункт [КРИТИЧНО]/[ВАЖНО] предыдущего аудита,
  без пропусков (проверяется построчным сравнением со старым файлом).
- Раздел «Как бизнес-логика и техника взаимодействуют» называет минимум
  один конкретный цикл (модуль→модуль→модуль) с указанием реальной или
  отсутствующей точки отказа — не сводится к перечислению модулей без связей.
- Каждый шаг «Пути до идеального SaaS» содержит все 4 обязательных поля
  (опирается на находки / технически / бизнес-процесс / критерий готовности)
  и ссылается минимум на одну находку ИЗ ЭТОГО ЖЕ прогона.
- «Идеальное состояние SaaS» определено 3-5 измеримыми характеристиками
  ДО списка шагов — шаги без этого определения выше по тексту недопустимы.
- Раздел «Что НЕ проверено» непустой в любом прогоне короче полного (это
  ожидаемо и корректно — пустой раздел при неполном прогоне значит, что
  модель это скрыла, а не то, что покрытие было полным).
- Executive Summary ≤ 400 слов, каждое рискованное утверждение в нём имеет
  опору на находку из разделов выше этого же прогона.

## Changelog

### v2 — 2026-07-06
- Добавлены три обязательных раздела вывода: «Бизнес-логика: находки»
  (Objectives/Gap/Initiatives/Plan/Acceptance/Execution Policy/Costs/World
  Model — с тем же требованием file:line, что и у технических находок, но
  указывающим на реализующий код, а не на абстрактный процесс), «Как
  бизнес-логика и техника взаимодействуют» (граф/цепочка вызовов между
  модулями с явной точкой отказа, а не список модулей россыпью) и «Путь до
  идеального SaaS» (roadmap, где каждый шаг обязан ссылаться на находку ИЗ
  ЭТОГО ЖЕ прогона и иметь проверяемый критерий готовности — не список
  пожеланий).
- Reasoning дополнен пп. 5-6: бизнес-концепции трассируются от сущности к
  РЕАЛИЗУЮЩЕМУ модулю (не по памяти о «типичном BOS-цикле»), roadmap строится
  снизу вверх от находок, а не сверху вниз от придуманного идеала.
- Добавлены 2 few-shot примера (business-interaction-good, roadmap-good) и
  2 новых test case (бизнес-логика без явного техбага; находка без места в
  roadmap) — тот же принцип, что в v1: без примера "хорошо" модель по
  умолчанию сваливается в расплывчатые формулировки на новых, ранее не
  специфицированных разделах вывода.
- Мотивация: v1 покрывала только технический трек и оставляла бизнес-логику
  и общую стратегию неспецифицированными — ровно тот же класс проблемы
  («расплывчатая спецификация»), который v1 устраняла для технической части.

### v1 — 2026-07-06
- Первая версия. Написана после того, как прогон без такой спецификации
  (свободная форма, `docs/audit-dd-2026-07-06.md`) дал галлюцинацию
  уверенности («ноль автотестов» без проверки) и пропустил находку
  безопасности (`_utf8_env` = полный `os.environ`), позже найденную отдельным
  целевым проходом. v1 структурно требует команду проверки перед каждым
  разделом и явный формат находки с `file:line`, чтобы устранить оба класса
  ошибки, а не полагаться на то, что модель "будет внимательнее в следующий раз".
