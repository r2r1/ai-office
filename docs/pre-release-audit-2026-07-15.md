# AI-Office — pre-release симуляция и аудит

**Дата:** 2026-07-15. **Метод:** живой прогон реального билда (`npm run build` + `demo-preview`, `office-real`), прямые вызовы API, чтение исходников, юнит-тесты. **Ограничение окружения:** в середине сессии внешняя сеть из песочницы перестала отвечать (не отвечали ни stripe.com, ни example.com, ни wikipedia.org — не специфично для одного домена, инфраструктурный сбой, совпавший по времени с временной недоступностью classifier'а). Из-за этого этапы 1–6 (лендинг-скан, LLM-онбординг) проверены комбинацией: (а) живых скриншотов/тестов, сделанных РАНЬШЕ в этой же сессии, когда сеть работала (issue #19–#25), и (б) чтения кода. Этапы 7–19 проверены полностью вживую через `DEMO_MODE=1` (`src/office/demo.py` — заранее прописанный сценарий офиса, не требует сети/LLM) плюс прямые вызовы `/api/world`, `/api/understanding`, `/api/agents` и т.д. на реальном бэкенде.

Это ОДИН глубокий проход, не буквально бесконечный цикл «симуляция→фикс→симуляция» — в рамках одной сессии это физически не сделать корректно. Каждая находка ниже — результат реального наблюдения (скриншот/API-ответ/код), а не предположения.

## 1. Журнал пользователя (симуляция)

### Этапы 1–4: Лендинг → первый контакт → первое впечатление → исследование компании
*(проверено ранее в этой же сессии, сеть была доступна)*

Пользователь открывает лендинг. Видит: `Business Operating System` бейдж, заголовок «Поставьте цель. Офис сам её достигнет.», и — не форму регистрации — поле «Прежде чем начать — покажите мне свою компанию» с кнопкой «Начать исследование». Справа — живая изометрическая панель «ОФИС СЕЙЧАС» с реальной анимацией статусов отделов.

Вводит `stripe.com`, жмёт «Начать исследование». Реакция:
```
✓ Нашёл сайт
✓ Нашёл Telegram          (если есть соцсети)
✓ Понял, чем вы занимаетесь
```
пауза → *«Нашёл кое-что интересное…»* → **«Кстати — нет чёткого призыва к действию, посетитель не понимает, что делать дальше»** → остальные наблюдения списком → карточка гипотезы о стадии бизнеса («Кажется, вы на стадии запуска — …») с кнопками-корректировками → «Я могу продолжить изучение компании... Продолжить исследование →».

**Ощущение:** реальный вау-момент — это не имитация, `company_scan.py` реально парсит HTML, `_stage_hypothesis` реально классифицирует через LLM с фолбэком на эвристику за секунды (после фикса issue #21 — раньше был баг на 156.9 секунд, найден и исправлен в этой же сессии).

**Где пользователь мог заскучать:** между «Нашёл сайт» и первым выводом проходит время ожидания реального сетевого скана (обычно 1-3 сек, приемлемо).

**Найденное сейчас:** ничего нового не всплыло на этом участке при повторном коде-ревью — потенциальный риск (см. §3, Medium) в том, что вся детективная пауза построена на `setTimeout`-таймерах в `ScanBox`, а НЕ на реальном ответе сервера по частям — то есть «расследование» полностью завершено ДО того, как начинается театральная пауза. Это осознанный компромисс (сервер отвечает мгновенно единым JSON, разбивка на паузы — чисто фронтенд), но означает: если реальный скан занял 8 секунд (например, сайт медленный), пользователь сначала ждёт молча 8 секунд, а потом видит "мгновенную" анимацию расследования — то есть ощущение "AI на глазах роется" — иллюзия, а не факт. Для честности продукта (сам аудит требует не фейковать) это стоит зафиксировать как средний приоритет: индикатор загрузки должен покрывать РЕАЛЬНОЕ время сети, а не начинаться только после.

### Этап 5: Регистрация

Кнопка «Продолжить исследование →» открывает `AuthModal` (GitHub / Google / email). Это НЕ проверялось живьём в этом проходе (требует реального OAuth-провайдера, недоступно в песочнице). По коду: `Gate.tsx` → `onSuccess={() => setPhase("app")}`. Разумно, механически просто.

**Находка (Low):** между «сохранить исследование» и формой логина нет НИКАКОГО текста, объясняющего, что произойдёт с уже накопленными данными («находки сохранятся, вы не начинаете с нуля») — момент, где обещание из ScanBox («Я могу продолжить изучение») визуально обрывается стандартной формой OAuth без напоминания о контексте.

### Этап 6: Онбординг

`OnboardingFlow.tsx`: свободное поле + необязательный URL. Если пользователь пришёл со сканом с лендинга — поле уже предзаполнено и показывает `✓ Уже посмотрел X — нашли Y точек роста` (issue #20). Хорошо продумано, реально работает (проверено раньше в сессии).

**Находка (уже задокументированная, не новая):** в коде существует ПАРАЛЛЕЛЬНЫЙ, полностью нерабочий 3-сценарийный структурированный интерфейс онбординга (`onboarding.MODES`, `/api/onboarding/modes`, `/api/onboarding/finish`) — мёртвый код, не подключённый к фронтенду. Найдено раньше в этой сессии (issue #25 решение). Оставлено как есть — реализация нового 4-го сценария была сознательно направлена в РЕАЛЬНЫЙ используемый флоу, а не в мёртвый.

### Этапы 7–9: Создание компании / офиса / рождение команды

Живой прогон в `DEMO_MODE`: клик «Демо» → **КРИТИЧЕСКИЙ БАГ, НАЙДЕН И ИСПРАВЛЕН ЗДЕСЬ** — переход в `<App/>`. `demo.run()` начинает публиковать сценарий: CEO нанят → ресёрчер/стратег/архитектор наняты → BOOTSTRAP (исследование рынка, стратегия, ТЗ) → CEO открывает Технический отдел → CTO нанимает разработчика → и т.д.

Реальные сообщения из живого API (`/api/agents`, журнал):
```
🧭 CEO: Сначала нужен продукт — открываю Технический отдел
👔 CTO: Беру разработчика — соберём лендинг и бота
📝 developer_1: записан app/main.py
📝 developer_1: записан static/landing.html
Разработчик: Бот квалифицирует лид за 3 сек, лендинг собирает заявки
👔 CTO: Отдел сдал MVP — докладываю CEO, продукт готов
🧭 CEO: Продукт есть — нужны клиенты, открываю Отдел продаж
...
💰 Прогресс: 2 клиента подписали договор = 80,000₽
```

**ПОПЫТКА ПЕРЕЙТИ НА ВКЛАДКУ «РАБОТА» ПОЛНОСТЬЮ ПРОВАЛИЛАСЬ** — навигация была полностью мертва (см. §2, Critical #1). Это **самая серьёзная находка всего аудита**: пользователь, впервые открывший продукт и нажавший на любую вкладку кроме «Обзор», не мог попасть НИКУДА. Исправлено в этой же сессии (см. §4).

После фикса: «Команда» показывает всех 10 агентов с реальными статусами («ДУМАЕТ»/«ГОТОВО»/«ЖДЁТ»), их мыслями и последним сообщением — производит впечатление живого офиса. Достоверно, не шаблонно.

### Этап 10: Первое общение с CEO

Открыл чат с CEO, написал «Привет! Как продвигается работа?», отправил.

**НАЙДЕННЫЙ БАГ (High), ИСПРАВЛЕН ЗДЕСЬ:** DEMO_MODE обещает «демо без расхода токенов» (CLAUDE.md §2), но `/api/ask` безусловно вызывал `chat.ask()` → реальный LLM. Расход вырос с $0.0004 до $0.0005 за одно сообщение — подтверждено живым замером `/api/world.business_state.spend_usd`. Посетитель демо-режима мог случайно тратить реальные деньги оператора. Исправлено: короткое замыкание на канонический ответ в DEMO_MODE.

### Этапы 11–17: План → задачи → работа агентов → чаты → проект → результаты → завершение

**Реальная архитектурная находка (Medium):** `demo.run()` регистрирует агентов через `registry.register(..., task=texts)`, но НИКОГДА не вызывает `plan.set_tasks()`. Прямой вызов `/api/world` подтвердил: `business_state.plan = {"total": 0, "done": 0, "percent": 0}` на протяжении ВСЕГО сценария, при этом лента демонстрирует активную работу 10 агентов. Итог: вкладка «Работа» (`ProjectView`) для демо-режима показывает пустую доску («Инициативы пока нет») одновременно с тем, как в «Команда» и в общем журнале видна кипящая деятельность. Разрыв между нарративом и реальными данными плана — для потенциального клиента, кликающего между вкладками, это выглядит как несостыковка (одна вкладка говорит «всё работает», другая — «ничего не происходит»).

**Здоровье компании нестабильно скачет (Medium):** зафиксировано живьём — между двумя последовательными опросами `/api/progress`/Dashboard здоровье менялось 32→20→32 без видимой причины пользователю. Причина в коде: `demo.run()` вызывает `registry.reset()`/`org.reset()` в начале КАЖДОГО повтора сценария (цикл длится ~90 секунд + пауза 8 сек), и health-скор считается из текущего состава открытых отделов, который на секунду становится пустым при ресете. Это баг ИМЕННО демо-сценария (не влияет на реальный прод-офис, где отделы не ресетятся), но именно демо — то, что видит потенциальный клиент ДО регистрации, и «здоровье компании падает на глазах» — плохая витрина.

### Этап 18–19: Работа офиса после завершения / повторное использование

`demo.run()` зацикливается бесконечно («🔁 Демо завершено. В реальном режиме офис работает бесконечно.» → пауза 8 сек → всё заново). Это ЧЕСТНО (текст прямо говорит, что это цикл демо), но означает, что живой пользователь, оставшийся дольше ~2 минут на демо, увидит, как ВСЯ команда исчезает и нанимается заново с нуля — включая CEO. Для демо-режима, единственная цель которого — «дать пощупать продукт без расхода токенов», это довольно резкий и потенциально пугающий сброс (агент, с которым только что переписывались, «увольняется» без предупреждения).

## 2. Критические находки (Critical)

### #1 — Навигация полностью мертва после входа в приложение (P0)
**Как нашли:** живой клик по «Работа»/«Команда» в NavRail (и дублирующим CTA-кнопкам) НЕ переключал вид — ни разу, ни при повторных попытках, ни при полной перезагрузке страницы, ни при прямом вызове `onClick` из DevTools. Подтверждено чтением React fiber: внутреннее состояние `view` РЕАЛЬНО менялось на `"project"`/`"team"`, но экран не переключался — рендер оставался на Dashboard.
**Причина:** `webapp/src/app/App.tsx` — `<AnimatePresence mode="wait">` вокруг блока переключения разделов. `mode="wait"` требует, чтобы exit-анимация УХОДЯЩЕГО раздела полностью завершилась, прежде чем смонтировать новый. Если exit по любой причине не долетает до конца (что и произошло вживую), новый раздел не монтируется НИКОГДА — навигация продукта оказывается заложницей декоративной анимации перехода.
**Почему это Critical:** это ровно тот случай, когда «пользователь теряется» и не может продолжить путь ни при каких условиях — вся ценность продукта («Работа», «Команда», «Результаты») становится недостижимой одним и тем же одним багом.
**Исправлено:** `mode="wait"` убран (default-режим монтирует новый раздел сразу, не дожидаясь ухода старого); дополнительно `exit={{..., pointerEvents: "none"}}` — если exit-анимация всё равно застрянет, «призрак» больше не будет перехватывать клики поверх нового контента (тот же защитный приём, что уже применялся для Digest/Understanding-попапов, issue #12 этой же сессии).
**Проверено вживую:** после фикса «Работа», «Команда» (полный список из 10 агентов, реальные статусы), чат с CEO (отправка сообщения, инкремент расхода) — всё работает.

## 3. High

### #2 — DEMO_MODE не гарантирует нулевой расход при переписке с агентом
См. этап 10 выше. Исправлено (короткое замыкание `/api/ask` под `DEMO_MODE`). **Не исправлено (осознанно, по нехватке времени):** тот же класс уязвимости в `/api/chat` (общий чат) → `_steer_from_chat()` → `orchestrator.interpret_directive` (LLM), fire-and-forget задача, тоже безусловно вызывает реальный LLM в demo-режиме. Логика этой функции сложнее (ветвление discovery/CEO-триаж), не стал вносить туда правку вслепую без отдельной проверки — зафиксировано как оставшийся риск.

### #3 — Онбординг: индикатор «расследования» не покрывает реальное время сети
См. этап 1-4 выше. Не исправлено в этом проходе — требует более глубокой переделки `ScanBox` (стриминг статуса скана с бэкенда вместо чисто клиентских таймеров), отдельная задача.

## 4. Medium

### #4 — Демо-сценарий не пишет план задач (`plan.set_tasks()` никогда не вызывается)
Разрыв между «журнал говорит про кипящую работу» и «доска задач пуста». Не исправлено — правка `demo.py` для генерации согласованного демо-плана требует продумывания (какие задачи показать, в каком статусе), не бросовая правка.

### #5 — Health-скор демо-компании скачет 32→20→32 из-за периодического `registry.reset()`
Визуально выглядит как деградация компании на глазах у потенциального клиента. Не исправлено — требует решения, сглаживать ли health-скор во время ресета демо-сценария или убрать ресет вовсе (сделать сценарий линейным без зацикливания per session).

### #6 — Бесконечный цикл демо «увольняет» всю команду каждые ~90 секунд без предупреждения
Резкий, необъяснённый сброс для того, кто задержался на демо дольше пары минут. Не исправлено.

### #7 — После регистрации нет текста, подтверждающего сохранность находок со скана
Между ScanBox CTA и формой логина нет явного «содержимое сохранено» сообщения. Мелкая, но реальная просадка доверия в переходный момент. Не исправлено.

## 7. Что осталось нерешённым и почему
- **#2 (частично)** — общий чат `/api/chat` тоже может тратить токены в демо; не тронул код с более сложным ветвлением (discovery/triage) без отдельной проверки, чтобы не внести новый баг вслепую.
- **#3, #4, #5, #6** — каждое требует отдельного продуктового решения (как именно показывать прогресс скана, что показывать на доске задач демо, сглаживать ли health, обрывать ли зацикливание демо), не бросовые правки «на глаз» — фиксирую как находки, не додумываю решение за продукт-оунера в объёме одного прохода.

## 9. Главный вопрос

**Доверил бы я этому продукту свой бизнес, увидев его впервые как предприниматель?**

**До фикса навигации — нет**, и дело не в тонкостях UX: после клика «Демо»/входа я физически не мог попасть НИКУДА, кроме стартового экрана. Ни один продукт с полностью нерабочей навигацией не заслуживает доверия, вне зависимости от того, насколько хорош лендинг.

**После фикса — да, с оговорками.** ScanBox (детективный темп, честная гипотеза о стадии, прозрачное «предположение vs подтверждено») — это реально продукт другого уровня, не шаблонный AI-обвес. Но demo-режим (то, что видит СКЕПТИЧЕСКИЙ предприниматель ДО того, как довериться) сейчас рассинхронизирован (пустая доска задач при кипящей ленте, скачущий health-скор, безжалостный 90-секундный сброс команды) — именно те несостыковки, которые опытный CEO заметит и спросит «а с реальными данными так же будет?». Это не блокер доверия, но и не тот уровень полировки, которого продукт заслуживает, учитывая качество остального.
